CPU Scheduling

With more runnable processes than CPU cores, the scheduler decides who runs, when and for how long. Different goals lead to different algorithms.

A process alternates between computing and waiting for I/O. One continuous run on the CPU is a CPU burst, and a process that mostly waits for devices is I/O-bound. The scheduler chooses the next process and the dispatcher hands it the CPU (performing the context switch). Preemption means the OS can take the CPU away from a running process before its burst is over.

Beyond the textbook

Module 8 simulates all of these: feedback queues, real-time guarantees and multicore balancing.

  • Multilevel feedback queues (MLFQ) approximate SJF without knowing burst lengths: new jobs start at high priority and sink if they use their whole quantum.
  • Linux uses a fair scheduler (CFS, and more recently EEVDF) that tracks how much CPU time each task has received and picks the one furthest behind.
  • Real-time systems use algorithms such as rate-monotonic or earliest-deadline-first, where meeting deadlines matters more than average speed.
  • Multicore schedulers add load balancing and processor affinity, because migrating a task throws away its warm caches.

AdvancedGoing deeper: how real schedulers work
  • Multilevel feedback queues. Real systems cannot know a job’s length in advance, so they estimate it from behavior: a task that uses its whole time slice drops to a lower-priority queue, and one that blocks early stays high. Interactive programs are favored without anyone labeling them.
  • Linux CFS and EEVDF. The Completely Fair Scheduler tracks each task’s virtual runtime and always runs the one that has had the least, kept in a red-black tree. Newer kernels replace it with EEVDF, which also considers each task’s latency requirement.
  • Multicore adds a second problem. Each core usually has its own run queue, so the OS must balance load without losing cache affinity: a task moved to another core starts with a cold cache. Processor affinity lets a program pin itself to specific cores.
  • Real-time scheduling. Rate-monotonic scheduling gives the highest priority to the shortest period, and earliest-deadline-first always runs the task whose deadline is nearest. Both have schedulability tests, and a missed deadline is a failure, not a slowdown.
  • Priority inversion. If a low-priority task holds a lock that a high-priority task needs, a medium-priority task can run ahead of both. The 1997 Mars Pathfinder resets were caused by exactly this. The fix is priority inheritance: the lock holder temporarily takes the waiter’s priority.
