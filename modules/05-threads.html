Threads & Parallel Performance

A thread is a unit of CPU execution inside a process. Threads share the process's memory, so they can cooperate cheaply, but that sharing is also where the danger lies.

Threads vs. processes

PropertyProcessThread (within a process)
Address spaceOwnShared with the other threads
Heap, globals, open filesOwnShared
Stack, registers, program counterOwnOwn (per thread)
Creation / switch costHigherLower (no address-space switch)
IsolationStrong: a crash stays in one processWeak: one bad thread can corrupt or crash all

Benefits: responsiveness (UI stays alive while work runs), resource sharing, cheaper creation, and scalability across cores.

Threading models

  • User-level threads are managed by a library. They are fast, but the kernel sees one thread, so a blocking system call stalls all of them (many-to-one).
  • Kernel-level threads are scheduled by the OS. A blocking call only blocks one thread and threads can use several cores (one-to-one, used by Linux, Windows and macOS).
  • Thread pools reuse a fixed set of worker threads, avoiding creation cost and bounding resource use.
# Python: threads vs. processes
import threading, multiprocessing

def work(n): return sum(i*i for i in range(n))

# CPython's Global Interpreter Lock (GIL) lets only one thread run Python bytecode
# at a time, so threads help I/O-bound code but not CPU-bound code.
# For CPU-bound work, use processes:
with multiprocessing.Pool() as pool:
    results = pool.map(work, [10**6] * 8)

Try it: split work across threads

Why C is the clearer version here: POSIX threads give true parallelism. The four threads can run on four cores at the same time, and the program is a direct picture of the lesson: split the work, start the threads, join them, combine the results.

/* Four threads each sum the squares of their own quarter of a range. Build with: gcc -std=c99 -D_POSIX_C_SOURCE=200809L -pthread */
#include <pthread.h>
#include <stdio.h>

#define THREADS 4
#define N 1000000ULL

typedef struct { unsigned long long from, to, sum; } job_t;

static void *partial_sum(void *arg) {
    job_t *job = arg;
    unsigned long long s = 0;
    for (unsigned long long i = job->from; i < job->to; i++) s += i * i;
    job->sum = s;                                   /* (3) each thread writes only to its own slot, so no lock is needed */
    return NULL;
}

int main(void) {
    pthread_t threads[THREADS];
    job_t jobs[THREADS];
    for (int t = 0; t < THREADS; t++) {             /* (1) split the range [0, N) into one piece per thread */
        jobs[t].from = N * (unsigned long long)t / THREADS;
        jobs[t].to = N * (unsigned long long)(t + 1) / THREADS;
        pthread_create(&threads[t], NULL, partial_sum, &jobs[t]);   /* (2) start the thread: it runs while main continues */
    }
    unsigned long long total = 0;
    for (int t = 0; t < THREADS; t++) {
        pthread_join(threads[t], NULL);             /* (4) wait for the thread, then it is safe to read its result */
        printf("thread %d summed the squares of [%llu, %llu): %llu\n", t, jobs[t].from, jobs[t].to, jobs[t].sum);
        total += jobs[t].sum;
    }
    unsigned long long expected = (N - 1) * N * (2 * N - 1) / 6;      /* closed formula for 0^2 + 1^2 + ... + (N-1)^2 */
    printf("total = %llu (matches the formula: %s)\n", total, total == expected ? "True" : "False");
    return 0;
}

The structure is the same, but speed is not. In standard CPython a global interpreter lock lets only one thread run Python code at a time, so this pure-Python sum is no faster with four threads than with one. Threads still help when they wait for I/O. For CPU-bound work Python programs use multiprocessing or a free-threaded build. The example shows the pattern, not the speedup.

"""Four threads each sum the squares of their own quarter of a range."""
import threading

THREADS = 4
N = 1_000_000
sums = [0] * THREADS


def partial_sum(slot, start, stop):
    sums[slot] = sum(i * i for i in range(start, stop))   # (3) each thread writes only to its own slot, so no lock is needed


pieces = [(t, N * t // THREADS, N * (t + 1) // THREADS) for t in range(THREADS)]   # (1) split the range [0, N) into one piece per thread
threads = [threading.Thread(target=partial_sum, args=piece) for piece in pieces]
for t in threads:
    t.start()                                              # (2) start the thread: it runs while the main thread continues
total = 0
for t, (slot, start, stop) in zip(threads, pieces):
    t.join()                                               # (4) wait for the thread, then it is safe to read its result
    print(f"thread {slot} summed the squares of [{start}, {stop}): {sums[slot]}")
    total += sums[slot]
expected = (N - 1) * N * (2 * N - 1) // 6                  # closed formula for 0^2 + 1^2 + ... + (N-1)^2
print(f"total = {total} (matches the formula: {total == expected})")

How much speedup can you expect?

Amdahl's law says that if a fraction p of a program can be parallelized across N cores, then

speedup = 1 / ((1 − p) + p / N)

The serial fraction (1 − p) sets a hard ceiling of 1/(1 − p) no matter how many cores you add. Gustafson's law gives the more optimistic view that when you have more cores you usually also solve bigger problems.

Try it: set p = 90% and add cores. The curve flattens near 10×. Going from 8 to 16 cores buys little, so work on the serial part instead.

The price of switching

Each context switch costs time without doing useful work. If the quantum is q and a switch costs s, the useful fraction is q / (q + s). But a longer quantum makes every process wait longer between turns.

AdvancedGoing deeper: what threads cost and what they buy
  • Thread stacks and thread-local storage. Each thread has its own stack (typically 8 MiB of address space on Linux, committed lazily) and its own thread-local variables, which is why a thousand threads uses far more address space than a thousand function calls.
  • Many-to-many models and user-level threads. Go goroutines and Erlang processes are scheduled by the language runtime on top of a few kernel threads, so creating one costs a few kilobytes and a switch costs no system call. The price is that a blocking system call must be handled by the runtime.
  • Event loops as an alternative. A server can handle thousands of connections on one thread by waiting with epoll, kqueue or io_uring and never blocking. Node.js and Python’s asyncio are built this way.
  • Amdahl versus Gustafson. Amdahl’s law fixes the problem size. Gustafson’s observation is that larger machines are used for larger problems, so the serial fraction matters less than the formula suggests when the parallel part grows with the machine.
  • False sharing. Two threads writing different variables that happen to sit in the same 64-byte cache line force that line to bounce between cores. Padding the variables apart can make a program several times faster without changing its logic.
