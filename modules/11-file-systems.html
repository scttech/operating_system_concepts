File Systems

A file system turns a raw array of disk blocks into named, persistent, protected files and directories.

Files and directories

  • A file is a named collection of bytes plus metadata: size, owner, permissions, timestamps, location of its blocks.
  • A directory is itself a file that maps names to files (in Unix: names to inode numbers).
  • Programs refer to open files via a file descriptor, an index into a per-process table that points to system-wide open-file entries.
  • Access methods: sequential (read next), direct/random (read block k) and indexed.

Allocating blocks to files

How a file's blocks are placed on disk determines speed, space efficiency and how well files can grow.

  • Contiguous: fast and simple, but suffers external fragmentation and growth problems (like contiguous memory allocation).
  • Linked: no external fragmentation; terrible random access, and one lost pointer loses the rest of the file.
  • FAT: moves the links into a table (the File Allocation Table), usually cached in memory; simple and robust but the table can grow large.
  • Indexed / inode-based: an index structure lists the blocks; good random access with no external fragmentation.

Inodes

An inode stores everything about a file except its name: permissions, owner, timestamps, size and block pointers. A classic Unix inode has about 12 direct pointers (fast for small files) followed by single, double and triple indirect pointers that point to blocks of pointers. Small files stay quick, while huge files remain possible.

Check the quiz answer yourself: 4 KiB blocks and 4-byte pointers give 1024 pointers per indirect block. With 12 direct and one single-indirect pointer that's (12 + 1024) × 4 KiB = 4,144 KiB. Switch on double-indirect and the maximum jumps to about 4 GiB.

Links

  • Hard link: another directory entry pointing to the same inode. The inode keeps a link count; data is freed when it reaches 0. Cannot cross file systems.
  • Symbolic link: a small file containing a path. It can cross file systems and point to directories, but dangles if the target goes away.

Try it: hard links, symbolic links and inodes

Why C is the clearer version here: link, symlink, unlink and stat are the system calls themselves, and st_ino and st_nlink are the inode fields the lesson describes.

/* Hard links, symbolic links and inodes. Unix only. */
#define _POSIX_C_SOURCE 200809L
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/stat.h>
#include <unistd.h>

int main(void) {
    char dir[] = "/tmp/osc_links_XXXXXX", orig[64], hard[64], soft[64];
    if (mkdtemp(dir) == NULL) return 1;
    snprintf(orig, sizeof orig, "%s/original.txt", dir);
    snprintf(hard, sizeof hard, "%s/hard.txt", dir);
    snprintf(soft, sizeof soft, "%s/soft.txt", dir);

    int fd = open(orig, O_CREAT | O_WRONLY, 0644);
    if (fd < 0 || write(fd, "hello\n", 6) != 6) return 1;
    close(fd);
    struct stat a, b, c;
    if (stat(orig, &a) != 0) return 1;
    printf("created original.txt: link count %ld\n", (long)a.st_nlink);

    if (link(orig, hard) != 0) return 1;            /* (1) a hard link is a second NAME for the same inode */
    stat(orig, &a); stat(hard, &b);
    printf("after link(): link count %ld, same inode: %s\n", (long)a.st_nlink, a.st_ino == b.st_ino ? "yes" : "no");

    if (symlink(orig, soft) != 0) return 1;         /* (2) a symbolic link is a separate small file that holds a PATH */
    lstat(soft, &c);
    printf("the symbolic link has its own inode: %s\n", c.st_ino != a.st_ino ? "yes" : "no");

    if (unlink(orig) != 0) return 1;                /* (3) remove the original name: the data lives on while any name remains */
    stat(hard, &b);
    char text[16] = "";
    fd = open(hard, O_RDONLY);
    if (fd >= 0) { ssize_t n = read(fd, text, sizeof text - 1); text[n > 0 ? n : 0] = '\0'; close(fd); }
    printf("after removing the original name: link count %ld, data still readable: %s\n", (long)b.st_nlink, text[0] == 'h' ? "yes" : "no");

    int through_symlink = open(soft, O_RDONLY);     /* (4) the symbolic link still holds the old path, which no longer exists: it dangles */
    printf("the symbolic link now dangles (opening it fails): %s\n", through_symlink < 0 ? "yes" : "no");
    if (through_symlink >= 0) close(through_symlink);

    unlink(hard); unlink(soft); rmdir(dir);
    return 0;
}

Python’s os module mirrors the calls one-to-one (os.link, os.symlink, os.unlink, os.stat), so this is no more contrived than the C version. It needs Linux or macOS: on Windows, hard links exist but behave differently and symbolic links usually need extra privileges.

"""Hard links, symbolic links and inodes. Unix only."""
import os
import shutil
import tempfile

folder = tempfile.mkdtemp(prefix="osc_links_")
orig, hard, soft = (os.path.join(folder, n) for n in ("original.txt", "hard.txt", "soft.txt"))

with open(orig, "w") as f:
    f.write("hello\n")
print(f"created original.txt: link count {os.stat(orig).st_nlink}")

os.link(orig, hard)                                  # (1) a hard link is a second NAME for the same inode
a, b = os.stat(orig), os.stat(hard)
print(f"after link(): link count {a.st_nlink}, same inode: {'yes' if a.st_ino == b.st_ino else 'no'}")

os.symlink(orig, soft)                               # (2) a symbolic link is a separate small file that holds a PATH
print(f"the symbolic link has its own inode: {'yes' if os.lstat(soft).st_ino != a.st_ino else 'no'}")

os.unlink(orig)                                      # (3) remove the original name: the data lives on while any name remains
with open(hard) as f:
    text = f.read()
print(f"after removing the original name: link count {os.stat(hard).st_nlink}, data still readable: {'yes' if text.startswith('h') else 'no'}")

try:                                                 # (4) the symbolic link still holds the old path, which no longer exists: it dangles
    open(soft).close()
    dangles = "no"
except OSError:
    dangles = "yes"
print(f"the symbolic link now dangles (opening it fails): {dangles}")
shutil.rmtree(folder)

Free space and reliability

  • Free-space tracking: bitmaps (1 bit per block) or free lists/extents.
  • Crash consistency: a single logical operation (creating a file) touches several structures (bitmap, inode, directory). A crash in the middle leaves them inconsistent. Old systems ran fsck over the whole disk; modern file systems use journaling (write-ahead log) or copy-on-write designs to recover quickly.
  • Performance: the buffer cache, read-ahead, delayed writes and extents (ranges of blocks instead of single pointers, as in ext4 and NTFS).
  • Layering: a Virtual File System (VFS) layer lets the same system calls work across ext4, NTFS, NFS and others.

AdvancedGoing deeper: what modern file systems add
  • Journaling. Without it a crash in the middle of an update can leave the structures inconsistent, so older systems had to scan the whole disk at boot (fsck). A journal records the intended change first, so recovery replays or discards it in seconds. Most systems journal only metadata by default, which keeps structure safe but not necessarily your data.
  • Copy-on-write file systems. ZFS, Btrfs and APFS never overwrite live blocks. They write a new version and then switch a pointer, which makes snapshots nearly free and makes a torn write impossible. The cost is fragmentation and more work to track free space.
  • Extents instead of block lists. Modern systems (ext4, NTFS, XFS) store a file as a few (start, length) ranges rather than one pointer per block, so a large contiguous file needs only a handful of entries and the classic indirect-block limits do not apply.
  • fsync and lying disks. A successful write only means the data reached the page cache. Durability needs fsync, and database authors worry about drives that acknowledge writes before they are on stable media. Many “lost data after power failure” stories come from skipping this.
  • Checksums and silent corruption. Disks sometimes return wrong data without an error. ZFS and Btrfs store a checksum with every block pointer and, with redundancy, repair what fails. Traditional systems trust the device.
  • Directories are files too. A directory is a file whose contents map names to inode numbers, which is why a hard link is just another entry and why large directories use hash tables or B-trees to avoid slow linear searches.
