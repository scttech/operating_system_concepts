Module 17

Advanced Scheduling

The algorithms in Module 4 assume that the scheduler knows how long each job will run, that all that matters is average speed, and that there is one CPU. Real systems break all three assumptions. This module covers the answers: queues that learn which jobs are interactive, schedulers that guarantee deadlines, and schedulers that spread work across many cores.

Learning from behavior: feedback queues

Shortest-job-first gives the best average waiting time, but it needs each job’s run time in advance, which an operating system never has. The multilevel feedback queue (MLFQ) approximates it by watching what jobs do. A handful of rules are enough:

  1. A new job starts in the top queue.
  2. The scheduler runs a job from the highest non-empty queue (round robin inside a queue). A higher queue always preempts a lower one.
  3. A job that uses its whole time slice is probably CPU-bound, so it moves down one queue. (Lower queues typically have longer slices, so the long jobs switch less often.)
  4. A job that gives up the CPU before its slice ends (to wait for a key press or a disk read) is probably interactive, so it keeps its level.
  5. Every so often, a priority boost moves every job back to the top, so nothing starves and a job that changes behavior is noticed.

Try it: in the first workload, watch the long job (long) sink to the lowest queue while the short interactive jobs stay at the top and respond immediately. Now switch to the second workload, a stream of short jobs, and notice that the long job gets no CPU for a long stretch. Turn on a priority boost every 6 ticks: the long job gets a share. The cost is that the short jobs now finish a little later. Every setting is a trade-off between responsiveness and fairness.

The scheduler can be fooled. A program that issues a tiny read just before its slice ends looks interactive forever, and so keeps the top queue while hogging the CPU. This is why real implementations count the total CPU time used at a level rather than only the last burst.

Meeting deadlines: real-time scheduling

A real-time system is correct only if it finishes work on time. A brake controller or an audio buffer cannot be “on average fast”. The usual model is a set of periodic tasks: task i releases a job every Ti ticks, each job needs Ci ticks of CPU, and it must finish before the next release, its deadline. The load the tasks place on the CPU is their utilization, U = Σ Ci/Ti. If U is more than 1 no algorithm can succeed. The question is how close to 1 each algorithm can go.

  • Rate-monotonic: fixed priorities, shortest period highest. Simple and predictable. It is guaranteed to work when U ≤ n(21/n − 1), which is 0.828 for two tasks and falls toward 0.693 as tasks are added. Above that it may still work; the bound is sufficient, not necessary.
  • Earliest deadline first: priorities change as time passes; the job with the nearest deadline runs. On one CPU it is optimal: it meets every deadline exactly when U ≤ 1.

Try it: the first task set has U = 0.97. Under rate-monotonic, T2 is preempted by T1 at tick 5 and finishes at tick 8, one tick after its deadline of 7. EDF notices that T2’s deadline is nearer and finishes both. Then try “U = 1.00”, where the periods are multiples of each other (harmonic), and rate-monotonic reaches 100% too. Finally, push the utilization above 1 and watch every algorithm fail.

Try it: simulate both algorithms

Why C is the clearer version here: the scheduler is a handful of comparisons per tick, and C shows that the only difference between the two algorithms is the rule in comments (1) and (2) that chooses the next job. Real real-time kernels are written in C for the same reason: the cost of each decision is visible and bounded. (The root for the guarantee is found by bisection, so no math library is linked.)

/* Real-time scheduling by simulation: rate-monotonic versus earliest-deadline-first. Runs anywhere. */
#include <stdio.h>

#define TASKS 2
#define HORIZON 35        /* the hyperperiod: the least common multiple of the periods 5 and 7 */
#define MAXJOBS 64

typedef struct { int task, release, deadline, remaining, missed; } Job;
static const int C[TASKS] = { 2, 4 };      /* worst-case execution time of each task */
static const int T[TASKS] = { 5, 7 };      /* period of each task; the deadline is the next release */

/* The n-th root of 2, found by bisection so that no math library is needed. */
static double root_of_two(int n) {
    double lo = 1.0, hi = 2.0;
    for (int i = 0; i < 60; i++) {
        double mid = (lo + hi) / 2, p = 1.0;
        for (int k = 0; k < n; k++) p *= mid;
        if (p < 2.0) lo = mid; else hi = mid;
    }
    return lo;
}

/* Run every tick of the horizon; return how many jobs missed their deadline and describe the first one. */
static int run(int edf, int *first_task, int *first_release, int *first_deadline) {
    Job jobs[MAXJOBS];
    int n = 0, misses = 0;
    for (int t = 0; t < HORIZON; t++) {
        for (int i = 0; i < TASKS; i++)
            if (t % T[i] == 0) { Job j = { i, t, t + T[i], C[i], 0 }; jobs[n++] = j; }    /* a new job is released every period */
        int pick = -1;
        for (int k = 0; k < n; k++) {
            if (jobs[k].remaining <= 0) continue;
            if (pick < 0) { pick = k; continue; }
            int better;
            if (edf)        /* (2) EDF: the job whose deadline is nearest runs */
                better = jobs[k].deadline < jobs[pick].deadline
                      || (jobs[k].deadline == jobs[pick].deadline && (jobs[k].task < jobs[pick].task || (jobs[k].task == jobs[pick].task && jobs[k].release < jobs[pick].release)));
            else            /* (1) rate-monotonic: the task with the shorter period always wins, a fixed priority */
                better = T[jobs[k].task] < T[jobs[pick].task]
                      || (T[jobs[k].task] == T[jobs[pick].task] && (jobs[k].task < jobs[pick].task || (jobs[k].task == jobs[pick].task && jobs[k].release < jobs[pick].release)));
            if (better) pick = k;
        }
        if (pick >= 0) jobs[pick].remaining--;              /* (3) one tick per decision, so a new arrival can preempt */
        for (int k = 0; k < n; k++)
            if (!jobs[k].missed && jobs[k].remaining > 0 && jobs[k].deadline == t + 1) {
                jobs[k].missed = 1;
                if (misses++ == 0) { *first_task = jobs[k].task; *first_release = jobs[k].release; *first_deadline = jobs[k].deadline; }
            }
    }
    return misses;
}

int main(void) {
    double u = 0;
    for (int i = 0; i < TASKS; i++) u += (double)C[i] / T[i];
    double bound = TASKS * (root_of_two(TASKS) - 1.0);        /* (4) Liu and Layland: below this utilization rate-monotonic is guaranteed to work */
    printf("utilization = %.3f (rate-monotonic is guaranteed below %.3f, EDF up to 1.000)\n", u, bound);
    int task = 0, release = 0, deadline = 0;
    if (run(0, &task, &release, &deadline)) printf("rate-monotonic: first missed deadline: T%d job released at %d (deadline %d)\n", task + 1, release, deadline);
    else printf("rate-monotonic: no deadline missed in %d ticks\n", HORIZON);
    if (run(1, &task, &release, &deadline)) printf("earliest-deadline-first: first missed deadline: T%d job released at %d (deadline %d)\n", task + 1, release, deadline);
    else printf("earliest-deadline-first: no deadline missed in %d ticks\n", HORIZON);
    return 0;
}

The Python version is the shorter one, because min(..., key=...) expresses “pick the job with the smallest (period, task, release)” in one line. For a simulation like this one that is a good fit. For an actual real-time system Python would be a poor choice: garbage collection and the interpreter make execution times hard to bound, and bounded timing is the whole point.

"""Real-time scheduling by simulation: rate-monotonic versus earliest-deadline-first."""
C = [2, 4]                      # worst-case execution time of each task
T = [5, 7]                      # period of each task; the deadline is the next release
HORIZON = 35                    # the hyperperiod: the least common multiple of the periods 5 and 7


def run(edf):
    """Run every tick of the horizon; return the first job that missed its deadline, or None."""
    jobs, first = [], None
    for t in range(HORIZON):
        for i in range(len(T)):
            if t % T[i] == 0:                                        # a new job is released every period
                jobs.append({"task": i, "release": t, "deadline": t + T[i], "remaining": C[i], "missed": False})
        ready = [j for j in jobs if j["remaining"] > 0]
        if ready:
            if edf:                                                  # (2) EDF: the job whose deadline is nearest runs
                pick = min(ready, key=lambda j: (j["deadline"], j["task"], j["release"]))
            else:                                                    # (1) rate-monotonic: the task with the shorter period always wins, a fixed priority
                pick = min(ready, key=lambda j: (T[j["task"]], j["task"], j["release"]))
            pick["remaining"] -= 1                                   # (3) one tick per decision, so a new arrival can preempt
        for j in jobs:
            if not j["missed"] and j["remaining"] > 0 and j["deadline"] == t + 1:
                j["missed"] = True
                if first is None:
                    first = j
    return first


utilization = sum(c / t for c, t in zip(C, T))
bound = len(T) * (2 ** (1 / len(T)) - 1)                            # (4) Liu and Layland: below this utilization rate-monotonic is guaranteed to work
print(f"utilization = {utilization:.3f} (rate-monotonic is guaranteed below {bound:.3f}, EDF up to 1.000)")
for name, edf in (("rate-monotonic", False), ("earliest-deadline-first", True)):
    miss = run(edf)
    if miss:
        print(f"{name}: first missed deadline: T{miss['task'] + 1} job released at {miss['release']} (deadline {miss['deadline']})")
    else:
        print(f"{name}: no deadline missed in {HORIZON} ticks")

Deadlines add a sharp edge to the synchronization problems of Module 6. If a low-priority task holds a lock that a high-priority task needs, and a medium-priority task then preempts the lock holder, the high-priority task is delayed by a task that is less important than it. This is priority inversion, and real-time systems fix it with priority inheritance: the lock holder temporarily runs at the waiter’s priority.

Many cores

With several CPUs the question changes from “which job next?” to “which job where?”. The usual design gives each core its own run queue, because one shared queue would need a lock that every core fights over. But separate queues can become unbalanced: one core has a backlog while another idles.

Load balancing moves tasks between queues. In work stealing, an idle core takes a waiting task from a busy core’s queue. The catch is processor affinity: a task that has been running on one core has its data in that core’s cache. Move it and it starts cold, running slowly while the new cache fills. A balancer therefore weighs the benefit of using an idle core against the cost of the move.

Try it: keep “all queued on core 0” and compare no balancing with work stealing. Then change the workload to one big task and many small ones: even with perfect balancing nothing can finish before the big task does, which is what the “best possible” figure shows. Finally raise the cost of a move and compare stealing with dealing tasks out evenly.

Try it: the knobs on a real system

Why C is the clearer version here: nice, getpriority and sched_setaffinity are the actual calls, and a CPU set is a small bit array manipulated with the CPU_SET family of macros. This is exactly what tools such as taskset and nice do on your behalf. Linux only (sched_setaffinity is a Linux call).

/* Two knobs the Linux scheduler gives every process: niceness (a priority hint) and CPU affinity. Linux only. */
#define _GNU_SOURCE
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <sys/resource.h>
#include <unistd.h>

int main(void) {
    int before = getpriority(PRIO_PROCESS, 0);
    errno = 0;
    int r = nice(5);                                        /* (1) a higher niceness is a lower priority: the process is being "nice" to others */
    if (r == -1 && errno != 0) return 1;
    int after = getpriority(PRIO_PROCESS, 0);
    int expected = before + 5 > 19 ? 19 : before + 5;       /* niceness is capped at 19 */
    printf("nice(5) raised the niceness by 5 (capped at 19): %s\n", after == expected ? "True" : "False");

    cpu_set_t allowed;
    CPU_ZERO(&allowed);
    if (sched_getaffinity(0, sizeof allowed, &allowed) != 0) return 1;          /* (2) the set of CPUs this process is allowed to run on */
    printf("this process may run on at least one CPU: %s\n", CPU_COUNT(&allowed) >= 1 ? "True" : "False");
    int first = 0;
    while (!CPU_ISSET(first, &allowed)) first++;

    cpu_set_t only;
    CPU_ZERO(&only);
    CPU_SET(first, &only);
    if (sched_setaffinity(0, sizeof only, &only) != 0) return 1;                /* (3) pin the process: the scheduler may now use only that CPU, so its cache stays warm */
    cpu_set_t now;
    CPU_ZERO(&now);
    if (sched_getaffinity(0, sizeof now, &now) != 0) return 1;
    printf("after pinning, the allowed set is exactly that one CPU: %s\n", CPU_COUNT(&now) == 1 && CPU_ISSET(first, &now) ? "True" : "False");
    return 0;                                               /* (4) the OS balances load by moving tasks between CPUs; affinity forbids it from moving this one */
}

Python exposes the same calls in the os module (os.nice, os.sched_getaffinity, os.sched_setaffinity) and uses an ordinary set of integers instead of a bit array, so it is no more contrived than the C version and a good deal tidier. As in C, they exist only on Linux.

"""Two knobs the Linux scheduler gives every process: niceness (a priority hint) and CPU affinity. Linux only."""
import os

before = os.getpriority(os.PRIO_PROCESS, 0)
os.nice(5)                                                           # (1) a higher niceness is a lower priority: the process is being "nice" to others
after = os.getpriority(os.PRIO_PROCESS, 0)
print(f"nice(5) raised the niceness by 5 (capped at 19): {after == min(19, before + 5)}")

allowed = os.sched_getaffinity(0)                                    # (2) the set of CPUs this process is allowed to run on
print(f"this process may run on at least one CPU: {len(allowed) >= 1}")
first = min(allowed)

os.sched_setaffinity(0, {first})                                     # (3) pin the process: the scheduler may now use only that CPU, so its cache stays warm
print(f"after pinning, the allowed set is exactly that one CPU: {os.sched_getaffinity(0) == {first}}")
# (4) the OS balances load by moving tasks between CPUs; affinity forbids it from moving this one

What Linux actually does

PolicyForHow it chooses
SCHED_OTHER (the default)Ordinary programsFair sharing: the task that has had the least CPU time relative to its weight runs next (the CFS and EEVDF schedulers). Niceness changes the weight. Works like a feedback queue in spirit, without explicit levels.
SCHED_FIFO, SCHED_RRReal-time tasksFixed priorities 1–99, above all ordinary tasks. FIFO runs until it blocks; RR adds time slices among equals. This is rate-monotonic-style scheduling, with the priorities assigned by the programmer.
SCHED_DEADLINETasks with explicit deadlinesEarliest deadline first, with an admission test: the kernel refuses a new task if the total utilization would go above what it can guarantee.
Per-CPU run queues, load balancingMulticoreEach core has its own queue. Idle cores pull work, and a periodic balancer evens out loads, preferring moves within a cache domain or NUMA node.
cgroup cpu.weight and cpu.maxContainersThe shares and caps from Module 14, applied to groups of tasks.
AdvancedGoing deeper: limits of the models
  • Where the 69% comes from. The Liu and Layland bound n(21/n − 1) is the worst case over all possible task sets. As n grows it tends to ln 2 ≈ 0.693. Many task sets with “awkward” periods fail below it, but most real sets (and every harmonic set) can go much higher, which is why exact response-time analysis, as in the table above, is used in practice.
  • Response-time analysis. For fixed priorities, a task’s worst response time R is its own C plus the interference from higher-priority tasks that release during R: R = C + Σ ⌈R/Tj⌉ Cj. Solving it by repeated substitution gives an exact schedulability test for rate-monotonic scheduling.
  • EDF’s weakness. EDF is optimal but fragile under overload: when it cannot meet all deadlines it can miss many, because it keeps preferring jobs that are about to be late. Fixed-priority schedulers fail more gracefully, since the low-priority tasks miss and the high-priority ones are untouched. Many safety-critical systems accept lower utilization for that predictability.
  • Multiprocessor real time. On several CPUs, the optimal-on-one-CPU result no longer holds. Global EDF can miss deadlines even at low utilization (Dhall’s effect), so systems often partition tasks onto cores and run rate-monotonic or EDF on each.
  • Graham’s bound. Any scheduler that never leaves a core idle while work is waiting finishes within (2 − 1/m) times the best possible time on m cores. The simulator’s “best possible” figure is the lower bound used in that argument.
  • NUMA and caches. Large machines have memory that is faster for some cores than others (NUMA). A balancer prefers to move tasks within a cache or memory domain first, and may migrate a task’s memory to follow it. Hyper-threading adds another level: two hardware threads on one core share its caches.
  • Big.LITTLE and energy. Phones mix fast and slow cores. An energy-aware scheduler puts light tasks on slow cores and bursts on fast ones, and the scheduler’s “load” signal includes how much each task actually needs, not only how long it ran.
  • Lottery and stride scheduling. A different route to proportional sharing: give each job tickets, draw one at random each slice (lottery), or advance a per-job counter by an amount inversely proportional to its tickets and always run the smallest (stride). Both are simple, and the second is deterministic.
