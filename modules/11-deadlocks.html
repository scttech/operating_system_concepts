Module 7

Deadlocks

A deadlock is a set of processes that are each waiting for a resource held by another in the set, so none of them will ever proceed.

Four necessary conditions (Coffman)

All four must hold at the same time for deadlock to occur. Break any one and deadlock is impossible.

ConditionMeaningHow to break it
Mutual exclusionA resource can be used by only one process at a timeMake resources sharable (read-only files, lock-free structures). Not always possible.
Hold and waitA process holds some resources while waiting for othersRequest everything at once, or release before requesting more
No preemptionResources can only be released voluntarilyAllow the OS to take resources back (works for CPU/memory, not for printers or locks)
Circular waitA cycle P1→P2→…→P1 of waitingImpose a global ordering on resources and always acquire in that order

A resource-allocation graph shows these relationships: an edge from a process to a resource means “requests”; from a resource to a process means “held by”. With one instance of each resource, a cycle means deadlock. With multiple instances, a cycle is necessary but not sufficient.

Dining philosophers

Five philosophers sit around a table with one fork between each pair. A philosopher needs both adjacent forks to eat. This small puzzle contains all four deadlock conditions. Run the naive strategy a few times with different seeds. If every philosopher grabs their left fork at the same moment, nobody can ever eat. Then compare the fixes.

  • Resource ordering removes circular wait: one philosopher picks up forks in the opposite order from the others.
  • Limiting the table to N−1 philosophers guarantees at least one can get both forks.
  • Asymmetric pickup order (odd vs. even) also breaks the cycle.

Handling deadlock: four strategies

StrategyIdeaCost
PreventionDesign so that one of the four conditions can never holdMay reduce resource utilization or concurrency
AvoidanceGrant a request only if the system stays in a safe stateNeeds advance knowledge of maximum demands
Detection & recoveryLet it happen, find the cycle, kill or roll back a victimDetection overhead; lost work
Ignore it (“ostrich”)Assume it's rare; let users rebootUsed by many general-purpose OSes

Banker's algorithm

The Banker's algorithm keeps matrices Allocation, Max and Available, and derives Need = Max − Allocation. A state is safe if some ordering lets every process obtain its Need, finish, and release its resources. To check a request, pretend to grant it and test the safety of the resulting state.

Try it: in the safe preset, ask P4 for (3, 3, 0). There are enough available resources, but granting it leaves no process able to finish, so the Banker refuses. Then switch to the unsafe preset to see the safety search fail.

Safe ⇒ no deadlock. Unsafe does not mean deadlock has happened, just that it can no longer be ruled out.

AdvancedGoing deeper: deadlock in the real world
  • Lock ordering in practice. Large programs avoid deadlock by assigning every lock a rank and always acquiring in increasing order. The Linux kernel’s lockdep checker watches every lock acquisition at run time and warns about an ordering cycle even if the deadlock never actually happened.
  • Livelock and starvation. In a livelock the threads are not blocked but keep reacting to one another (two people stepping aside in a corridor), so no progress is made. Starvation is a thread that never gets a turn even though the system is moving. Neither is a deadlock, and neither is fixed by the same remedies.
  • Distributed and database deadlock. Databases detect a deadlock by finding a cycle in the wait-for graph, choose a victim transaction, roll it back and let the application retry. Two-phase locking makes deadlock possible, and timeouts are the fallback when no coordinator exists.
  • Why operating systems mostly ignore it. Prevention restricts programs and avoidance needs advance knowledge of every maximum claim. Most general-purpose systems take the ostrich approach for application resources and rely on programmers to order locks, because deadlocks are rare and the cost of the alternatives is paid constantly.
  • Priority inversion looks like deadlock. A task blocked behind a lock holder that cannot run appears hung. It is solved by priority inheritance rather than by any of the four strategies on this page.
