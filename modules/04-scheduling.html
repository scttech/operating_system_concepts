CPU Scheduling

With more runnable processes than CPU cores, the scheduler decides who runs, when and for how long. Different goals lead to different algorithms.

A process alternates between computing and waiting for I/O. One continuous run on the CPU is a CPU burst, and a process that mostly waits for devices is I/O-bound. The scheduler chooses the next process and the dispatcher hands it the CPU (performing the context switch). Preemption means the OS can take the CPU away from a running process before its burst is over.

Things to try

  1. On the Textbook preset, switch FCFS → SJF. Average waiting time drops from 6.67 to 4.00. SJF is provably optimal for average waiting time when bursts are known.
  2. On Round Robin example, slide the quantum from 1 to 12. What happens to context switches? To response time? Where does RR start to look like FCFS?
  3. Add a long process arriving at time 0 and several short ones arriving at time 1. Which algorithms suffer the most?
  4. On Staggered arrivals, compare SJF with SRTF. When does preemption help?

Beyond the textbook

  • Multilevel feedback queues (MLFQ) approximate SJF without knowing burst lengths: new jobs start at high priority and sink if they use their whole quantum.
  • Linux uses a fair scheduler (CFS, and more recently EEVDF) that tracks how much CPU time each task has received and picks the one furthest behind.
  • Real-time systems use algorithms such as rate-monotonic or earliest-deadline-first, where meeting deadlines matters more than average speed.
  • Multicore schedulers add load balancing and processor affinity, because migrating a task throws away its warm caches.
