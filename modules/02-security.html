Security & Access Control

Protection is the mechanism that controls who can do what to which resource. Security is the broader goal of defending against threats, including attackers that exploit weak protection.

Goals and principles

  • Confidentiality, integrity, availability (the CIA triad): keep secrets secret, keep data correct, keep services usable.
  • Authentication answers “who are you?” (passwords, keys, biometrics, MFA). Authorization answers “what may you do?” (permissions, ACLs).
  • Least privilege: give every user and program only the rights it needs, for only as long as it needs them.
  • Defense in depth: several independent layers, so one failure does not mean compromise.
  • Separation of policy and mechanism: the kernel provides the checking mechanism; administrators set the policy.

Unix file permissions

Every file has an owner, a group, and three sets of read/write/execute bits: for the owner, the group and others. Each set is written as one octal digit (r=4, w=2, x=1).

Special bits: setuid (run with the file owner's privileges), setgid, and the sticky bit (in a shared directory like /tmp, only a file's owner may delete it).

$ ls -l report.txt
-rw-r----- 1 alice staff 2048 Nov 3 09:12 report.txt
$ chmod 640 report.txt      # rw-r-----
$ chmod g+w,o-r report.txt  # symbolic form
$ umask 022                 # new files default to 644, directories to 755

Try it: umask and chmod

Why C is the clearer version here: open, umask, chmod and stat are the real system calls, and the mode is an integer whose bits you can see. The octal constants (0666, 022) are the notation chmod uses too.

/* File permissions: the umask, chmod and the permission bits. Unix only. */
#define _POSIX_C_SOURCE 200809L
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/stat.h>
#include <unistd.h>

static void show(const char *what, const char *path) {
    struct stat st;
    if (stat(path, &st) != 0) { perror("stat"); exit(1); }
    char sym[10];
    for (int i = 0; i < 9; i++) sym[i] = (st.st_mode & (0400u >> i)) ? "rwxrwxrwx"[i] : '-';   /* (1) nine bits: owner, group, others */
    sym[9] = '\0';
    printf("%-36s %03o (%s)\n", what, (unsigned)(st.st_mode & 0777u), sym);
}

int main(void) {
    char dir[] = "/tmp/osc_mode_XXXXXX", path[64];
    if (mkdtemp(dir) == NULL) return 1;
    snprintf(path, sizeof path, "%s/report.txt", dir);

    umask(022);                                      /* (2) the umask REMOVES permission bits from newly created files */
    int fd = open(path, O_CREAT | O_WRONLY, 0666);   /* (3) ask for 666 (rw-rw-rw-)... */
    if (fd < 0) return 1;
    close(fd);
    show("created with mode 666, umask 022:", path); /* ...and the umask turns it into 644 */

    if (chmod(path, 0640) != 0) return 1;            /* (4) chmod sets the permissions explicitly: the umask does not apply */
    show("after chmod 640:", path);
    if (chmod(path, 0600) != 0) return 1;
    show("after chmod 600:", path);

    struct stat st;
    if (stat(path, &st) != 0) return 1;
    printf("others can read the file: %s\n", (st.st_mode & 004) ? "yes" : "no");

    remove(path);
    rmdir(dir);
    return 0;
}

Python’s os module mirrors the C calls almost one-to-one, so nothing here is contrived. The built-in open() has no mode argument, which is why the example uses os.open. On Windows, chmod can only toggle the read-only flag, so this example needs Linux or macOS.

"""File permissions: the umask, chmod and the permission bits. Unix only."""
import os
import shutil
import tempfile


def show(what, path):
    mode = os.stat(path).st_mode
    sym = "".join(c if mode & (0o400 >> i) else "-" for i, c in enumerate("rwxrwxrwx"))   # (1) nine bits: owner, group, others
    print(f"{what:<36} {mode & 0o777:03o} ({sym})")


folder = tempfile.mkdtemp(prefix="osc_mode_")
path = os.path.join(folder, "report.txt")

os.umask(0o022)                                      # (2) the umask REMOVES permission bits from newly created files
fd = os.open(path, os.O_CREAT | os.O_WRONLY, 0o666)  # (3) ask for 666 (rw-rw-rw-)...
os.close(fd)
show("created with mode 666, umask 022:", path)      # ...and the umask turns it into 644

os.chmod(path, 0o640)                                # (4) chmod sets the permissions explicitly: the umask does not apply
show("after chmod 640:", path)
os.chmod(path, 0o600)
show("after chmod 600:", path)

print("others can read the file:", "yes" if os.stat(path).st_mode & 0o004 else "no")
shutil.rmtree(folder)

Access-control matrix

Conceptually, protection is a matrix: rows are subjects (users, processes), columns are objects (files, devices), and each cell lists the permitted operations. Real systems never store the full sparse matrix. They store it by column (ACLs) or by row (capabilities).

Typical attacks and defenses

ThreatWhat happensMitigation
Buffer overflowInput larger than a buffer overwrites adjacent memory (e.g., a return address)Bounds checking, stack canaries, NX/DEP, ASLR, memory-safe languages
Privilege escalationA flaw in a privileged (setuid/root) program gives an attacker more rightsLeast privilege, drop privileges early, patching, sandboxing
MalwareViruses, worms, trojans, ransomwarePermissions, code signing, updates, backups, user training
Password attacksGuessing, credential stuffing, stolen hashesSalted slow hashing, rate limiting, MFA
Denial of serviceExhaust CPU, memory, disk or networkQuotas, rate limits, cgroups, redundancy

Trade-off to discuss: stronger isolation (containers, sandboxes, mandatory access control like SELinux) costs convenience and sometimes performance. Security decisions are always about balancing risk, usability and cost.

AdvancedGoing deeper: beyond owner, group and others
  • Access-control lists. Nine permission bits cannot say “Alice may read, Bob may write”. POSIX ACLs (getfacl, setfacl) and Windows ACLs attach a list of (principal, rights) entries to a file, which is the access-control matrix stored by column.
  • Capabilities. Linux splits root’s power into about 40 capabilities such as CAP_NET_BIND_SERVICE, so a web server can bind port 80 without being able to read every file. This is least privilege applied to the kernel itself.
  • Mandatory access control. With discretionary control the owner decides. SELinux, AppArmor and Android’s SELinux policy let the administrator define rules that even the owner (and root) cannot override. This is how a compromised app is confined.
  • Setuid and its risks. A setuid program runs with its owner’s privileges, so passwd can edit the password file. Any bug in such a program becomes a privilege escalation, which is why the set of setuid binaries is kept small and audited.
  • Address-space randomization and non-executable memory. ASLR places the stack, heap and libraries at random addresses, and NX/DEP forbids running data pages as code. Neither stops a bug, but together they make buffer-overflow exploits much harder to write.
