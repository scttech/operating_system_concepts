Beyond Windows, macOS and Linux

Every operating system is a set of trade-offs shaped by what it is for. A phone, a car's dashboard, a bank's transaction engine and a journalist's laptop each push the same ideas (scheduling, memory, files, protection) in very different directions.

Why systems differ

The concepts from Modules 1–11 apply everywhere, but the priorities change. Compare what each kind of system optimizes for:

Kind of systemMain goalWhat that does to the design
Desktop / server (Windows, macOS, Linux)Run many different programs wellGeneral-purpose scheduling, large virtual memory, broad driver support

Where did they come from?

Many systems are relatives. Android, ChromeOS and Raspberry Pi OS all share the Linux kernel; macOS and iOS share Apple's Darwin core. IBM's mainframe world has two parallel families (OS/360 and DOS/360), and its midrange line grew from a different idea altogether (System/38).

Mobile: Android and iOS

  • Apps do not own the machine. The OS starts, pauses and kills apps to protect battery and memory. A mobile app must save its state whenever it is sent to the background, because it may never be resumed.
  • Strong sandboxes. Each app is isolated from the others and gets only the permissions the user grants (camera, location, contacts).
  • Same ideas, different kernels. Android uses a modified kernel from Linux; iOS uses Apple's XNU. Both rely on the hardware's user/kernel separation from Module 1.
  • Memory pressure is handled by terminating apps rather than paging to a slow flash drive.

Security-focused: Qubes OS

Most operating systems try to make one big system trustworthy. Qubes does the opposite and assumes something will be hacked, then limits the blast radius. A hypervisor runs separate virtual machines (“qubes”) for work, personal browsing, banking and untrusted downloads. A bug in a browser in the “untrusted” qube cannot read files in the “work” qube. This is least privilege applied to whole operating systems. The price is higher hardware needs and a more complex workflow, which is the central security versus usability trade-off.

Embedded and real-time

A real-time operating system guarantees that important work finishes on time, not that it finishes fast on average. That pushes the design toward predictable fixed-priority scheduling and away from features such as virtual memory, whose page faults make timing unpredictable. At the small end (FreeRTOS), the “OS” is a library compiled into the firmware on a microcontroller. At the larger end (QNX), a microkernel runs drivers as separate processes so that a driver failure in a car does not crash the whole system.

Raspberry Pi OS sits between worlds: a full Linux system on a tiny, inexpensive board whose GPIO pins let your code blink LEDs or read sensors. It is excellent for learning but, being standard Linux, it is not a hard real-time system.

Mainframe and midrange systems

Mainframes are not museum pieces. They process a very large share of the world's banking and airline transactions, and their operating systems reflect that job. A few ideas that look different from what you see on a PC:

IdeaPC-style OSMainframe-style OS (z/OS, z/VSE)
Typical workInteractive programsHuge batch runs (described in JCL) plus thousands of simultaneous online transactions
I/OCPU drives devices via drivers and DMAA dedicated channel subsystem handles I/O so the CPUs stay busy computing
Scheduling goalFairness and responsivenessMeet business goals (“payments must complete in 0.2 s”) through the Workload Manager
Sharing the hardwareProcesses, maybe VMsLogical partitions (LPARs) in hardware, each running its own OS, plus z/VM for more virtual machines
FilesHierarchical directoriesDatasets located by catalogs (and a UNIX file system alongside)
Text encodingASCII / UnicodeEBCDIC traditionally, so data is converted when exchanged with other systems
ReliabilityReboot occasionallyDesigned for continuous operation and clustering (Parallel Sysplex)
CompatibilityOften broken by major upgradesPrograms from the 1960s still run, a core selling point
  • z/OS descends from OS/360 and MVS. It is the large-scale flagship.
  • z/VSE descends from the separate DOS/360 line: smaller, simpler and cheaper to operate, often used by smaller organizations.
  • IBM i (formerly AS/400, iSeries, System i) is a midrange system with a database built into the OS, an object-based design, and single-level storage: memory and disk form one address space, so applications never manage paging or files the way they do on a PC.
  • z/VM is IBM's mainframe hypervisor: it runs many virtual machines, often Linux, alongside z/OS and z/VSE guests. z/TPF is a very lean system for enormous volumes of short transactions, such as airline bookings and payments.

Connect it back: single-level storage is virtual memory taken to its logical extreme, and the channel subsystem is a more powerful version of the DMA idea.

Questions to ask about any new OS

  1. What is it for, and what does it sacrifice to do that well?
  2. Where is the line between kernel and user space? Is it a monolithic kernel, a microkernel, or a hypervisor?
  3. How does it schedule work: fairness, priorities, deadlines, or business goals?
  4. Does it give each program its own virtual memory? What happens when memory runs short: swap, kill, or nothing?
  5. What is a “file” here, and how are names organized?
  6. What is the unit of isolation and trust: user, app, container, VM, partition?
  7. Who controls updates and software installation?
AdvancedGoing deeper: design ideas worth knowing
  • Unikernels. Link the application with only the OS libraries it needs and run the result directly on a hypervisor. There is no shell, no other process and almost nothing to attack, and the image can boot in milliseconds.
  • Capability-based systems. seL4 and Fuchsia’s Zircon replace ambient authority (“run as user X”) with unforgeable handles: a program can use only what it was explicitly given. This is the access-control matrix stored by row, and seL4’s kernel is formally verified.
  • Containers are not virtual machines. A container is ordinary processes using kernel namespaces (what they can see) and cgroups (what they can use), so all share one kernel. A VM runs its own kernel on virtual hardware, which isolates more strongly and costs more.
  • Real-time operating systems. VxWorks, FreeRTOS and Zephyr guarantee a bounded response time rather than a fast average. Their schedulers are simple priority-based designs so that worst-case latency can be proven.
  • Microkernels in production. QNX runs cars and medical devices, and Apple’s Secure Enclave runs an L4-family kernel. A fault in one driver restarts that driver, not the machine. Minix 3 even restarts failed drivers automatically.
