Storage Reliability

Everything an operating system remembers lives on storage that eventually fails, and fails in several different ways. Module 10 covered how fast storage is and Module 11 how it is organized. This module covers what keeps data safe: redundancy across disks, the odd ways flash wears out, and updates that survive a crash.

How storage fails

Different failures need different defenses, and no single tool covers them all:

RAID

RAID combines several disks so they behave like one. The levels differ in how they spread data and what redundancy they add. Two ideas are involved: striping (spreading data across disks so reads and writes run in parallel) and redundancy, either mirroring (complete copies) or parity (computed information from which a lost piece can be rebuilt).

LevelHow it worksCapacity (n disks)Failures survived
RAID 0Striping onlyn0: any failure loses everything
RAID 1Every disk is a full copy1n − 1
RAID 5Striping with one parity block per stripe, rotated across the disksn − 11
RAID 6Striping with two different parity blocks per stripen − 22
RAID 10Mirrored pairs, striped togethern / 21 for sure; more if each lands in a different pair

Try it: with RAID 5 on five disks, fail one disk (still safe, but now degraded), then a second (data lost). Switch to RAID 10 and fail one disk from each pair: it survives. Fail both disks of one pair: it does not. RAID 6 needs three failures to lose data.

How parity works

The parity block is the XOR of the data blocks. XOR has a convenient property: anything XOR-ed with itself is zero. So XOR-ing all the blocks, including the parity block, gives zero, and a missing block is therefore the XOR of everything that survived.

One cost deserves attention. A small write to a RAID 5 array must also update parity. Rather than read every other disk, the controller reads the old data and old parity, computes new parity = old parity XOR old data XOR new data, and writes both: four disk operations for one logical write. This is the “small-write penalty”, and it is why databases often prefer RAID 10.

Try it: rebuild a disk from parity

Why C is the clearer version here: parity is a loop of XOR over bytes, and C shows that it is nothing more: no special hardware, one operator. Comment (3) is the small-write shortcut, and comment (4) shows that a second failure leaves one equation with two unknowns.

/* XOR parity, the idea behind RAID 5: rebuild a lost disk from the others. Runs anywhere. */
#include <stdio.h>
#include <string.h>

#define DISKS 4
#define BLOCK 8

static void xor_into(unsigned char *dst, const unsigned char *src) { for (int i = 0; i < BLOCK; i++) dst[i] ^= src[i]; }

int main(void) {
    unsigned char data[DISKS][BLOCK + 1] = { "alpha-01", "bravo-02", "charlie3", "delta-04" };
    unsigned char parity[BLOCK] = { 0 };
    for (int d = 0; d < DISKS; d++) xor_into(parity, data[d]);          /* (1) the parity block is the XOR of all the data blocks */
    printf("data disks:  %s %s %s %s\n", data[0], data[1], data[2], data[3]);
    printf("parity disk: ");
    for (int i = 0; i < BLOCK; i++) printf("%02x", parity[i]);
    printf("\n");

    unsigned char rebuilt[BLOCK];
    memcpy(rebuilt, parity, BLOCK);                                    /* (2) disk 2 fails: XOR the parity with every disk that survived... */
    for (int d = 0; d < DISKS; d++) if (d != 2) xor_into(rebuilt, data[d]);
    printf("disk 2 fails; rebuilt from parity and the other disks: %.8s (matches original: %s)\n", (char *)rebuilt, memcmp(rebuilt, data[2], BLOCK) == 0 ? "True" : "False");

    const unsigned char fresh[BLOCK] = { 'B', 'R', 'A', 'V', 'O', '-', '9', '9' };
    unsigned char updated[BLOCK], recomputed[BLOCK] = { 0 };
    memcpy(updated, parity, BLOCK);                                    /* (3) a small write: new parity = old parity XOR old data XOR new data */
    xor_into(updated, data[1]); xor_into(updated, fresh);
    for (int d = 0; d < DISKS; d++) xor_into(recomputed, d == 1 ? fresh : data[d]);
    printf("small write to disk 1: new parity from old parity, old data and new data matches a full recompute: %s\n", memcmp(updated, recomputed, BLOCK) == 0 ? "True" : "False");
    printf("that small write costs 2 reads + 2 writes = 4 disk operations\n");

    unsigned char wrong[BLOCK];
    memcpy(wrong, parity, BLOCK);                                      /* (4) with a second disk lost there are two unknowns and one equation: the result is wrong */
    for (int d = 0; d < DISKS; d++) if (d != 2 && d != 3) xor_into(wrong, data[d]);
    printf("a second failure (disks 2 and 3 both lost) cannot be rebuilt: wrong data produced: %s\n", memcmp(wrong, data[2], BLOCK) != 0 ? "True" : "False");
    return 0;
}

Python needs a few extra lines because bytes objects do not support ^ directly, so a small xor helper combines them column by column with zip and reduce. The idea is identical to the C version, and the output is the same. Real arrays do this in the kernel or in hardware, on whole stripes at a time.

"""XOR parity, the idea behind RAID 5: rebuild a lost disk from the others."""
from functools import reduce

data = [b"alpha-01", b"bravo-02", b"charlie3", b"delta-04"]


def xor(*blocks):
    return bytes(reduce(lambda a, b: a ^ b, column) for column in zip(*blocks))


parity = xor(*data)                                                    # (1) the parity block is the XOR of all the data blocks
print("data disks:  " + " ".join(d.decode() for d in data))
print("parity disk: " + parity.hex())

rebuilt = xor(parity, *[d for i, d in enumerate(data) if i != 2])      # (2) disk 2 fails: XOR the parity with every disk that survived...
print(f"disk 2 fails; rebuilt from parity and the other disks: {rebuilt.decode()} (matches original: {rebuilt == data[2]})")

fresh = b"BRAVO-99"
updated = xor(parity, data[1], fresh)                                  # (3) a small write: new parity = old parity XOR old data XOR new data
recomputed = xor(data[0], fresh, data[2], data[3])
print(f"small write to disk 1: new parity from old parity, old data and new data matches a full recompute: {updated == recomputed}")
print("that small write costs 2 reads + 2 writes = 4 disk operations")

wrong = xor(parity, *[d for i, d in enumerate(data) if i not in (2, 3)])   # (4) with a second disk lost there are two unknowns and one equation: the result is wrong
print(f"a second failure (disks 2 and 3 both lost) cannot be rebuilt: wrong data produced: {wrong != data[2]}")

The danger of the rebuild

After a failure, the array is running with no redundancy until the replacement disk is rebuilt, and rebuilding means reading every surviving disk from start to finish. Drives specify an unrecoverable read error rate, perhaps one per 1014 bits. Read tens of terabytes and meeting one is likely. In RAID 5 an error then loses data, because there is no parity left to correct it.

Try it: raise the disk size and watch RAID 5’s risk climb while RAID 6 stays covered. Then switch to the enterprise error rate. This is why big arrays use RAID 6 or mirrors, and why the figure that matters is the rebuild, not the failure.

Flash and wear

An SSD stores bits in flash cells grouped into pages (a few kilobytes) and blocks (hundreds of pages). Two rules shape everything: a page can be written only after its whole block has been erased, and each block survives only a limited number of erases. So a drive cannot overwrite data in place. A firmware layer, the flash translation layer, writes the new version into a fresh page, remembers the new location, and leaves the old page stale.

When free blocks run low, garbage collection picks a block, copies its still-valid pages elsewhere, and erases it. Those copies are extra writes: the write amplification is flash writes divided by the writes the computer asked for. The firmware also practises wear leveling, steering new writes to the least-erased blocks so that none dies early.

Try it: start with random overwrites on a 90%-full drive: the amplification is high. Lower the fill, or raise the hidden spare space, and it falls. Switch to sequential writes and it drops to about 1.0, because whole blocks go stale together and nothing needs copying. The operating system can help with TRIM, which tells the drive which blocks hold deleted data, so that space counts as spare rather than valid.

Surviving a crash

Many updates need several separate writes. Appending to a file changes the free-space bitmap, the inode and the data block (Module 11). The disk can write only one at a time, and the power can fail between any two. Without protection the file system can be left inconsistent: a block marked used but belonging to no file, or a file pointing at a block that was never written, or two files sharing one block.

The old remedy was fsck, a scan of the whole disk at the next boot, slow on large disks and unable to repair everything. The modern remedy is to make the update atomic. In write-ahead logging, the file system first writes what it intends to do into a log (the journal), then writes a single commit record, and only then changes the data in place. After a crash, a transaction with a commit record is replayed; one without is ignored.

Try it: with no journal and the order “bitmap, inode, data”, crash after two steps: the file includes a block with no data. Change the order to data first: the worst case becomes a leaked block, which is harmless. Then switch to a journal and slide through every crash point: it always ends up all-old or all-new, with the commit record as the dividing line.

Try it: a write-ahead log that survives a torn write

Why C is the clearer version here: write, fsync, ftruncate and pread are the actual system calls. Comment (1) is the essential rule: the change is not done until fsync says the bytes are on stable storage. The program then simulates a crash by cutting the file short, and recovery replays only records whose length and checksum are right. Needs Linux or macOS (the example uses POSIX calls).

/* A write-ahead log: make each change durable first, and recover after a crash by replaying only the complete records. Linux or macOS. */
#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

/* A record is: one byte of length, the text "key=value", then a one-byte checksum (the sum of the text, modulo 256). */

static void append(int fd, const char *text) {
    unsigned char buf[64];
    size_t n = strlen(text);
    unsigned sum = 0;
    for (size_t i = 0; i < n; i++) sum += (unsigned char)text[i];
    buf[0] = (unsigned char)n;
    memcpy(buf + 1, text, n);
    buf[n + 1] = (unsigned char)(sum & 255);
    if (write(fd, buf, n + 2) != (ssize_t)(n + 2)) exit(1);
    if (fsync(fd) != 0) exit(1);                         /* (1) the change counts as done only once it is on stable storage */
}

/* Replay the log: apply each complete, correct record in order and stop at the first one that is not. */
static int replay(const char *path, char *out, size_t outsize) {
    FILE *f = fopen(path, "rb");
    if (!f) exit(1);
    int a = 0, b = 0, records = 0, c;
    while ((c = fgetc(f)) != EOF) {
        unsigned char text[64];
        size_t n = (size_t)c;
        if (n == 0 || n >= sizeof text || fread(text, 1, n, f) != n) break;          /* (2) a record that is cut short is a torn write: ignore it */
        int sum = fgetc(f);
        unsigned want = 0;
        for (size_t i = 0; i < n; i++) want += text[i];
        if (sum == EOF || (unsigned)sum != (want & 255)) break;                      /* (3) a record whose checksum is wrong was damaged: stop here */
        if (text[0] == 'A') a = text[2] - '0'; else b = text[2] - '0';
        records++;
    }
    fclose(f);
    snprintf(out, outsize, "A=%d, B=%d (%d record%s)", a, b, records, records == 1 ? "" : "s");
    return records;
}

int main(void) {
    char path[] = "/tmp/osc_wal_XXXXXX", result[64];
    int fd = mkstemp(path);
    if (fd < 0) return 1;
    append(fd, "A=1"); append(fd, "B=2"); append(fd, "A=5");
    printf("wrote 3 records (A=1, B=2, A=5) to the log\n");
    replay(path, result, sizeof result);
    printf("full log replays to: %s\n", result);

    off_t size = lseek(fd, 0, SEEK_END);
    if (ftruncate(fd, size - 3) != 0) return 1;                                      /* (4) simulate a crash in the middle of the last write by cutting it short */
    replay(path, result, sizeof result);
    printf("log cut in the middle of the last record: replays to %s\n", result);

    unsigned char flipped;
    if (pread(fd, &flipped, 1, 6) != 1) return 1;                                    /* flip one bit in the second record's text */
    flipped ^= 1;
    if (pwrite(fd, &flipped, 1, 6) != 1) return 1;
    replay(path, result, sizeof result);
    printf("a flipped bit in the second record is caught by its checksum: replays to %s\n", result);
    close(fd);
    unlink(path);
    return 0;
}

Python’s os module exposes the same calls (os.write, os.fsync, os.ftruncate), so this is no more contrived than the C version, and the record format is identical. Parsing is shorter because slices of a bytes object replace the manual reading. Python’s ordinary open() adds its own buffering, which is why a durable log uses the lower-level calls.

"""A write-ahead log: make each change durable first, and recover after a crash by replaying only the complete records."""
import os
import tempfile

# A record is: one byte of length, the text "key=value", then a one-byte checksum (the sum of the text, modulo 256).


def append(fd, text):
    data = text.encode()
    os.write(fd, bytes([len(data)]) + data + bytes([sum(data) & 255]))
    os.fsync(fd)                                         # (1) the change counts as done only once it is on stable storage


def replay(path):
    """Apply each complete, correct record in order and stop at the first one that is not."""
    with open(path, "rb") as f:
        raw = f.read()
    state, records, i = {"A": 0, "B": 0}, 0, 0
    while i < len(raw):
        n = raw[i]
        if n == 0 or i + n + 2 > len(raw):               # (2) a record that is cut short is a torn write: ignore it
            break
        text = raw[i + 1:i + 1 + n]
        if raw[i + 1 + n] != sum(text) & 255:            # (3) a record whose checksum is wrong was damaged: stop here
            break
        key, value = text.decode().split("=")
        state[key] = int(value)
        records += 1
        i += n + 2
    return f"A={state['A']}, B={state['B']} ({records} record{'' if records == 1 else 's'})"


fd, path = tempfile.mkstemp(prefix="osc_wal_")
for entry in ("A=1", "B=2", "A=5"):
    append(fd, entry)
print("wrote 3 records (A=1, B=2, A=5) to the log")
print(f"full log replays to: {replay(path)}")

os.ftruncate(fd, os.fstat(fd).st_size - 3)               # (4) simulate a crash in the middle of the last write by cutting it short
print(f"log cut in the middle of the last record: replays to {replay(path)}")

os.lseek(fd, 6, os.SEEK_SET)                             # flip one bit in the second record's text
byte = os.read(fd, 1)
os.lseek(fd, 6, os.SEEK_SET)
os.write(fd, bytes([byte[0] ^ 1]))
print(f"a flipped bit in the second record is caught by its checksum: replays to {replay(path)}")
os.close(fd)
os.remove(path)

Databases use exactly this idea (the “write-ahead log”), and so do journaling file systems such as ext4, XFS and NTFS. Copy-on-write file systems (ZFS, Btrfs, APFS) reach the same goal differently: they never overwrite live data, and switch to the new version with one atomic pointer update.

Checksums and backups

Redundancy repairs data only if you know which copy is wrong. Disks usually report a failure, but sometimes they return the wrong data without any error. A checksum stored with each block lets the system notice, and if a mirror or parity exists, repair it from the good copy. Some file systems (ZFS, Btrfs) checksum every block and scrub the whole pool regularly to find damage while a good copy still exists.

Finally, none of this is a backup. RAID, mirrors and journals protect against hardware faults and crashes. A deleted file, a bug that scribbles on data, or ransomware is deleted, scribbled on or encrypted on every disk at once, instantly. A backup is a separate, older, preferably off-site copy. A common rule of thumb is 3-2-1: three copies, on two kinds of media, with one kept elsewhere. And a backup you have never restored is only a hope.

AdvancedGoing deeper: what real systems add
  • The write hole. In RAID 5, a crash between writing the data and writing the parity leaves a stripe whose parity no longer matches. After a disk failure that stripe rebuilds to garbage. Fixes include a battery-backed write cache, a small journal of in-flight stripes, or file systems (ZFS RAID-Z) whose stripes are written atomically.
  • Erasure coding. RAID 6 is a case of a more general idea: split data into k pieces and compute m extra, so that any k of the k + m pieces rebuild everything. Large storage systems spread such pieces across machines and data centers.
  • Failures are correlated. Disks from the same batch, in the same chassis, with the same firmware and the same workload tend to fail together. That makes a second failure during a rebuild more likely than independent odds suggest, and it is one reason to mix batches and to keep spares.
  • Hot spares and degraded mode. A hot spare starts rebuilding automatically. While the array is degraded, reads of the missing disk’s data need extra work: every read becomes XOR of the others, which slows the system just when it is most at risk.
  • Lying drives and write barriers. A drive may acknowledge a write while the data is still in its volatile cache. File systems issue flush commands as barriers so that the journal reaches stable storage before the commit record. Skipping them is a classic cause of corruption after power loss.
  • SSD details. Drives keep a small write buffer and often a capacitor to finish writes after power loss. Cells that store several bits (TLC, QLC) are denser and cheaper but wear faster. Zoned and multi-stream interfaces let the operating system tell the drive which writes belong together, which is the “separate blocks” option in the simulator.
  • Journal modes in practice. Most file systems journal only metadata by default and write data first (the “ordered” mode in the simulator), so the structure is always consistent but the contents of a file after a crash can be old. Full data journaling writes everything twice and is correspondingly slower.
  • Measured failure rates. Large studies of data-center disks found annual failure rates of a few percent, with failures concentrated early in life and in older age, and with only weak links to temperature or to the manufacturer’s quoted “mean time between failures”. Treat such figures as estimates, not guarantees.
