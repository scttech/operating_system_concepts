Module 6

Process Synchronization

When concurrent threads or processes share data, the result can depend on exact timing. Synchronization tools enforce order and exclusive access.

The race condition

A race condition exists when the outcome depends on how operations interleave. Even counter++ is three machine steps (load, add, store), so two threads can both load the same old value and one increment disappears.

Step the threads by hand: run thread 1's LOAD, then thread 2's LOAD, then everything else. Then switch on the mutex and notice that thread 2 is forced to wait.

The critical-section problem

The code that touches shared data is the critical section. A correct solution must provide:

  1. Mutual exclusion: only one thread inside at a time.
  2. Progress: if no one is inside, a thread that wants in is not delayed forever by threads that don't.
  3. Bounded waiting: a limit on how often others can overtake a waiting thread.
do {
    acquire(lock);      // entry section
    /* critical section: touch shared data */
    release(lock);      // exit section
    /* remainder section */
} while (true);

Try it: a spinlock built from test-and-set

Why C is the clearer version here: atomic_flag_test_and_set is the hardware instruction the lesson talks about: it sets the flag and returns the old value in one indivisible step. Spinning on it is a real spinlock. (This example needs C11 for <stdatomic.h>.)

/* build: c11 */
/* A spinlock built from one atomic hardware operation. Build with: gcc -std=c11 -D_POSIX_C_SOURCE=200809L -pthread */
#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>

#define THREADS 4
#define ITERATIONS 2000

static atomic_flag lock_flag = ATOMIC_FLAG_INIT;
static long counter = 0;                       /* an ordinary variable: only the spinlock protects it */

static void spin_lock(void) {
    /* (1) test-and-set sets the flag AND returns its old value in one indivisible step.
           If the old value was already "set", someone else holds the lock, so we spin and try again. */
    while (atomic_flag_test_and_set(&lock_flag)) { }
}
static void spin_unlock(void) { atomic_flag_clear(&lock_flag); }      /* (2) release: clear the flag so another thread can take it */

static void *worker(void *arg) {
    (void)arg;
    for (int i = 0; i < ITERATIONS; i++) {
        spin_lock();
        counter++;                             /* (3) the critical section: only one thread at a time gets here */
        spin_unlock();
    }
    return NULL;
}

int main(void) {
    pthread_t t[THREADS];
    for (int i = 0; i < THREADS; i++) pthread_create(&t[i], NULL, worker, NULL);
    for (int i = 0; i < THREADS; i++) pthread_join(t[i], NULL);        /* (4) wait for all of them, then read the result */
    printf("%d threads x %d increments, protected by a spinlock: counter = %ld (correct: %s)\n",
           THREADS, ITERATIONS, counter, counter == (long)THREADS * ITERATIONS ? "True" : "False");
    return 0;
}

This is more contrived in Python. Pure Python has no atomic test-and-set, so a threading.Lock stands in for the flag, and the loop yields the CPU with time.sleep(0) because a bare busy loop is very slow under the global interpreter lock. Python programs almost never spin; they just call with lock: and let the OS put the waiter to sleep. Read the example for the idea, not as a pattern to copy.

"""A spinlock. Pure Python has no hardware test-and-set, so a threading.Lock stands in for the atomic flag."""
import threading
import time

THREADS = 4
ITERATIONS = 2000

flag = threading.Lock()                        # stands in for the atomic flag (the lock itself is the atomic operation)
counter = 0


def spin_lock():
    # (1) try to take the flag; if someone else holds it, spin and try again (acquire(False) never waits)
    while not flag.acquire(False):
        time.sleep(0)                          # yield the CPU so the holder can run: a plain busy loop is very slow under the GIL


def spin_unlock():
    flag.release()                             # (2) release: clear the flag so another thread can take it


def worker():
    global counter
    for _ in range(ITERATIONS):
        spin_lock()
        counter += 1                           # (3) the critical section: only one thread at a time gets here
        spin_unlock()


threads = [threading.Thread(target=worker) for _ in range(THREADS)]
for t in threads:
    t.start()
for t in threads:
    t.join()                                   # (4) wait for all of them, then read the result
print(f"{THREADS} threads x {ITERATIONS} increments, protected by a spinlock: counter = {counter} (correct: {counter == THREADS * ITERATIONS})")

Bounded buffer (producer–consumer)

Producers add items to a buffer of N slots and consumers remove them. Three semaphores solve it: empty = N (free slots), full = 0 (filled slots) and mutex = 1 (protects the buffer structure).

producer:                     consumer:
  wait(empty)                   wait(full)
  wait(mutex)                   wait(mutex)
  insert item                   remove item
  signal(mutex)                 signal(mutex)
  signal(full)                  signal(empty)

Order matters: if a producer does wait(mutex) before wait(empty) and the buffer is full, it sleeps while holding the mutex, so the consumer can never get in to make room. That is a deadlock. See Module 7.

Other classic problems

  • Readers–writers: many readers may share data, but writers need exclusive access (beware writer starvation).
  • Dining philosophers: see Module 7.
  • Priority inversion: a high-priority task blocked on a lock held by a low-priority task that is preempted by a medium one. Fix with priority inheritance.

AdvancedGoing deeper: lock-free ideas and what hardware really guarantees
  • Compare-and-swap. The instruction at the heart of lock-free code atomically sets a location to a new value only if it still holds the expected old one. A thread retries in a loop until it succeeds, so no thread can block another by sleeping inside a critical section.
  • Memory ordering. Compilers and CPUs reorder reads and writes. On x86 stores are seen in order but a store may be delayed past a later load, and ARM allows far more reordering. Atomic operations carry an ordering (acquire, release, sequentially consistent) that tells both what they may not move.
  • Why Peterson’s algorithm fails on modern hardware. It is correct only if each thread’s writes become visible to the other in program order. Without memory barriers, real CPUs break that assumption, so the textbook proof does not apply to real machines unless the algorithm uses atomics.
  • Futexes. Linux mutexes are fast because the uncontended case is one atomic instruction in user mode. Only when a thread must wait does it call the kernel (futex) to sleep, and the unlocker wakes it. So the system call cost is paid only under contention.
  • The ABA problem. A compare-and-swap can succeed even though the value changed from A to B and back to A in between, which corrupts lock-free stacks that reuse memory. Version counters or hazard pointers address it.
  • Read-copy-update and transactional memory. RCU lets readers proceed with no locks at all while a writer publishes a new copy, which is why the Linux kernel uses it for read-mostly data. Hardware transactional memory tried to make whole critical sections speculative, but it has had limited success.
