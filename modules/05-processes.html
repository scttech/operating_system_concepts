Module 3

Processes

A program is a file on disk. A process is that program in execution, with its own address space, open files and CPU state.

What a process contains

  • Text (code), data (globals), heap (dynamic memory, grows up) and stack (function frames, grows down).
  • CPU state: program counter, registers, stack pointer.
  • Kernel bookkeeping in the process control block (PCB): PID, state, scheduling info, memory maps, open-file table, accounting.

Process states

As a process runs, it moves between states. Only one process per CPU core can be Running; the rest are Ready (waiting in the ready queue for a CPU) or Waiting (blocked for I/O or an event).

Notice: a process whose I/O completes goes to Ready, not Running. The scheduler alone decides who runs next. A process can never go Waiting → Running directly.

Context switching

A context switch saves the running process's registers into its PCB and loads another's. It is pure overhead (no user work happens), and it also disturbs caches and the TLB, so schedulers try not to switch needlessly. See Module 5 for how the cost trades off against responsiveness.

Creating processes: fork, exec, wait

fork() makes a copy of the calling process (using copy-on-write so it's cheap). The copy is the child and the original is its parent. It returns 0 in the child and the child's PID in the parent. exec() replaces the process image with a new program. wait() lets the parent collect the child's exit status.

#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>

int main(void) {
    pid_t pid = fork();
    if (pid < 0)       { perror("fork"); return 1; }
    else if (pid == 0) { printf("child  pid=%d\n", getpid()); }
    else               { wait(NULL); printf("parent pid=%d reaped child %d\n", getpid(), pid); }
    return 0;
}

In Python the same primitives are available as os.fork(), os.execvp() and os.waitpid(), and higher-level as subprocess.

How many processes?

Every call to fork() doubles the number of processes, because both the parent and every existing child continue to execute the next line.

Special cases

  • Zombie: finished, but the parent hasn't called wait() yet, so the PCB lingers.
  • Orphan: the parent exited first. The child is adopted by init/systemd (PID 1), which reaps it.
  • Daemon: background service process with no controlling terminal.

AdvancedGoing deeper: what fork really copies
  • Copy-on-write. fork() does not copy the parent’s memory. The child gets copies of the page tables, with every writable page marked read-only. The first write by either process faults, and only then is that page copied. This is why fork followed by exec is cheap.
  • vfork, posix_spawn and clone. When the child will immediately call exec, even copying page tables is wasted. posix_spawn creates the new program directly, and Linux’s clone lets the caller choose what is shared, which is how threads and containers are built.
  • Windows has no fork. CreateProcess builds a new process running a named program in one step, and the family of calls on this page is a Unix design choice rather than a law of operating systems.
  • Zombies and orphans. A child that exits stays in the process table as a zombie until the parent calls wait, because the exit status must be kept. If the parent dies first, the child is adopted by init (PID 1), which reaps it. A long-running parent that never waits slowly fills the table.
  • Pipes are just file descriptors. A pipe is a kernel buffer with two descriptors, and a shell builds a | b by forking twice, connecting standard output to one end and standard input to the other, then calling exec. The programs never know.
