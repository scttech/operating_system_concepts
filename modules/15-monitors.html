Monitors and Readers–Writers

Semaphores can solve any synchronization problem, but they are easy to get wrong: swap two calls, forget one, and the program deadlocks or races. This module covers the tools that real programs use instead: the monitor with its condition variables, and the read-write lock, which shows that even “who goes first?” is a design decision with consequences.

Monitors and condition variables

Recall the bounded buffer from Module 6: it needed one semaphore as a mutex and two more to count empty and full slots, and the order of the calls mattered. A monitor packages the same ideas more safely. It bundles the shared data, the lock that protects it, and one or more condition variables on which threads can sleep until something they need has happened. Because the data can only be touched through the monitor’s own operations, the locking discipline lives in one place instead of in every caller.

A condition variable has three operations, always used while holding the lock:

  • wait: atomically release the lock and go to sleep. When woken, reacquire the lock before returning. Doing both at once is essential: if a thread released the lock, then slept, a signal sent in between would be lost forever.
  • signal (notify): wake one sleeping thread, if there is one. Signaling with no one waiting does nothing. A condition variable does not remember signals, unlike a semaphore, which counts them.
  • broadcast (notify all): wake every sleeping thread, for when the change may help several of them.

Why “while”, not “if”

When a thread signals, who runs next? In the textbook’s original design (Hoare semantics) the signaler hands the lock straight to the waiter, so the condition is guaranteed true when the waiter wakes. That is hard to implement efficiently, and real systems do something simpler, called Mesa semantics after the language where it was first used: the signal only makes the waiter ready. The signaler keeps the lock, and the waiter must queue for it like anyone else. In the gap, another thread can get in and change the data. The wake-up is a hint that the condition may be true, not a promise that it still is. (Some systems also deliver a spurious wakeup, a return from wait that nobody signaled, which the specification permits.)

The rule that follows is simple: always wait inside a loop that re-tests the condition.

Try it: step through the if version. C1 finds the buffer empty and sleeps. P1 adds an item and signals, but keeps the lock. Before C1 gets the lock back, C2 arrives and takes the item. C1 then continues as if the item were still there. Switch to while and run the same steps: C1 re-checks and sleeps again. The random runs show that this is not a freak case.

A bounded queue, done properly

Here is the producer–consumer problem with a monitor-style design: one lock, and two condition variables (“not full” for producers to sleep on, “not empty” for consumers). Notice that every wait is in a loop, and that each side signals the other condition.

Try it: two producers, two consumers

Why C is the clearer version here: pthread_cond_wait(&cond, &lock) takes the mutex as an argument, which makes the atomic “release and sleep” visible (comment 3). The final broadcast shows a detail beginners miss: consumers asleep on an empty queue must be woken when the work is over, or the program never exits (comment 5).

/* A bounded queue shared by producers and consumers: one mutex, two condition variables. Linux or macOS. */
#define _POSIX_C_SOURCE 200809L
#include <pthread.h>
#include <stdio.h>

#define CAPACITY 4
#define PRODUCERS 2
#define CONSUMERS 2
#define ITEMS_EACH 100

static int queue[CAPACITY];
static int head = 0, tail = 0, count = 0, most = 0, finished = 0;
static long sum = 0, received = 0;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;            /* (1) one mutex protects all of the shared state above */
static pthread_cond_t not_full = PTHREAD_COND_INITIALIZER;
static pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;

static void *producer(void *arg) {
    (void)arg;
    for (int v = 1; v <= ITEMS_EACH; v++) {
        pthread_mutex_lock(&lock);
        while (count == CAPACITY)                                    /* (2) a WHILE, not an if: after waking, check the condition again */
            pthread_cond_wait(&not_full, &lock);                     /* (3) releases the mutex and sleeps as one step; relocks before returning */
        queue[tail] = v;
        tail = (tail + 1) % CAPACITY;
        count++;
        if (count > most) most = count;
        pthread_cond_signal(&not_empty);                             /* (4) tell one sleeping consumer that there is something to take */
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

static void *consumer(void *arg) {
    (void)arg;
    for (;;) {
        pthread_mutex_lock(&lock);
        while (count == 0 && !finished)
            pthread_cond_wait(&not_empty, &lock);
        if (count == 0) { pthread_mutex_unlock(&lock); return NULL; }   /* (5) nothing left and no more coming: stop instead of sleeping forever */
        sum += queue[head];
        head = (head + 1) % CAPACITY;
        count--;
        received++;
        pthread_cond_signal(&not_full);
        pthread_mutex_unlock(&lock);
    }
}

int main(void) {
    pthread_t p[PRODUCERS], c[CONSUMERS];
    for (int i = 0; i < CONSUMERS; i++) pthread_create(&c[i], NULL, consumer, NULL);
    for (int i = 0; i < PRODUCERS; i++) pthread_create(&p[i], NULL, producer, NULL);
    for (int i = 0; i < PRODUCERS; i++) pthread_join(p[i], NULL);
    pthread_mutex_lock(&lock);
    finished = 1;
    pthread_cond_broadcast(&not_empty);                              /* wake every sleeping consumer so it can notice that the work is over */
    pthread_mutex_unlock(&lock);
    for (int i = 0; i < CONSUMERS; i++) pthread_join(c[i], NULL);
    printf("%d producers sent %d items each; %d consumers received %ld items (sum of values = %ld)\n", PRODUCERS, ITEMS_EACH, CONSUMERS, received, sum);
    printf("the queue never held more than %d items: %s\n", CAPACITY, most <= CAPACITY ? "True" : "False");
    return 0;
}

Python’s threading.Condition is the same idea with less ceremony. A with block takes and releases the lock, and wait() releases it while sleeping. In practice you would use queue.Queue, which is exactly this code packaged up, so a hand-written version is mostly for understanding. The global interpreter lock does not make the loops unnecessary: a thread can still lose its turn between the signal and its wake-up.

"""A bounded queue shared by producers and consumers: one lock, two condition variables."""
import threading

CAPACITY = 4
PRODUCERS = 2
CONSUMERS = 2
ITEMS_EACH = 100

queue = []
state = {"sum": 0, "received": 0, "most": 0, "finished": False}
lock = threading.Lock()                                              # (1) one lock protects all of the shared state above
not_full = threading.Condition(lock)
not_empty = threading.Condition(lock)


def producer():
    for v in range(1, ITEMS_EACH + 1):
        with lock:
            while len(queue) == CAPACITY:                            # (2) a WHILE, not an if: after waking, check the condition again
                not_full.wait()                                      # (3) releases the lock and sleeps as one step; relocks before returning
            queue.append(v)
            state["most"] = max(state["most"], len(queue))
            not_empty.notify()                                       # (4) tell one sleeping consumer that there is something to take


def consumer():
    while True:
        with lock:
            while not queue and not state["finished"]:
                not_empty.wait()
            if not queue:                                            # (5) nothing left and no more coming: stop instead of sleeping forever
                return
            state["sum"] += queue.pop(0)
            state["received"] += 1
            not_full.notify()


consumers = [threading.Thread(target=consumer) for _ in range(CONSUMERS)]
producers = [threading.Thread(target=producer) for _ in range(PRODUCERS)]
for t in consumers + producers:
    t.start()
for t in producers:
    t.join()
with lock:
    state["finished"] = True
    not_empty.notify_all()                                           # wake every sleeping consumer so it can notice that the work is over
for t in consumers:
    t.join()
print(f"{PRODUCERS} producers sent {ITEMS_EACH} items each; {CONSUMERS} consumers received {state['received']} items (sum of values = {state['sum']})")
print(f"the queue never held more than {CAPACITY} items: {state['most'] <= CAPACITY}")

Readers and writers

Many programs read shared data far more often than they change it: a routing table, a configuration, a cache. Two readers cannot interfere with each other, so making them take turns wastes parallelism. The readers–writers problem is to let readers share while a writer is kept alone. The usual tool is a read–write lock with two modes: shared and exclusive.

That leaves a policy question for when both kinds are waiting:

  • Reader preference. A reader never waits behind another reader, even if a writer is already waiting. Maximum sharing, but a steady stream of readers can keep a writer out indefinitely.
  • Writer preference. When a writer is waiting, new readers wait too. Data stays fresh, but a steady stream of writers can starve the readers.
  • First come, first served. Requests are admitted in arrival order, and a run of readers at the front can go together. Nobody starves, at the cost of some sharing.

Try it: the first workload is a steady stream of readers plus a single writer that arrives early. Under reader preference it waits for the entire stream. Switch to writer preference, and then to first come, first served. Then pick the second workload (a stream of writers and one reader) and see the roles reverse. The comparison table shows that no policy wins every column.

Try it: readers that always see a consistent pair

Why C is the clearer version here: POSIX has a read-write lock built in (pthread_rwlock_t), with rdlock for shared and wrlock for exclusive access. The writer changes two variables that must always match; a reader that holds the lock can rely on them matching, which is exactly what the lock buys.

/* A read-write lock: many readers at once, one writer alone. Linux or macOS. */
#define _POSIX_C_SOURCE 200809L
#include <pthread.h>
#include <stdio.h>

#define READERS 4
#define READS_EACH 1000
#define UPDATES 1000

static int a = 0, b = 0;                           /* the writer always changes both, so a == b whenever nobody is in the middle of an update */
static pthread_rwlock_t rw = PTHREAD_RWLOCK_INITIALIZER;

typedef struct { int reads, torn; } Result;

static void *reader(void *arg) {
    Result *r = arg;
    for (int i = 0; i < READS_EACH; i++) {
        pthread_rwlock_rdlock(&rw);                /* (1) a shared lock: any number of readers may hold it together */
        if (a != b) r->torn++;                     /* (3) holding either lock, nobody else can be mid-update, so a == b can be trusted */
        r->reads++;
        pthread_rwlock_unlock(&rw);                /* (4) release the lock, whichever kind it was */
    }
    return NULL;
}

static void *writer(void *arg) {
    (void)arg;
    for (int i = 0; i < UPDATES; i++) {
        pthread_rwlock_wrlock(&rw);                /* (2) an exclusive lock: waits until every reader and writer has left */
        a++;                                       /* in between these two lines the pair is inconsistent, but only the writer can see that */
        b++;
        pthread_rwlock_unlock(&rw);
    }
    return NULL;
}

int main(void) {
    pthread_t rt[READERS], wt;
    Result res[READERS] = {{0, 0}};
    pthread_create(&wt, NULL, writer, NULL);
    for (int i = 0; i < READERS; i++) pthread_create(&rt[i], NULL, reader, &res[i]);
    pthread_join(wt, NULL);
    long reads = 0, torn = 0;
    for (int i = 0; i < READERS; i++) { pthread_join(rt[i], NULL); reads += res[i].reads; torn += res[i].torn; }
    printf("%d readers made %ld reads; every read saw a consistent pair: %s\n", READERS, reads, torn == 0 ? "True" : "False");
    printf("the writer made %d updates; final value: %d\n", UPDATES, a);
    return 0;
}

This is more contrived in Python. The standard library has no read–write lock, so the example builds one from a Condition, and it is a plain reader-preference lock, so it can starve a writer. Also, because of the global interpreter lock, Python readers never run in parallel anyway, so the speed benefit that motivates a read-write lock mostly disappears. The code is useful for seeing how such a lock works, not as something to copy into a program.

"""A read-write lock: many readers at once, one writer alone. Python has none built in, so this one is built from a Condition."""
import threading

READERS = 4
READS_EACH = 1000
UPDATES = 1000


class ReadWriteLock:
    def __init__(self):
        self._cond = threading.Condition()
        self._readers = 0
        self._writing = False

    def acquire_read(self):
        with self._cond:
            while self._writing:
                self._cond.wait()
            self._readers += 1

    def release_read(self):
        with self._cond:
            self._readers -= 1
            if self._readers == 0:
                self._cond.notify_all()

    def acquire_write(self):
        with self._cond:
            while self._writing or self._readers:
                self._cond.wait()
            self._writing = True

    def release_write(self):
        with self._cond:
            self._writing = False
            self._cond.notify_all()


rw = ReadWriteLock()
pair = {"a": 0, "b": 0}                     # the writer always changes both, so a == b whenever nobody is in the middle of an update
results = [{"reads": 0, "torn": 0} for _ in range(READERS)]


def reader(result):
    for _ in range(READS_EACH):
        rw.acquire_read()                   # (1) a shared lock: any number of readers may hold it together
        if pair["a"] != pair["b"]:          # (3) holding either lock, nobody else can be mid-update, so a == b can be trusted
            result["torn"] += 1
        result["reads"] += 1
        rw.release_read()                   # (4) release the lock, whichever kind it was


def writer():
    for _ in range(UPDATES):
        rw.acquire_write()                  # (2) an exclusive lock: waits until every reader and writer has left
        pair["a"] += 1                      # in between these two lines the pair is inconsistent, but only the writer can see that
        pair["b"] += 1
        rw.release_write()


threads = [threading.Thread(target=writer)] + [threading.Thread(target=reader, args=(r,)) for r in results]
for t in threads:
    t.start()
for t in threads:
    t.join()
reads = sum(r["reads"] for r in results)
torn = sum(r["torn"] for r in results)
print(f"{READERS} readers made {reads} reads; every read saw a consistent pair: {torn == 0}")
print(f"the writer made {UPDATES} updates; final value: {pair['a']}")

AdvancedGoing deeper: costs and alternatives
  • Hoare versus Mesa, precisely. In Hoare’s version the signal transfers the lock and the condition immediately, so an if is enough, but it forces an extra context switch on every signal. Mesa lets the signaler continue, which allows the cheaper “signal, then keep working” pattern, at the price of the loop. Java, POSIX, Python and C++ are all Mesa-style.
  • Signal or broadcast? Signaling one waiter is only safe when any waiter can use the change. If waiters want different things (a buffer of unequal-size requests, say), signaling one may wake a thread that cannot proceed and leave the right one asleep. broadcast is always correct; it can be slower because everyone wakes and re-checks (a thundering herd).
  • Lost wake-ups. If a program checks a condition without holding the lock and then sleeps, a signal arriving between the two steps is lost, and the thread may sleep forever. This is the reason waiting and the lock release are one atomic operation.
  • Read–write locks are not free. Even shared readers must update the lock’s counter, which bounces a cache line between cores. With short read sections, a plain mutex or a lock-free design can beat a read–write lock. Linux uses RCU for read-mostly kernel data, so readers do not write to shared memory at all.
  • Upgrading is dangerous. A thread holding a read lock cannot simply ask for the write lock: two readers both trying to upgrade will each wait for the other to leave, a deadlock (see Module 7). Most libraries do not support upgrade for this reason.
  • Seqlocks. For small, frequently read data, a writer increments a version number before and after updating, and a reader retries if the number changed or was odd. Readers never block the writer and never take a lock, which solves writer starvation by construction.
  • Fairness versus throughput. Fair queues can create a lock convoy: every thread wakes, runs a moment, and sleeps again behind the next. Real implementations mix policies, for example letting a thread barge in once but putting it at the back after it has waited too long.
