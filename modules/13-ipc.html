Inter-Process Communication

Every process lives in its own protected address space, which is great for safety and terrible for cooperation. Inter-process communication (IPC) is the set of controlled openings the kernel provides so that processes can still work together.

Why processes need IPC

A shell pipeline such as ls | grep txt | wc -l runs three separate programs. A web server hands requests to worker processes. A browser keeps each tab in its own process and still has to draw them in one window. None of these programs can read another's variables, because the MMU and the page tables you met in Module 8 make each address space private. To share anything, they must ask the kernel.

Two families

  • Message passing: the sender calls a system call to hand data to the kernel, and the receiver calls another to get it. The kernel copies the data and also decides who must wait. Pipes, sockets and message queues work this way. It is easy to get right, and it works across machines.
  • Shared memory: the kernel maps the same physical pages into both address spaces. After the set-up, data moves with ordinary loads and stores: no system call, no copy. The price is that the kernel is no longer in the middle, so the processes must synchronize themselves.

Pipes

A pipe is a buffer inside the kernel with two ends, each referred to by a file descriptor. One process writes into one end and another reads from the other end. Three rules explain almost everything about its behavior:

  1. It is a byte stream. The pipe does not remember where one write stopped and the next began. Two writes may be returned by one read, and one write by several reads.
  2. Waiting is built in. A write to a full pipe puts the writer to sleep, and a read from an empty pipe puts the reader to sleep. A sleeping process uses no CPU. This is the same producer–consumer idea as the bounded buffer in Module 6, with the kernel doing the locking.
  3. Ends close, and that means something. A read returns zero bytes, end of file, only when the buffer is empty and every write end is closed. A write when no read end remains is a broken pipe: the writer gets a signal (SIGPIPE) or an error.

Try it: use the scenarios, then experiment. With a pipe, write hello and then world and read 20 bytes: you get helloworld in one read. Switch to a message queue and the same sequence needs two reads. Next, fill the pipe, and notice that the writer sleeps until the reader makes room. Finally close the writer's end while the reader is asleep.

Try it: a pipe between a parent and its child

Why C is the clearer version here: pipe, fork, read, write and close are the real system calls, and the two file descriptors are plain integers in an array. Look at comment (2): because fork copies the descriptor table, the child holds a write end it never uses, and forgetting to close it is the classic reason a reader never sees end of file.

/* A pipe between a parent and its child. Linux or macOS. */
#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int fd[2];
    if (pipe(fd) != 0) return 1;                    /* (1) a pipe is a kernel buffer with two ends: fd[0] to read from, fd[1] to write to */
    pid_t pid = fork();
    if (pid < 0) return 1;
    if (pid == 0) {                                 /* (2) the child inherited both ends; it closes the one it does not use */
        close(fd[1]);
        char buf[64];
        ssize_t n;
        while ((n = read(fd[0], buf, sizeof buf - 1)) > 0) {      /* (4) read waits for data; it returns 0 (end of file) only when every write end is closed */
            buf[n] = '\0';
            printf("child read %zd bytes: %s\n", n, buf);
        }
        printf("child saw end of file\n");
        close(fd[0]);
        return 0;
    }
    close(fd[0]);
    const char *msg = "hello through a pipe";
    ssize_t sent = write(fd[1], msg, strlen(msg));  /* (3) the parent copies the bytes into the kernel's buffer */
    if (sent < 0) return 1;
    close(fd[1]);                                   /* closing the last write end is what lets the child's read return 0 */
    int status = 0;
    wait(&status);
    printf("parent wrote %zd bytes and the child exited with status %d\n", sent, WEXITSTATUS(status));
    return 0;
}

Python’s os module mirrors the C calls almost one-to-one (os.pipe, os.fork, os.read, os.write), so nothing here is contrived. The difference is convenience: higher-level tools such as subprocess and multiprocessing build and close the pipes for you, which is why Python programmers rarely write this code by hand. Needs Linux or macOS because of fork.

"""A pipe between a parent and its child. Unix only."""
import os
import sys

read_end, write_end = os.pipe()                     # (1) a pipe is a kernel buffer with two ends: one to read from, one to write to
pid = os.fork()
if pid == 0:                                        # (2) the child inherited both ends; it closes the one it does not use
    os.close(write_end)
    while True:
        data = os.read(read_end, 63)                # (4) read waits for data; it returns b"" (end of file) only when every write end is closed
        if not data:
            break
        print(f"child read {len(data)} bytes: {data.decode()}")
    print("child saw end of file")
    sys.stdout.flush()
    os._exit(0)

os.close(read_end)
message = b"hello through a pipe"
sent = os.write(write_end, message)                 # (3) the parent copies the bytes into the kernel's buffer
os.close(write_end)                                 # closing the last write end is what lets the child's read return b""
_, status = os.waitpid(pid, 0)
print(f"parent wrote {sent} bytes and the child exited with status {os.waitstatus_to_exitcode(status)}")

An ordinary pipe has no name, so only related processes (a parent and children that inherit it) can use it. A named pipe (FIFO) appears in the file system, so unrelated processes can open it. It behaves the same way otherwise.

Sockets and message queues

A pipe is one-way. A socket is an endpoint that can both send and receive, and the same calls work whether the other end is a process on this machine (a Unix-domain socket) or a program on the other side of the world (a network socket). That is why sockets are the foundation of client/server software.

If you need the boundaries between items preserved, use a message queue (POSIX mq_send and mq_receive, or datagram sockets): each receive returns exactly one message. Compare the two mechanisms in the explorer above.

Try it: asking a question and getting an answer

Why C is the clearer version here: socketpair returns two connected descriptors, exactly like pipe, except that either end can be read and written. Comment (4) shows the blocking rule from the pipe section again: the parent’s read sleeps until the child answers.

/* Two-way messages between a parent and a child over a connected pair of sockets. Linux or macOS. */
#define _POSIX_C_SOURCE 200809L
#include <ctype.h>
#include <stdio.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int sv[2];
    if (socketpair(AF_UNIX, SOCK_STREAM, 0, sv) != 0) return 1;    /* (1) two connected ends; unlike a pipe, each end can both send and receive */
    pid_t pid = fork();
    if (pid < 0) return 1;
    if (pid == 0) {
        close(sv[0]);                               /* (2) each process keeps one end and closes the other */
        char buf[32];
        ssize_t n = read(sv[1], buf, sizeof buf);
        for (ssize_t i = 0; i < n; i++) buf[i] = (char)toupper((unsigned char)buf[i]);
        if (write(sv[1], buf, (size_t)n) != n) return 1;           /* the child answers on the same socket */
        close(sv[1]);
        return 0;
    }
    close(sv[1]);
    const char *request = "ping";
    if (write(sv[0], request, strlen(request)) < 0) return 1;      /* (3) send a request... */
    printf("parent sent:     %s\n", request);
    char reply[32];
    ssize_t n = read(sv[0], reply, sizeof reply - 1);              /* (4) ...then wait for the reply: read blocks until the child has answered */
    if (n < 0) return 1;
    reply[n] = '\0';
    printf("parent received: %s\n", reply);
    close(sv[0]);
    wait(NULL);
    return 0;
}

Python wraps this nicely. The socket module’s socketpair() returns objects with sendall and recv, so the same idea takes fewer lines and no pointer arithmetic. A real server would use socket.socket(...) with bind, listen and accept, which is where the network version begins.

"""Two-way messages between a parent and a child over a connected pair of sockets. Unix only."""
import os
import socket

parent_end, child_end = socket.socketpair()         # (1) two connected ends; unlike a pipe, each end can both send and receive
pid = os.fork()
if pid == 0:
    parent_end.close()                              # (2) each process keeps one end and closes the other
    request = child_end.recv(32)
    child_end.sendall(request.upper())              # the child answers on the same socket
    child_end.close()
    os._exit(0)

child_end.close()
request = b"ping"
parent_end.sendall(request)                         # (3) send a request...
print(f"parent sent:     {request.decode()}")
reply = parent_end.recv(31)                         # (4) ...then wait for the reply: recv blocks until the child has answered
print(f"parent received: {reply.decode()}")
parent_end.close()
os.waitpid(pid, 0)

Shared memory

With shared memory the kernel does the work once, when the mapping is created. Afterwards both processes just use the memory. This is the fastest local mechanism, and it is also the most dangerous, because two processes can now race on the same bytes exactly as two threads can. In practice shared memory is paired with a mutex or semaphore that lives inside the shared block itself.

Try it: what the child can and cannot change

Why C is the clearer version here: mmap with MAP_SHARED | MAP_ANONYMOUS shows precisely what is special about the block: ordinary memory is copied by fork (so the child’s change stays private), while the shared mapping points at the same physical pages in both processes.

/* Shared memory versus ordinary memory after fork(). Linux or macOS. */
#define _POSIX_C_SOURCE 200809L
#define _DEFAULT_SOURCE
#include <stdio.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int ordinary = 1;
    /* (1) MAP_SHARED | MAP_ANONYMOUS asks for one block of memory that parent and child will both see after fork() */
    int *shared = mmap(NULL, sizeof *shared, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    if (shared == MAP_FAILED) return 1;
    *shared = 1;

    pid_t pid = fork();
    if (pid < 0) return 1;
    if (pid == 0) {
        ordinary = 99;                              /* (2) the child changes both values; fork gave it its own copy of ordinary memory... */
        *shared = 99;                               /* ...but the shared block is the same physical memory in both processes */
        _exit(0);
    }
    wait(NULL);
    printf("ordinary variable after the child set it to 99: %d\n", ordinary);   /* (3) still 1: the child changed its own copy */
    printf("shared memory after the child set it to 99:     %d\n", *shared);    /* (4) 99: no system call or copy moved this value */
    munmap(shared, sizeof *shared);
    return 0;
}

Python can do it, but it is a thinner abstraction. An anonymous mmap is shared with a forked child, but it holds bytes rather than typed values, so structured data needs struct or ctypes. In day-to-day Python you would use multiprocessing.shared_memory or multiprocessing.Value, which add the locking and cleanup that raw shared memory leaves to you.

"""Shared memory versus ordinary memory after fork(). Unix only."""
import mmap
import os

ordinary = [1]
shared = mmap.mmap(-1, 1)                           # (1) an anonymous mmap is shared with a forked child: one block of memory both processes see
shared[0] = 1

pid = os.fork()
if pid == 0:
    ordinary[0] = 99                                # (2) the child changes both values; fork gave it its own copy of ordinary memory...
    shared[0] = 99                                  # ...but the shared block is the same physical memory in both processes
    os._exit(0)
os.waitpid(pid, 0)
print(f"ordinary variable after the child set it to 99: {ordinary[0]}")      # (3) still 1: the child changed its own copy
print(f"shared memory after the child set it to 99:     {shared[0]}")        # (4) 99: no system call or copy moved this value
shared.close()

What each one costs

Try it: choose “Small messages”, where a pipe needs two system calls per message, then “One big transfer”. Shared memory’s advantage grows with the number of transfers, but it never removes the need to coordinate.

AdvancedGoing deeper: how real systems do it
  • Atomic small writes. POSIX guarantees that a write of up to PIPE_BUF bytes (at least 512, 4096 on Linux) is never interleaved with another process’s write to the same pipe. Larger writes may be split, so several writers sending big records into one pipe can garble them.
  • Pipe capacity. Linux pipes hold 64 KiB by default (adjustable with fcntl). A writer that outruns its reader sleeps, and that back-pressure is why a shell pipeline never needs to buffer a whole file in memory.
  • Zero-copy. Calls such as splice, sendfile and vmsplice hand page references between descriptors instead of copying bytes, which is how a web server can send a file from the disk cache to a socket without the data ever entering user space.
  • Descriptors can themselves be passed. A Unix-domain socket can carry an open file descriptor to another process (SCM_RIGHTS), which is how a privileged helper opens a file and hands the result to an unprivileged program. This is the capability idea from Module 2 in practice.
  • IPC in the systems of Module 12. Android’s apps talk through Binder, a kernel driver that delivers a call to another process and returns the result, with the caller’s identity attached for permission checks. macOS and iOS use Mach ports. Windows offers named pipes, ALPC and COM. Microkernels such as QNX are built almost entirely on fast message passing.
  • Lock-free ring buffers. High-performance shared-memory channels use a circular buffer with one producer and one consumer, each advancing only its own index, so neither needs a lock. They depend on the memory-ordering rules from Module 6.
  • Shared memory is still memory. It is mapped through page tables like everything else, so each process may map it at a different virtual address. Pointers stored inside the shared block must therefore be offsets, not raw addresses.
