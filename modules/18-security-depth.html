Module 18

Security in Depth

Module 2 covered who is allowed to do what. This module covers what happens when something goes wrong anyway: a bug that lets an attacker run their own code, a stolen password file, or a design that never asked how it could be abused. The recurring lesson is defense in depth: no single protection is enough, so you layer them.

When memory is not protected: buffer overflows

An operating system keeps processes apart, but it cannot protect a process from its own bugs. The most famous bug is the buffer overflow: a program copies input into a fixed-size buffer and never checks how long the input is. In C, nothing stops the extra bytes from landing on whatever lies next to the buffer.

On the stack, that is a problem, because a function's frame holds more than its local variables. Just above a local buffer sit the saved frame pointer and, above that, the return address: the place the CPU will jump to when the function finishes. An attacker who can write past the end of the buffer can choose that address, and so choose what code runs next.

Try it: start with “Fits in the buffer”, then “Plain overflow”: filler bytes (AAAA…) wreck the return address and the program crashes. That is bad (an attacker can crash your service) but not a takeover. Now “Real attack, no defenses”: the attacker writes a chosen address, and the function returns there. Then switch on the defenses one by one.

Try it: an overflow you can look at safely

Why C is the clearer version here: C is the language where the bug exists, and it is plain from the code why: memcpy (or strcpy, or the long-removed gets) does exactly what it is told with no idea how big the destination is. The frame here is a byte array, so the demonstration is completely safe: nothing outside it is touched. Comment (4) shows the whole fix: never copy more than the buffer holds.

/* A stack frame simulated in a byte array, so you can see what an unchecked copy overwrites. Safe: nothing here breaks real memory. Runs anywhere. */
#include <stdint.h>
#include <stdio.h>
#include <string.h>

#define BUF 16
#define CANARY_AT 16
#define FP_AT 20
#define RET_AT 24
#define MEM 40                      /* the frame (28 bytes) plus some caller memory above it */

static const uint32_t CANARY = 0xC0FFEE42u, FRAME_PTR = 0xBFFFF100u, RETURN_ADDR = 0x08048456u;

static void put32(uint8_t *p, uint32_t v) { p[0] = (uint8_t)v; p[1] = (uint8_t)(v >> 8); p[2] = (uint8_t)(v >> 16); p[3] = (uint8_t)(v >> 24); }
static uint32_t get32(const uint8_t *p) { return (uint32_t)p[0] | ((uint32_t)p[1] << 8) | ((uint32_t)p[2] << 16) | ((uint32_t)p[3] << 24); }

static void new_frame(uint8_t *mem) {                /* (1) the buffer is the lowest part of the frame: everything above it is saved state */
    memset(mem, 0, MEM);
    put32(mem + CANARY_AT, CANARY);
    put32(mem + FP_AT, FRAME_PTR);
    put32(mem + RET_AT, RETURN_ADDR);
}
static void copy_unchecked(uint8_t *mem, const uint8_t *input, size_t n) { memcpy(mem, input, n); }          /* (2) trusts the length, like strcpy or gets */
static void copy_checked(uint8_t *mem, const uint8_t *input, size_t n) { memcpy(mem, input, n < BUF ? n : BUF); }   /* (4) never writes more than the buffer holds: the fix */

static void report(const char *label, const uint8_t *mem) {
    int canary_ok = get32(mem + CANARY_AT) == CANARY, fp_ok = get32(mem + FP_AT) == FRAME_PTR;
    uint32_t ret = get32(mem + RET_AT);
    const char *verdict = !canary_ok ? "aborted by the canary check"      /* (3) the canary sits between the buffer and the return address and is checked before returning */
                        : ret != RETURN_ADDR ? "returns to a changed address"
                        : !fp_ok ? "frame pointer damaged" : "returns normally";
    printf("%-36s canary %-6s, saved fp %-6s, return address 0x%08x -> %s\n", label, canary_ok ? "intact" : "SMASHED", fp_ok ? "intact" : "SMASHED", (unsigned)ret, verdict);
}

int main(void) {
    uint8_t mem[MEM], input[MEM];
    memset(input, 'A', sizeof input);
    const size_t sizes[4] = { 8, 16, 20, 28 };
    for (int i = 0; i < 4; i++) {
        char label[64];
        snprintf(label, sizeof label, "copy of %d bytes (unchecked):", (int)sizes[i]);
        new_frame(mem); copy_unchecked(mem, input, sizes[i]); report(label, mem);
    }
    /* an attacker who has learned the canary writes it back, and chooses the return address */
    memset(input, 'A', sizeof input);
    put32(input + CANARY_AT, CANARY); memset(input + FP_AT, 'B', 4); put32(input + RET_AT, 0x0804DEADu);
    new_frame(mem); copy_unchecked(mem, input, 28); report("crafted 28 bytes, canary known:", mem);
    memset(input, 'A', sizeof input);
    new_frame(mem); copy_checked(mem, input, 28); report("copy of 28 bytes (checked, cut to 16):", mem);
    return 0;
}

This is a simulation in Python, not the real thing. Pure Python is memory-safe: writing past the end of a list or bytearray raises an error instead of touching the next object, so this kind of bug cannot happen in ordinary Python code. It appears only when Python calls into C (extension modules, ctypes). That is the main reason memory-safe languages (Python, Java, Go, Rust) have become the default advice for new software. The program above imitates the C layout by hand, with struct doing the byte packing.

"""A stack frame simulated in a byte array, so you can see what an unchecked copy overwrites. Safe: nothing here breaks real memory."""
import struct

BUF, CANARY_AT, FP_AT, RET_AT, MEM = 16, 16, 20, 24, 40
CANARY, FRAME_PTR, RETURN_ADDR = 0xC0FFEE42, 0xBFFFF100, 0x08048456


def new_frame():                                         # (1) the buffer is the lowest part of the frame: everything above it is saved state
    mem = bytearray(MEM)
    struct.pack_into("<III", mem, CANARY_AT, CANARY, FRAME_PTR, RETURN_ADDR)
    return mem


def copy_unchecked(mem, data):
    mem[0:len(data)] = data                              # (2) trusts the length, like strcpy or gets


def copy_checked(mem, data):
    mem[0:min(len(data), BUF)] = data[:BUF]              # (4) never writes more than the buffer holds: the fix


def report(label, mem):
    canary, fp, ret = struct.unpack_from("<III", mem, CANARY_AT)
    if canary != CANARY:                                 # (3) the canary sits between the buffer and the return address and is checked before returning
        verdict = "aborted by the canary check"
    elif ret != RETURN_ADDR:
        verdict = "returns to a changed address"
    elif fp != FRAME_PTR:
        verdict = "frame pointer damaged"
    else:
        verdict = "returns normally"
    print(f"{label:<36} canary {'intact' if canary == CANARY else 'SMASHED':<6}, saved fp {'intact' if fp == FRAME_PTR else 'SMASHED':<6}, return address 0x{ret:08x} -> {verdict}")


for size in (8, 16, 20, 28):
    mem = new_frame()
    copy_unchecked(mem, b"A" * size)
    report(f"copy of {size} bytes (unchecked):", mem)
# an attacker who has learned the canary writes it back, and chooses the return address
payload = b"A" * 16 + struct.pack("<I", CANARY) + b"BBBB" + struct.pack("<I", 0x0804DEAD)
mem = new_frame()
copy_unchecked(mem, payload)
report("crafted 28 bytes, canary known:", mem)
mem = new_frame()
copy_checked(mem, b"A" * 28)
report("copy of 28 bytes (checked, cut to 16):", mem)

Layers of defense

The real fix is to check lengths, or to use a language that does so for you. But code will always have bugs, so the system adds layers that make an overflow harder to exploit. Each has a weakness, and that is why they are combined:

DefenseWhat it doesWhat gets around it
Stack canaryA secret value between the buffer and the return address; checked before the function returns, so an overflow is noticed.An information leak that reveals the canary, so the attacker can write it back; or a bug that skips over it.
Non-executable memory (NX)The hardware refuses to run code from the stack or heap, so code the attacker injected cannot run.Reusing code that already exists (return-oriented programming): the attacker chains small pieces of the program's own code.
ASLRPlaces the stack, heap and libraries at random addresses each run, so the attacker does not know where to jump.A leak that reveals one address; or guessing, when there is little randomness (about 8 bits in the simulator).
Least privilege, sandboxesEven if the program is taken over, it can do only what its account and sandbox allow (Module 2, Module 14).A second bug, in the kernel or the sandbox, that lets the attacker out.

This is defense in depth. In the simulator, tick all three defenses and the attack fails. Then add an information leak and a code-reuse target and it succeeds again, which is exactly how real exploits are built: first a leak, then the overflow.

Passwords

Passwords are the oldest form of authentication and the most attacked. Two separate questions matter: how hard is it to guess a password, and what should the system store so that a stolen file does not hand attackers every password?

How hard is it to guess?

Strength is the number of guesses an attacker needs, and it depends on how the password was chosen. A password picked at random from a large alphabet is far stronger than a word with a few digits added, even if the second looks longer. And it depends on what the attacker has: guessing through a login page is slow because the server limits tries, but an attacker who has stolen the file can try billions of guesses a second offline.

Try it: eight lower-case letters, against a fast unsalted hash, fall in seconds. Now switch to “a common word with digits” and notice that adding length does nothing, because the real search space is the same. Then try 16 characters of letters, digits and symbols chosen randomly.

What should the system store?

Never the password, and not a plain hash of it either. The right answer is a salted, deliberately slow hash. A salt is a random value stored next to each hash and mixed into it, so that two users with the same password get different hashes and a table of precomputed hashes is useless. Key stretching (repeating the hash, or using a function designed to be slow and memory-hungry such as bcrypt, scrypt or Argon2) makes each guess expensive. A login does the work once; an attacker does it for every guess.

Try it: storing and checking a password

Why C is the clearer version here: C has no password-hashing function in its standard library, so the example carries its own small SHA-256, which shows that a hash is just arithmetic on bytes. The loop in comment (3) is the “stretching”. The comparison in comment (4) looks at every byte instead of stopping at the first difference, so how long the check takes does not reveal how close a guess was. Do not use this in a real system: use a vetted library and a purpose-built password hash.

/* Storing passwords: why a plain hash is not enough, what a salt adds, and what repeating the hash costs an attacker. Runs anywhere.
 * Includes its own SHA-256 so that no library is needed; real programs should use a vetted library and a purpose-built password hash. */
#include <stdint.h>
#include <stdio.h>
#include <string.h>

#define ROUNDS 10000

static const uint32_t K[64] = {
    0x428a2f98, 0x71374491, 0xb5c0fbcf, 0xe9b5dba5, 0x3956c25b, 0x59f111f1, 0x923f82a4, 0xab1c5ed5, 0xd807aa98, 0x12835b01, 0x243185be, 0x550c7dc3, 0x72be5d74, 0x80deb1fe, 0x9bdc06a7, 0xc19bf174,
    0xe49b69c1, 0xefbe4786, 0x0fc19dc6, 0x240ca1cc, 0x2de92c6f, 0x4a7484aa, 0x5cb0a9dc, 0x76f988da, 0x983e5152, 0xa831c66d, 0xb00327c8, 0xbf597fc7, 0xc6e00bf3, 0xd5a79147, 0x06ca6351, 0x14292967,
    0x27b70a85, 0x2e1b2138, 0x4d2c6dfc, 0x53380d13, 0x650a7354, 0x766a0abb, 0x81c2c92e, 0x92722c85, 0xa2bfe8a1, 0xa81a664b, 0xc24b8b70, 0xc76c51a3, 0xd192e819, 0xd6990624, 0xf40e3585, 0x106aa070,
    0x19a4c116, 0x1e376c08, 0x2748774c, 0x34b0bcb5, 0x391c0cb3, 0x4ed8aa4a, 0x5b9cca4f, 0x682e6ff3, 0x748f82ee, 0x78a5636f, 0x84c87814, 0x8cc70208, 0x90befffa, 0xa4506ceb, 0xbef9a3f7, 0xc67178f2
};

static uint32_t rotr(uint32_t x, int n) { return (x >> n) | (x << (32 - n)); }

static void compress(uint32_t h[8], const uint8_t b[64]) {
    uint32_t w[64], v[8];
    for (int i = 0; i < 16; i++) w[i] = ((uint32_t)b[4 * i] << 24) | ((uint32_t)b[4 * i + 1] << 16) | ((uint32_t)b[4 * i + 2] << 8) | (uint32_t)b[4 * i + 3];
    for (int i = 16; i < 64; i++) {
        uint32_t s0 = rotr(w[i - 15], 7) ^ rotr(w[i - 15], 18) ^ (w[i - 15] >> 3), s1 = rotr(w[i - 2], 17) ^ rotr(w[i - 2], 19) ^ (w[i - 2] >> 10);
        w[i] = w[i - 16] + s0 + w[i - 7] + s1;
    }
    memcpy(v, h, sizeof v);
    for (int i = 0; i < 64; i++) {
        uint32_t S1 = rotr(v[4], 6) ^ rotr(v[4], 11) ^ rotr(v[4], 25), ch = (v[4] & v[5]) ^ (~v[4] & v[6]), t1 = v[7] + S1 + ch + K[i] + w[i];
        uint32_t S0 = rotr(v[0], 2) ^ rotr(v[0], 13) ^ rotr(v[0], 22), maj = (v[0] & v[1]) ^ (v[0] & v[2]) ^ (v[1] & v[2]), t2 = S0 + maj;
        v[7] = v[6]; v[6] = v[5]; v[5] = v[4]; v[4] = v[3] + t1; v[3] = v[2]; v[2] = v[1]; v[1] = v[0]; v[0] = t1 + t2;
    }
    for (int i = 0; i < 8; i++) h[i] += v[i];
}

static void sha256(const uint8_t *data, size_t len, uint8_t out[32]) {
    uint32_t h[8] = { 0x6a09e667, 0xbb67ae85, 0x3c6ef372, 0xa54ff53a, 0x510e527f, 0x9b05688c, 0x1f83d9ab, 0x5be0cd19 };
    size_t i = 0;
    for (; i + 64 <= len; i += 64) compress(h, data + i);
    uint8_t tail[128];
    size_t rem = len - i, total = rem < 56 ? 64 : 128;
    memset(tail, 0, sizeof tail);
    memcpy(tail, data + i, rem);
    tail[rem] = 0x80;
    uint64_t bits = (uint64_t)len * 8;
    for (int k = 0; k < 8; k++) tail[total - 1 - k] = (uint8_t)(bits >> (8 * k));
    compress(h, tail);
    if (total == 128) compress(h, tail + 64);
    for (int k = 0; k < 8; k++) { out[4 * k] = (uint8_t)(h[k] >> 24); out[4 * k + 1] = (uint8_t)(h[k] >> 16); out[4 * k + 2] = (uint8_t)(h[k] >> 8); out[4 * k + 3] = (uint8_t)h[k]; }
}

static void plain(const char *password, uint8_t out[32]) { sha256((const uint8_t *)password, strlen(password), out); }

static void salted(const char *salt, const char *password, uint8_t out[32]) {
    uint8_t buf[128];
    size_t a = strlen(salt), b = strlen(password);
    memcpy(buf, salt, a); memcpy(buf + a, password, b);
    sha256(buf, a + b, out);
}

static void stretched(const char *salt, const char *password, int rounds, uint8_t out[32]) {
    uint8_t buf[128];
    size_t b = strlen(password);
    salted(salt, password, out);
    for (int i = 1; i < rounds; i++) {            /* (3) repeating makes each guess cost many hashes, for the attacker and for us */
        memcpy(buf, out, 32); memcpy(buf + 32, password, b);
        sha256(buf, 32 + b, out);
    }
}

static int same(const uint8_t *a, const uint8_t *b) {
    uint8_t diff = 0;
    for (int i = 0; i < 32; i++) diff |= (uint8_t)(a[i] ^ b[i]);      /* (4) look at every byte, so the time taken does not reveal where they first differ */
    return diff == 0;
}

static void show(const char *label, const uint8_t d[32]) {
    printf("%-24s", label);
    for (int i = 0; i < 8; i++) printf("%02x", d[i]);
    printf("...\n");
}

int main(void) {
    const char *password = "correct horse", *alice_salt = "a1b2c3d4", *bob_salt = "9f8e7d6c";
    uint8_t a[32], b[32], stored[32], guess[32];
    char label[64];

    plain("password", a); show("sha256 of \"password\":", a);
    plain(password, a); plain(password, b);
    show("alice, no salt:", a); show("bob, no salt:", b);
    printf("same password, same stored hash: %s\n", same(a, b) ? "True" : "False");           /* (1) without a salt, equal passwords give equal hashes */
    salted(alice_salt, password, a); salted(bob_salt, password, b);
    show("alice, salted:", a); show("bob, salted:", b);
    printf("same password, same stored hash: %s\n", same(a, b) ? "True" : "False");           /* (2) a salt makes every record unique, so a table of precomputed hashes is useless */
    stretched(alice_salt, password, ROUNDS, stored);
    snprintf(label, sizeof label, "alice, salted, x%d:", ROUNDS);
    show(label, stored);
    const char *guesses[2] = { "correct horse", "correct horsf" };
    for (int i = 0; i < 2; i++) {
        stretched(alice_salt, guesses[i], ROUNDS, guess);
        printf("check \"%s\": %s\n", guesses[i], same(guess, stored) ? "True" : "False");
    }
    return 0;
}

Python makes this much shorter, because hashlib provides SHA-256 and hmac.compare_digest does the constant-time comparison. The repeated hash here teaches the idea; for real use Python also offers hashlib.scrypt and hashlib.pbkdf2_hmac, and libraries for bcrypt and Argon2. The output is byte-for-byte the same as the C program’s.

"""Storing passwords: why a plain hash is not enough, what a salt adds, and what repeating the hash costs an attacker."""
import hashlib
import hmac

PASSWORD = "correct horse"
ALICE_SALT, BOB_SALT = "a1b2c3d4", "9f8e7d6c"
ROUNDS = 10000


def sha(data):
    return hashlib.sha256(data).digest()


def plain(password):
    return sha(password.encode())


def salted(salt, password):
    return sha(salt.encode() + password.encode())


def stretched(salt, password, rounds):
    h = salted(salt, password)
    for _ in range(rounds - 1):
        h = sha(h + password.encode())                   # (3) repeating makes each guess cost many hashes, for the attacker and for us
    return h


def show(label, digest):
    print(f"{label:<24}{digest.hex()[:16]}...")


show('sha256 of "password":', plain("password"))
show("alice, no salt:", plain(PASSWORD))
show("bob, no salt:", plain(PASSWORD))
print(f"same password, same stored hash: {plain(PASSWORD) == plain(PASSWORD)}")                                     # (1) without a salt, equal passwords give equal hashes
show("alice, salted:", salted(ALICE_SALT, PASSWORD))
show("bob, salted:", salted(BOB_SALT, PASSWORD))
print(f"same password, same stored hash: {salted(ALICE_SALT, PASSWORD) == salted(BOB_SALT, PASSWORD)}")            # (2) a salt makes every record unique, so a table of precomputed hashes is useless
stored = stretched(ALICE_SALT, PASSWORD, ROUNDS)
show(f"alice, salted, x{ROUNDS}:", stored)
for guess in (PASSWORD, "correct horsf"):
    ok = hmac.compare_digest(stretched(ALICE_SALT, guess, ROUNDS), stored)                                         # (4) compare in constant time so the comparison itself leaks nothing
    print(f'check "{guess}": {ok}')

Hashing protects a stolen file, but it cannot make a weak password strong. That is why systems also add a second factor (a phone, a hardware key), why password managers help people use long random passwords, and why newer designs (passkeys) avoid shared secrets altogether: there is nothing to steal from the server that can be replayed elsewhere.

Finding threats early

Most security failures were not unforeseeable. Someone could have asked, before building, what could go wrong here? Threat modeling is that question made systematic. A common four-step form:

  1. What are we building? List the parts and how data moves between them.
  2. What can go wrong? Go through each part and each flow with a checklist.
  3. What will we do about it? Remove the threat, reduce it, accept it or transfer it.
  4. Did we do a good enough job? Check the defenses against the threats, and repeat when the design changes.

The checklist for step 2 is often STRIDE: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service and Elevation of privilege. Each is the opposite of a security property: authenticity, integrity, non-repudiation, confidentiality, availability and authorization.

Try it: do the photo-sharing site first, then check your answers. Some threats fit two categories (a flood of failed logins can be a denial of service or an abuse of a defense). Pick the best fit, and read why the model answer chose it: the reasoning matters more than the letter.

AdvancedGoing deeper: how real attacks and defenses evolved
  • Return-oriented programming. When NX forbade running injected code, attackers began chaining short snippets of existing code (“gadgets”, each ending in a ret) by laying a list of addresses on the stack. No new code runs, so NX cannot object. This is the “reuse” target in the simulator.
  • Control-flow integrity and shadow stacks. Newer defenses check that a return goes where the matching call came from. Hardware shadow stacks keep a second, protected copy of return addresses, so overwriting the one on the stack is detected. Pointer authentication on Arm signs return addresses cryptographically.
  • Other memory bugs. Overflows on the heap, use-after-free, and integer overflows that make a length check pass wrongly are the same family. About two-thirds of serious vulnerabilities in large C and C++ code bases have been reported as memory-safety bugs, which is why Rust and other safe languages are being adopted for system software.
  • Fuzzing. Automated tools feed a program millions of mangled inputs and watch for crashes. Sanitizers (AddressSanitizer and others) turn silent overflows into immediate, reportable errors during testing.
  • Speculative execution. Spectre and Meltdown showed that a CPU’s speed tricks can leak data across the boundaries the operating system sets up, through timing alone. Fixes such as page-table isolation (Module 8) cost performance, a reminder that security is a trade-off.
  • Time-of-check to time-of-use (TOCTOU). A program checks that a file is safe and then opens it, but an attacker swaps it between the two steps. Like the race conditions of Module 6, the fix is to make check and use one atomic operation.
  • The confused deputy. A privileged program is tricked into using its authority on an attacker’s behalf. Capability systems avoid it by passing the authority explicitly with each request, rather than letting a program use whatever its identity allows.
  • Password storage in practice. The memory cost of scrypt and Argon2 defeats attackers who use GPUs, which have many cores but little memory each. A system-wide secret kept outside the database (a “pepper”) adds a further layer. Breach checking and rate limiting protect against stolen passwords being reused across sites.
