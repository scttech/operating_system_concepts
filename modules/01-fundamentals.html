OS Fundamentals & System Calls

An operating system sits between applications and hardware. It shares the machine fairly, hides hardware details behind clean abstractions, and protects programs from one another.

What an OS does

  • Resource manager: allocates CPU time, memory, storage and I/O devices among competing programs.
  • Abstraction layer: turns messy hardware into files, processes, sockets and virtual memory.
  • Protector: prevents one program (or user) from damaging another or the system.
  • Control program: supervises execution to prevent errors and improper use of the computer.

The kernel is the always-resident core that performs these jobs. Everything else (shells, compilers, browsers, even the GUI) is just a program that asks the kernel for help.

The kernel does not start itself. When the machine powers on, firmware runs a boot loader, a small program that finds the kernel on disk, loads it into memory and starts it. Module 4 follows the whole boot, step by step.

Kernel mode and user mode

The CPU has a mode bit. In user mode only a safe subset of instructions is allowed. In kernel mode every instruction and every memory address is available. Privileged instructions (changing page tables, disabling interrupts, talking to devices, halting the CPU) fault if tried in user mode. That hardware enforcement is what makes protection possible.

Key idea: a program can never simply “jump into the kernel”. The only ways in are hardware-controlled entry points: interrupts, exceptions and traps (system calls).

In every case the CPU saves enough state, switches to kernel mode, and jumps to a handler found in the interrupt vector. The timer interrupt is especially important: it lets the OS retake the CPU from a program that never gives it up.

System calls

A system call is the API through which programs request kernel services: files, processes, memory, networking. Programs normally call a library wrapper (like read() in libc) instead of issuing the trap themselves.

Try different system calls. The kernel-side work differs, but the mode switch, argument validation and return path are always the same. That fixed cost is why batching I/O (bigger reads and writes) is faster than many tiny calls.

// What a shell does to run "ls", in terms of system calls
pid = fork();          // create a child process
if (pid == 0) {
    execvp("ls", argv); // replace the child's program with ls
}
waitpid(pid, &status, 0); // parent waits for the child to finish

Try it: a system call versus a library call

Why C is the clearer version here: printf and write are exactly the two layers this lesson describes: a library function with a buffer, and a thin wrapper around the system call. Run it and you see the output order change, which is the buffer at work.

/* A system call versus a library call: why does "B" appear before "A"? */
#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <unistd.h>

int main(void) {
    printf("A");                            /* (1) printf only copies text into a buffer inside this process... */
    if (write(1, "B", 1) != 1) return 1;    /* (2) write() is the system call: the kernel receives "B" right away */
    printf("C\n");                          /* (3) ...and the buffer is written out later: when it is full, at a newline on a terminal, or at exit */
    return 0;                               /* (4) leaving main flushes the buffer, so "AC" is written only now */
}

Python behaves the same way, with different names. print() writes into a buffer owned by sys.stdout, and os.write() is the thin wrapper around the system call. The surprise is the same, but it is less visible in everyday Python because you rarely call os.write directly.

"""A system call versus a library call: why does "B" appear before "A"?"""
import os

print("A", end="")                # (1) print() only copies text into a buffer inside this process...
os.write(1, b"B")                 # (2) os.write() is the system call: the kernel receives "B" right away
print("C")                        # (3) ...and the buffer is written out later: when it is full, at a newline on a terminal, or at exit
# (4) when the program ends, Python flushes the buffer, so "AC" is written only now

Common confusion: the OS is not the shell, the GUI or the whole distribution. The kernel is the privileged core; the rest is user-space software.

Beyond the big three: phones, cars, single-board computers and mainframes make very different choices about these same ideas. See Module 18 to compare Android, iOS, Qubes OS, Raspberry Pi OS, real-time systems and IBM's z/OS, z/VSE and IBM i.

AdvancedGoing deeper: how a system call really enters the kernel
  • The trap instruction. On x86-64 the wrapper executes syscall; on ARM64 it is svc. The CPU switches to kernel mode and jumps to one address chosen by the OS at boot, not by the program. The call number goes in a register, and the kernel uses it to index a table of handlers.
  • Arguments are checked, never trusted. A pointer passed to the kernel could point at kernel memory. The kernel verifies that every user pointer lies in user space and copies data across the boundary (for example copy_from_user in Linux).
  • The vDSO. Some calls, such as reading the clock, are so frequent that Linux avoids the mode switch: the kernel maps a small page of code and data into every process, and clock_gettime runs entirely in user mode.
  • Monolithic versus micro kernels, in practice. A microkernel keeps drivers and file systems in user-mode servers, so one system call can become several messages. That costs speed but isolates faults. Hybrids such as Windows NT and macOS (XNU) put some of each in the kernel.
  • Hardware support goes further than two modes. x86 has four privilege rings (only 0 and 3 are commonly used), and virtualization adds a mode below the kernel for the hypervisor. ARM calls these exception levels, EL0 to EL3.
