Hands-on with Docker

Troubleshooting

Problems that come up often when running the Docker labs, and what to try. Each lab also has its own short troubleshooting list.

These notes describe the usual cause and the usual fix. Docker's messages change a little between versions, so match on the idea, not the exact words. If something here does not help, the official Docker documentation for your platform is the best next place to look.

Docker will not start or cannot be reached

“Cannot connect to the Docker daemon”, “error during connect”, or “Is the docker daemon running?”
The engine is not running. On Windows and macOS, open Docker Desktop and wait until it says it is running (the whale icon stops animating). On Linux, run sudo systemctl start docker. Then run docker version: you should see both a Client and a Server section.
“permission denied … /var/run/docker.sock” (Linux)
Your user is not allowed to talk to Docker. Either put sudo before each command, or add yourself to the docker group (see Docker's Linux post-install instructions) and log out and in again. Remember that membership in that group is close to administrator power on that computer.
“docker: command not found” or “'docker' is not recognized”
Close and reopen your terminal after installing Docker. On Windows, if it is still missing, check that Docker Desktop finished installing and started once.
WSL 2 messages on Windows (“WSL 2 installation is incomplete”, “WSL needs updating”)
Docker Desktop on Windows Home needs WSL2. Run wsl --update in PowerShell, restart Docker Desktop and, if asked, restart Windows. If Docker Desktop says virtualization is not enabled, it must be switched on in your computer's firmware (BIOS/UEFI) settings; look for “Virtualization Technology”, “Intel VT-x” or “SVM Mode”. In Docker Desktop's settings, “Use the WSL 2 based engine” is expected to be on, and it cannot be turned off on Windows Home.

Shell and quoting problems

A command with quotes works in bash but fails or behaves oddly in PowerShell
Windows PowerShell 5.1 (the one built into Windows) removes double quotes from arguments passed to programs such as docker, and PowerShell 7 handles them differently again. The labs avoid the problem: they put the whole command after sh -c in single quotes and use no double quotes inside. Copy the commands exactly, on one line. If you write your own, keep to the same rule, or run them from a WSL shell, where bash quoting applies.
Git Bash on Windows changes /sys/fs/cgroup into a Windows path
Git Bash rewrites arguments that look like Unix paths. Set MSYS_NO_PATHCONV=1 before the command (export MSYS_NO_PATHCONV=1), start the path with two slashes (//sys/fs/cgroup), or use PowerShell or WSL instead. The labs' commands put paths inside sh -c '…' so the host shell does not see them, but a path given directly to docker run can be rewritten.
Scripts fail with “^M” or “bad interpreter” errors
A script saved with Windows line endings (CRLF) cannot run on Linux. Files downloaded from these labs use Unix line endings (LF). If you edit one, save it with LF endings (most editors have an option in the status bar), and if you keep the files in Git add a .gitattributes line such as *.sh text eol=lf.
The cleanup command prints a usage message
When no container or image matches, docker rm and docker rmi are given no names and print how to use them. That means there was nothing to remove.

Downloads and disk space

Image downloads fail, hang or time out
Check your internet connection first. On a work or school network, Docker may need your proxy settings (Docker Desktop: Settings → Resources → Proxies). A toomanyrequests message means Docker Hub's limit on anonymous downloads was reached: wait, or log in with a free Docker account. The labs never require an account, but logging in raises the limit.
Package installs inside a container fail (apt, apk, dnf, pacman)
Same causes: no network from inside containers, a proxy, or a firewall. Try docker run --rm alpine:3.22 ping -c 1 8.8.8.8. If it fails, the container has no route out. Restarting Docker Desktop often fixes it.
“no space left on device”
docker system df shows what Docker is using. The cleanup commands remove everything from these labs. docker system prune removes all unused containers, networks and dangling images on your computer, not just lab ones, so read its warning before you agree. On Windows, Docker Desktop's virtual disk can stay large after cleanup until you use its “Clean / Purge data” or compact options.
The Docker virtual machine has too little memory or too few processors
On Windows and macOS, the Docker VM has its own size limits, which is why nproc and /proc/meminfo inside a container show less than your computer has. Docker Desktop's Settings → Resources changes them (on Windows with WSL2 it may be controlled by a .wslconfig file in your user folder).

Platform differences

“exec format error”, or “no matching manifest for linux/arm64/v8”
You are on an ARM64 computer (for example an Apple Silicon Mac) and an image is x86-64 only, or the other way round. Every image used in these labs publishes both, except the official Arch Linux image, which is x86-64 only (Lab 1 says to skip it on ARM64). Docker can run an x86-64 image on ARM64 with --platform linux/amd64, using emulation, but it is slow.
Different numbers from the example output
Expected. Versions, sizes, times, PIDs and addresses all vary. Look for the same pattern, such as “the kernel versions match” or “the wall-clock time doubles”.
cgroup files are missing or named differently
Linux has two generations of control groups. v1 keeps separate folders such as /sys/fs/cgroup/memory/; v2 uses one tree with files such as /sys/fs/cgroup/memory.max. The labs use commands that try both. docker info --format '{{.CgroupVersion}}' tells you which one you have.
Something works on Linux but not on Windows or macOS (or the reverse)
Remember the hidden virtual machine: on Windows and macOS the “host” in a lab is Docker's Linux VM, not your real computer. Commands that look at the host, such as --pid=host, see the VM.

Leftover containers and name clashes

“The container name … is already in use”
A container from an earlier attempt still exists. Remove it by name (docker rm -f oslab-02-sleeper), or remove everything from the guide with the cleanup commands.
A container is still running and using resources
docker ps lists running containers. docker rm -f NAME stops and removes one.
A command seems to hang
Press Ctrl+C. If the prompt does not return, open a second terminal and run docker rm -f NAME for the container you started.
