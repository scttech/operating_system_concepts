Booting a different kernel

Every earlier lab shared one kernel. Here you start a second kernel for real: xv6, a small teaching operating system from MIT, running on an emulated RISC-V computer inside a container. Then you read its source and change it.

About 45 minutesIntermediateRelated: Module 19 Virtualization & Containers, Module 4 Boot Process, Module 1 OS Fundamentals

Concept link: Module 19 separates containers from virtual machines and emulators; this lab is the “emulator” case, and Module 4 describes what a kernel does when it starts.

What you will learn

  • Say precisely how an emulator differs from a container: it provides a pretend computer, so it can run a different kernel and even a different processor design.
  • Build and boot xv6 (a RISC-V teaching kernel of about 6,000 lines of C) under QEMU, and use its tiny shell.
  • Explain why this is slow without hardware help (no KVM), and why that does not matter for learning.
  • Find the boot message and the system-call list in the source, then change the message, add a program and rebuild.

Before you start

  • Prerequisites: Lab 0. Lab 5 is helpful background for the system-call step.
  • Disk and time: the first build downloads about 1 GB of tools and takes 3 to 5 minutes. The image is about 1 GB on disk. The clean-up removes it.
  • Make an empty folder for this lab (for example oslab-07) and open your terminal in it. You will download four small files into it.
  • You need internet access during the build: it downloads the xv6 source from GitHub. The lab pins one exact version, so what you build matches this page.

Platform notes. No KVM. Nothing here uses KVM (the Linux feature that lets a virtual machine run at full speed). On Windows Home with WSL2 and on many Macs it is not available inside containers, so QEMU emulates every instruction in software. xv6 is small enough that it still boots in a second or two. Works on x86-64 and ARM64: the guest is always RISC-V, so the same page works on both, and the example output comes from an x86-64 machine. Exit key: in the interactive session, press Ctrl+A, release, then press X to stop QEMU. Not tested on macOS or ARM64.

Steps

  1. Build the xv6 image

    Download these two files into your lab folder first. The Dockerfile installs a cross compiler (a compiler that runs on your computer but makes programs for a RISC-V processor), the QEMU emulator and make, downloads one pinned version of xv6 and builds it. run-xv6.sh is a small helper that boots xv6 without a keyboard, so the examples can be repeated exactly.

    # Debian with a RISC-V cross compiler and the QEMU emulator, plus one pinned copy of xv6, built once.
FROM debian:13-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends git make bc gcc libc6-dev gcc-riscv64-unknown-elf qemu-system-misc ca-certificates \
 && rm -rf /var/lib/apt/lists/*
RUN git clone -q https://github.com/mit-pdos/xv6-riscv.git /xv6 \
 && git -C /xv6 checkout -q fa2ddcb7ca87a77af579380a6eafd5aff163b44f
WORKDIR /xv6
RUN make kernel/kernel fs.img
COPY --chmod=755 run-xv6.sh /usr/local/bin/run-xv6.sh
CMD ["make", "qemu", "CPUS=1"]
    #!/bin/sh
# Boot xv6 without a keyboard: type each command in $XV6_CMDS (separated by semicolons), then quit QEMU.
cd /xv6 || exit 1
{
  sleep 4
  echo "$XV6_CMDS" | tr ';' '\n' | while read -r line; do echo "$line"; sleep 2; done
  printf '\001x'
} | make qemu CPUS=1

    Also download Dockerfile.mine and hello.c now, so the folder is complete (they are explained in step 7). Then build:

    docker build -q --label oslab=true -t oslab-07-xv6 .

    Example output (be patient: several minutes the first time):

    sha256:dadd50223420d1b617fe703b00d40fbdc83c4a1a604e41a295e3b9e7ab204f75

    Why this matters: xv6 is built for a processor that is not yours. gcc-riscv64-unknown-elf is a compiler whose output is RISC-V machine code, and the kernel it makes cannot run on an x86-64 or Arm processor directly. A second, ordinary gcc is there only to build one helper that makes the xv6 disk image. The version is pinned by its commit ID, so everyone builds the same code.

  2. Two different machines in one image

    The container itself runs on your computer's processor, under Docker's Linux kernel. Ask it what that is. Then ask what kind of program the xv6 kernel is:

    docker run --rm --label oslab=true oslab-07-xv6 uname -m
docker run --rm --label oslab=true oslab-07-xv6 riscv64-unknown-elf-objdump -f kernel/kernel

    Example output (the first line is aarch64 on an ARM64 computer):

    x86_64

kernel/kernel:     file format elf64-littleriscv
architecture: riscv:rv64, flags 0x00000112:
EXEC_P, HAS_SYMS, D_PAGED

    Why this matters: the container's processor is x86_64, but the kernel file is riscv:rv64, a different instruction set. A container could never run it: a container shares the host's kernel and runs programs for the host's processor. To run xv6 you need something that pretends to be a RISC-V computer (memory, a disk, a serial port, a processor) and then runs a real boot on it. That something is QEMU.

  3. Boot xv6

    Start it yourself first. -it connects your keyboard and screen to the container, and the image's default command is make qemu, which starts QEMU with the kernel and a virtual disk. Try a few commands (ls, echo hello), then press Ctrl+A, release, and press X to quit.

    docker run -it --rm --label oslab=true oslab-07-xv6

    The same boot, typed for you, so the output can be shown exactly. The -e option sets an environment variable: here, the list of commands, separated by semicolons:

    docker run --rm --label oslab=true -e 'XV6_CMDS=ls' oslab-07-xv6 run-xv6.sh

    Example output (shortened; QEMU: Terminated at the end is the exit key):

    qemu-system-riscv64 -machine virt -bios none -kernel kernel/kernel -m 128M -smp 1 -nographic -global virtio-mmio.force-legacy=false -drive file=fs.img,if=none,format=raw,id=x0 -device virtio-blk-device,drive=x0,bus=virtio-mmio-bus.0

xv6 kernel is booting

init: starting sh
$ ls
.              1 1 1024
..             1 1 1024
README         2 2 2441
cat            2 3 36760
echo           2 4 35592
…
sh             2 13 58608
…
console        3 23 0
$ QEMU: Terminated

    Why this matters: read the first line: it is the QEMU command, and its options describe the pretend computer: a virt machine, 128 MB of memory (-m 128M), one processor (-smp 1), a virtual disk (fs.img), and a serial console in place of a screen (-nographic). The kernel starts and prints xv6 kernel is booting. It then starts init, the first process (Lab 6), which starts a shell, sh, whose prompt is $. That is the whole boot: a kernel, a first process and a shell. It is the sequence Module 4 describes, on a very small system. Unlike every earlier lab, this kernel is not the Linux kernel of Docker's virtual machine.

  4. Use it: a different operating system

    xv6 looks like Unix but is far smaller. Run a few commands: echo prints its arguments, wc README counts lines, words and bytes, and a pipe (|) sends one program's output into another.

    docker run --rm --label oslab=true -e 'XV6_CMDS=echo hello from xv6;wc README;ls | grep sh' oslab-07-xv6 run-xv6.sh

    Example output (without the first lines you saw in step 3):

    $ echo hello from xv6
hello from xv6
$ wc README
48 336 2441 README
$ ls | grep sh
sh             2 13 58608
$ QEMU: Terminated

    Why this matters: everything you just ran, the shell, echo, wc, ls, grep, is a user program that xv6 loaded from its own disk image and ran on its own kernel, using xv6's own system calls. None of it is Linux. The pipe worked because xv6 has the same pipe, fork and exec system calls you met in Lab 5. xv6 has no uname, no network and no users: a minimal system that still has processes, memory management, a file system and a shell.

  5. Why is it slow without KVM?

    Ask QEMU which accelerators (ways of running the guest's instructions) it can use inside this container:

    docker run --rm --label oslab=true oslab-07-xv6 qemu-system-riscv64 -accel help

    Example output:

    Accelerators supported in QEMU binary:
tcg

    Why this matters: tcg is QEMU's Tiny Code Generator: it reads RISC-V instructions one block at a time and translates them into instructions your processor understands, then runs those. That is pure software, so every guest instruction costs many host instructions. A faster accelerator, KVM (or Apple's and Microsoft's equivalents), lets the guest's instructions run directly on the real processor, but it works only if the guest and the host processor are the same kind, and a RISC-V guest on an x86-64 or Arm computer never qualifies. So a RISC-V guest is always emulated, and that is why this lab uses a very small kernel. Contrast a container: it runs at full speed because it never pretends to be a computer at all.

  6. Read the source

    The source is in the image. Find the line that printed the boot message, count the lines of kernel code, and list the first system calls:

    docker run --rm --label oslab=true oslab-07-xv6 sh -c 'grep -n booting kernel/main.c; wc -l kernel/*.c kernel/*.h | tail -n 1; grep -n define.SYS_ kernel/syscall.h | head -n 6'

    Example output:

    17:    printk("xv6 kernel is booting\n");
 6334 total
2:#define SYS_fork   1
3:#define SYS_exit   2
4:#define SYS_wait   3
5:#define SYS_pipe   4
6:#define SYS_read   5
7:#define SYS_kill   6

    Why this matters: the entire kernel, the part that does scheduling, memory management, the file system, the system calls and the drivers, is about 6,300 lines in kernel/*.c and kernel/*.h. You can read all of it. The message came from kernel/main.c, the file where the boot code starts. The system-call numbers live in kernel/syscall.h; xv6 defines 22 of them (fork, exit, wait, pipe, read and so on). Linux defines hundreds. Good places to start reading: kernel/proc.c (processes and the scheduler), kernel/vm.c (page tables) and kernel/syscall.c (how a system call reaches its code).

  7. Change the kernel and add a program

    Make your own xv6. hello.c is a new user program; Dockerfile.mine starts from the image you built, changes the boot message in kernel/main.c with sed (a text-replacing tool), adds the program to the list of programs on the disk (UPROGS in the Makefile) and rebuilds.

    #include "kernel/types.h"
#include "kernel/stat.h"
#include "user/user.h"

int
main(void)
{
  printf("Hello from a program I added to xv6!\n");
  exit(0);
}
    # Your own xv6: a changed boot message and one new program, rebuilt on top of the first image.
FROM oslab-07-xv6
COPY hello.c user/hello.c
RUN sed -i 's/xv6 kernel is booting/my own kernel is booting/' kernel/main.c \
 && sed -i 's|^UPROGS=|UPROGS=$U/_hello |' Makefile \
 && make kernel/kernel fs.img
    docker build -q --label oslab=true -f Dockerfile.mine -t oslab-07-mine .

    Boot it and run your new program:

    docker run --rm --label oslab=true -e 'XV6_CMDS=hello' oslab-07-mine run-xv6.sh

    Example output:

    qemu-system-riscv64 -machine virt -bios none -kernel kernel/kernel -m 128M -smp 1 -nographic -global virtio-mmio.force-legacy=false -drive file=fs.img,if=none,format=raw,id=x0 -device virtio-blk-device,drive=x0,bus=virtio-mmio-bus.0

my own kernel is booting

init: starting sh
$ hello
Hello from a program I added to xv6!
$ QEMU: Terminated

    Why this matters: you changed a kernel and ran it. Two lines of change in a build recipe gave you your own boot message, and the new program, compiled by the RISC-V cross compiler, was written onto xv6's virtual disk and found by its shell. This is how operating-system courses work: the kernel is small enough to modify, and a failed experiment costs only a rebuild, because a bug in your kernel cannot harm your computer. It can only crash the pretend computer.

Try it yourself

  1. Change the boot message to your own name, and add a second program that prints the numbers 1 to 5. (Write the C, add it to UPROGS the same way, rebuild.) Remember to give the new image a different name, such as oslab-07-mine2, and remove it afterwards.
  2. Read kernel/syscall.c in the image (docker run --rm --label oslab=true oslab-07-xv6 sh -c 'sed -n 1,40p kernel/syscall.c'). Find the table that maps system-call numbers to functions. How is it like the numbered calls you saw in Lab 5?
  3. Run the interactive session again and try usertests or forktest. Slower, longer-running tests show the cost of emulation. (Quit with Ctrl+A, X.)

Clean up

Remove the two images, then check that nothing from this lab remains. The last command lists any oslab containers and should print only its header line.

docker rmi oslab-07-mine oslab-07-xv6
docker ps -a --filter label=oslab=true

The shared debian:13-slim base image stays on your computer; clean up everything removes it. If you built extra images in the exercises, remove them with docker rmi NAME.

Troubleshooting

  • The build fails while downloading packages or from GitHub: check your internet connection and any proxy or firewall; the build needs deb.debian.org and github.com. Then run the same docker build again.
  • “no space left on device” during the build: the image needs about 1 GB plus working space. See docker system df and the troubleshooting page.
  • The interactive session seems frozen: xv6 prints nothing until you press Enter at the $ prompt. To stop it, use Ctrl+A, release, then X. If that fails, run docker rm -f NAME from a second terminal (find the name with docker ps).
  • The scripted run shows the commands but no output for them: the helper types a command two seconds apart and waits four seconds for the first boot. A very slow computer may need more; copy run-xv6.sh, increase the sleep numbers, and rebuild.
  • The pinned version no longer downloads: the Dockerfile fetches one exact commit from the xv6 repository. If that repository were ever deleted or rewritten, the step would fail; use a current commit ID from github.com/mit-pdos/xv6-riscv and expect small differences in the output.
  • See the troubleshooting page for other problems.

Key takeaways

  • A container shares its host's kernel and processor type. An emulator such as QEMU pretends to be a whole computer, so it can run a different kernel on a different processor design, such as RISC-V.
  • Without hardware help (KVM) QEMU translates every guest instruction in software, which is slow; a RISC-V guest on an x86-64 or Arm computer can never use that help.
  • A small kernel such as xv6 shows the whole shape of an operating system (boot, first process, shell, system calls) in a few thousand lines you can read, change and rebuild safely.
