Hands-on with Docker · Lab 8

Exploring other operating systems

A capstone. Every lab so far used Linux, or xv6 (a teaching kernel). Here you boot a third, a complete, real, independently designed system, OpenBSD, and compare it with Linux using the same commands. Then you fill in a worksheet you can reuse on any other system.

About 40 minutesIntermediateRelated: Module 19 Virtualization & Containers, Module 4 Boot Process, Module 1 OS Fundamentals

Concept link: Module 1 describes what every operating system provides and how kernels are structured; Module 19 explains the emulation used to run a different one.

What you will learn

  • Boot a real BSD system headless (with no screen, only a text console) under QEMU, and recognise the same boot sequence you saw in Lab 7.
  • Tell two Unix-family systems apart using commands, and say which differences are design choices (names, numbers, where information lives) and which are shared ideas (files, devices, a shell, a root file system).
  • Read an honest feasibility list of other systems, and know why a few are not given a recipe here.
  • Use a worksheet to study any operating system: its process model, memory management, file system, boot and what surprised you.

Before you start

  • Prerequisites: Lab 0. Lab 7 is strongly recommended: it explains why QEMU is needed and why it is slow without KVM.
  • Disk and time: the build downloads about 300 MB of tools plus a 6 MB OpenBSD image, and takes 2 to 4 minutes the first time. Each boot takes roughly half a minute. The clean-up removes everything.
  • Make an empty folder for this lab (for example oslab-08) and open your terminal in it. You will download two small files into it.
  • You need internet access during the build (Debian packages and cdn.openbsd.org).

Platform notes. No KVM. As in Lab 7, nothing here uses KVM; QEMU translates every instruction in software. The guest is an x86-64 PC, and the lab pins one OpenBSD image, so the output matches the page. On an ARM64 computer (Apple silicon, Windows on Arm) the guest is still an x86-64 PC and QEMU emulates it more slowly; allow a few minutes per boot. Not tested on macOS or ARM64; tested on Windows 11 with Docker Desktop (WSL2) on x86-64. Exit key: in the interactive session, press Ctrl+A, release, then X.

Steps

  1. Build the OpenBSD image

    Download these two files into your lab folder. The Dockerfile installs QEMU for a PC, downloads one pinned install image (a small disk image that contains a complete mini OpenBSD, used to install the full system) and checks it against its published SHA-256 sum, so you know it is the file intended. run-openbsd.exp is a helper written for expect, a tool that types into a program and waits for replies. It boots the image over a serial console, picks the installer's shell, and either types your commands or gives you the keyboard.

    # Debian with the QEMU emulator (for a PC) and one pinned OpenBSD install image, checked against its published SHA-256 sum.
FROM debian:13-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends qemu-system-x86 expect curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*
WORKDIR /os
RUN curl -4 -fsSL -o miniroot80.img https://cdn.openbsd.org/pub/OpenBSD/8.0/amd64/miniroot80.img \
 && echo 'fe268f373dacf249b36306096404aa578e0ceb950d08c19c5a1117806997399a  miniroot80.img' | sha256sum -c -
COPY --chmod=755 run-openbsd.exp /usr/local/bin/run-openbsd
CMD ["run-openbsd"]
    #!/usr/bin/expect -f
# Boot the OpenBSD install image on an emulated PC, with the serial port as the console.
# Choose the installer's shell, then either type each command in $OBSD_CMDS (separated by
# semicolons) and quit, or, if it is not set, hand the keyboard to you.
set timeout 300
log_user 0
spawn qemu-system-x86_64 -machine pc -m 512 -nographic -accel tcg -nic none \
  -drive file=/os/miniroot80.img,format=raw,snapshot=on
expect "boot> "
send "set tty com0\r"
expect "boot> "
send "boot\r"
expect "(I)nstall, (U)pgrade, (A)utoinstall or (S)hell? "
send "s\r"
expect "# "
if {![info exists env(OBSD_CMDS)]} {
  puts "\nYou are in the OpenBSD installer's shell. Quit with Ctrl-A, then X.\n"
  send "\r"
  interact
  exit 0
}
puts -nonewline "# "
foreach c [split $env(OBSD_CMDS) ";"] {
  send "[string trim $c]\r"
  expect "# "
  puts -nonewline [string map [list "\r" ""] $expect_out(buffer)]
}
send "\001x"
expect eof
puts ""
    docker build -q --label oslab=true -t oslab-08-openbsd .

    Example output:

    sha256:06857846b58bf0fc5dc832d92405b03d61518d6166ff904d13c1d5b6a849869f

    Why this matters: the line that downloads the image also verifies it. If the file were damaged or swapped on the way, sha256sum -c would fail and the build would stop. Checking a download against a known sum before running it is a good habit with any operating-system image. The helper script is also instructive: a PC starts with a program called a boot loader that asks which kernel to start (the boot> prompt). Telling it set tty com0 sends the console to the serial port instead of a screen, which is what lets this system run with no display.

  2. Boot it and read its boot messages

    Start it yourself first (-it connects your keyboard). With no commands given, the helper hands you the keyboard once the installer's shell appears. Try a few commands, then press Ctrl+A, release, and press X to quit. Nothing you do is saved.

    docker run -it --rm --label oslab=true oslab-08-openbsd

    The same boot, typed for you. dmesg prints the messages the kernel wrote while it started:

    docker run --rm --label oslab=true -e 'OBSD_CMDS=dmesg' oslab-08-openbsd run-openbsd

    Example output (shortened to the lines that matter; the full output is about 60 lines):

    # dmesg
OpenBSD 8.0 (RAMDISK_CD) #79: Tue Oct  6 23:24:34 MDT 2026
    deraadt@amd64.openbsd.org:/usr/src/sys/arch/amd64/compile/RAMDISK_CD
real mem = 519962624 (495MB)
…
bios0: QEMU Standard PC (i440FX + PIIX, 1996)
cpu0 at mainbus0: apid 0 (boot processor)
cpu0: QEMU Virtual CPU version 2.5+, 2905.82 MHz, 0f-6b-01
…
com0 at acpi0 COM1 addr 0x3f8/0x8 irq 4: ns16550a, 16 byte fifo
com0: console
…
wd0 at pciide0 channel 0 drive 0: <QEMU HARDDISK>
…
root on rd0a swap on rd0b dump on rd0b
#

    Why this matters: this is the boot sequence from Module 4, written by the kernel itself. It found a (pretend) PC from QEMU's BIOS, found the processor, cpu0, found the serial port com0 and chose it as the console, found a disk, wd0, and finally mounted its root file system on a RAM disk (rd0a, a disk that lives in memory) because this is an installer. Every operating system does these jobs in some order. Only the names are OpenBSD's: devices are named for their driver (wd for an IDE disk, com for a serial port), where Linux names them by kind (sda).

  3. Two kernels, one question: who are you?

    Ask the Linux kernel your containers use, then the OpenBSD kernel in the emulated machine. sysctl reads settings and facts from the kernel; the installer's version is cut down and answers only a few names, which is enough here.

    docker run --rm --label oslab=true oslab-08-openbsd uname -sr
docker run --rm --label oslab=true -e 'OBSD_CMDS=sysctl -n kern.osrelease;sysctl hw.machine;sysctl hw.model' oslab-08-openbsd run-openbsd

    Example output (the Linux version on your computer will differ):

    Linux 5.15.146.1-microsoft-standard-WSL2
# sysctl -n kern.osrelease
8.0
# sysctl hw.machine
hw.machine=amd64
# sysctl hw.model
hw.model=QEMU Virtual CPU version 2.5+

    Why this matters: the first command is the one that ran on the Docker kernel that every earlier lab shared. The others ran on a completely different kernel, with its own version number, on a processor that is a pretend one (QEMU Virtual CPU). Notice what you are not doing: you are not running a Linux program on OpenBSD. The two kernels do not share anything. The different tool names (uname on Linux, sysctl here) are the first sign that even closely related systems make different choices.

  4. Where does the system keep its information?

    On Linux, /proc is a window into the kernel (Lab 4 used it). Look for the same thing on OpenBSD:

    docker run --rm --label oslab=true oslab-08-openbsd ls -d /proc/1 /proc/cpuinfo
docker run --rm --label oslab=true -e 'OBSD_CMDS=ls /proc' oslab-08-openbsd run-openbsd

    Example output:

    /proc/1
/proc/cpuinfo
# ls /proc
ls: /proc: No such file or directory

    Why this matters: Linux decided that the kernel should publish its internals as files; OpenBSD decided that they belong behind a system call (sysctl), so there is no /proc at all. Both are valid designs of the same idea: a program needs some way to ask the kernel about processes and hardware. “Everything is a file” is a Linux and Plan 9 emphasis, not a law of all Unix systems. When you move to a new system, the question to ask is not “where is /proc?” but “how does this system let me ask the kernel?”.

  5. What tools come with it?

    The installer is a very small system, so its tool list is short enough to read in full. List its two main program folders:

    docker run --rm --label oslab=true -e 'OBSD_CMDS=ls /bin;ls /sbin' oslab-08-openbsd run-openbsd

    Example output:

    # ls /bin
arch     chmod    dd       eject    ln       mt       rm       sha512   sync
cat      cp       df       hostname ls       mv       sh       sleep    tar
chgrp    date     ed       ksh      mkdir    pax      sha256   stty
# ls /sbin
bioctl       fsck         init         mount_ffs    ping         slaacd
chown        fsck_ffs     kbd          mount_msdos  ping6        sysctl
dhcpleased   fsck_msdos   mknod        mount_nfs    reboot       umount
disklabel    growfs       mount        mount_udf    resolvd
dmesg        halt         mount_cd9660 newfs        restore
fdisk        ifconfig     mount_ext2fs newfs_msdos  route
#

    Why this matters: this is a system with a shell (sh, ksh), file tools (cp, mv, ls), init (the first process, as in Lab 6), a file-system checker (fsck), partitioning tools (fdisk, disklabel) and tools for several other file-system types (mount_msdos, mount_ext2fs, mount_udf, mount_nfs). It has no ps, no uname and no head: an installer needs only enough to partition a disk and copy files. The split between /bin (needed by everyone) and /sbin (system administration) is a shared Unix tradition.

  6. Devices and file systems

    Compare how the two systems describe a mounted file system and a device file (a file name that stands for a device). ls -l on a device shows two numbers, the major and minor device numbers, where a file normally shows its size:

    docker run --rm --label oslab=true -e 'OBSD_CMDS=mount;ls -l /dev/null /dev/rd0a' oslab-08-openbsd run-openbsd
docker run --rm --label oslab=true oslab-08-openbsd ls -l /dev/null

    Example output (dates will differ):

    # mount
/dev/rd0a on / type ffs (local)
# ls -l /dev/null /dev/rd0a
crw-rw-rw-  1 root  wheel      2, 2 Nov 18 22:38 /dev/null
brw-r-----  1 root  operator  17, 0 Oct  7 05:24 /dev/rd0a
#
crw-rw-rw- 1 root root 1, 3 Nov 18 22:38 /dev/null

    Why this matters: the same /dev/null, the “discard everything” device, exists on both systems and starts with c (a character device, which handles a stream of bytes). But its numbers are 2, 2 on OpenBSD and 1, 3 on Linux. A major number picks the driver, a minor number picks the instance, and each kernel numbers its drivers in its own way. The disk /dev/rd0a starts with b, a block device (data in fixed-size blocks). The root file system type is ffs, the Fast File System that BSD pioneered and that many later systems learned from (Module 16), where Linux containers show overlay (Lab 4).

  7. The installer is a shell script

    Look at the installer that normally runs when you choose “Install”. It is a file in the root directory:

    docker run --rm --label oslab=true -e 'OBSD_CMDS=ls -l /install;grep -c . /install.sub' oslab-08-openbsd run-openbsd

    Example output:

    # ls -l /install
lrwxr-xr-x  1 root  wheel  11 Oct  7 05:24 /install -> install.sub
# grep -c . /install.sub
2409
#

    Why this matters: /install is a symbolic link (Lab 4) to install.sub, a script of 2,409 non-blank lines for the very shell you are typing into. The program that installs the whole operating system is not a special tool but ordinary shell commands calling fdisk, newfs and mount. You can read it in the interactive session with more /install.sub. That is a lesson about operating systems in general: most of what “installing” means is the simple tools you have already met, partition a disk, make a file system, copy files and make the disk bootable.

Try it yourself

  1. Start the interactive session (docker run -it --rm --label oslab=true oslab-08-openbsd) and read /install.sub with more. Find where it calls fdisk and newfs. Which steps match what Module 16 says a file system needs?
  2. Run ifconfig in the guest. Which network devices does it show, and why is there no real network? (Look at the -nic none option in the helper script.)
  3. Pick another system from the table and, if you can reach its download, try to boot it the same way. Use the worksheet below. If you succeed, you have a recipe worth adding.

Worksheet: study any operating system

Pick one system (OpenBSD, xv6, or another you can boot) and answer these questions in your own words. The hints show where to look in OpenBSD. Keep your answers: comparing two systems side by side is where the learning happens.

  1. Process model. How is the first process started? How does a program create another (is there a fork)? How are processes listed? Hints: /sbin/init, Lab 6; this installer has no ps.
  2. Memory management. How much memory does the kernel see, and does it report paging or swap? Hints: dmesg shows real mem, avail mem and a swap device (rd0b).
  3. File systems. What is the root file system's type, and which others can it mount? How are devices named and numbered? Hints: step 6, /sbin/mount_*.
  4. Init and boot. What runs between power-on and a shell? Where does the console go? Hints: step 2, the boot> prompt and com0.
  5. System interface. How does a program ask the kernel for information (/proc, sysctl, something else)? Hints: steps 3 and 4.
  6. Kernel structure. Is it monolithic (one big program with drivers inside), a microkernel (drivers outside), or something else? Hint: OpenBSD's drivers appear in the kernel's own boot messages, so it is monolithic.
  7. What surprised you? Name one thing that works differently from Linux and say why you think the designers chose it.

Check your understanding

Clean up

Remove the image, then check that nothing from this lab remains. The last command lists any oslab containers and should print only its header line.

docker rmi oslab-08-openbsd
docker ps -a --filter label=oslab=true

The shared debian:13-slim base image stays on your computer; clean up everything removes it.

Troubleshooting

  • The build cannot download the OpenBSD image: check your internet connection and any proxy or firewall for cdn.openbsd.org. The build forces IPv4 (curl -4) because some networks stall on IPv6; if your network is IPv6-only, remove the -4.
  • The build says the checksum failed: the download was damaged or the file changed. Run the build again. If it still fails, do not use the image.
  • The pinned version no longer downloads: OpenBSD moves older releases off its main mirror after a time. Use archive.openbsd.org in the URL, or a newer release (change 8.0 and 80 in the Dockerfile and the helper, and take the new SHA-256 from the SHA256 file in the same folder). Expect small differences in the output.
  • The scripted run prints nothing, or stops early: a very slow computer may exceed the helper's five-minute wait. Increase set timeout 300 in the helper and rebuild.
  • You are stuck in the interactive session: press Ctrl+A, release, then X. If that fails, run docker rm -f NAME from a second terminal (find the name with docker ps).
  • See the troubleshooting page for other problems.

Key takeaways

  • A different operating system is a different kernel with its own design choices: names, numbers, tools and ways of exposing information, even when the big ideas (processes, files, devices, a boot sequence) are shared.
  • QEMU can run a whole PC with no screen if the console is a serial port, which makes complete systems scriptable and repeatable.
  • Compare systems by asking the same questions (process model, memory, file systems, boot, kernel structure), not by looking for the same file names.
  • Say what you could and could not verify. A recipe is only worth following if someone has run it.
