Processes and namespaces

A container is not a machine: it is ordinary processes that the kernel has given a restricted view of the system. See that view from inside and outside, and build a piece of it yourself.

About 40 minutesIntermediateRelated: Module 5 Processes, Module 19 Virtualization & Containers

Concept link: Module 5 explains what a process is and how fork creates one; the containers section of Module 19 introduces namespaces and control groups. This lab lets you see them on a real kernel.

What you will learn

  • Read a container's process list from inside it, from outside it (docker top) and from the host's point of view (--pid=host).
  • Explain why the first process of a container is PID 1, and why that is special.
  • Create a PID namespace by hand with unshare, and read a process's different PIDs from /proc.
  • Meet the other namespaces (host name, network, mounts) with one small experiment each.

Before you start

  • Prerequisites: Lab 0.
  • Everything runs inside containers, so the commands are the same in bash, zsh and PowerShell.

Platform notes. On Windows and macOS, the “host” in this lab means Docker Desktop's hidden Linux virtual machine, not Windows or macOS. On Linux it is your real computer. On a Linux host you may see more processes and different names than the examples. The examples were captured on Windows 11 Home with Docker Desktop (WSL2), x86-64. Not tested on macOS or ARM64.

Two commands in this lab loosen the container's isolation, on purpose. --pid=host lets a container see the host's processes, and --cap-add=SYS_ADMIN lets it create namespaces. Both are used in throwaway containers, with --rm or removed at the end, and neither touches your files. Never use them with software you do not trust.

Steps

  1. List the processes inside a container

    ps lists processes. Alpine's ps comes from BusyBox, so it exists even in this tiny image.

    docker run --rm --label oslab=true alpine:3.22 ps

    Example output:

    PID   USER     TIME  COMMAND
    1 root      0:00 ps

    Why this matters: on a normal computer ps would list dozens of processes. Here there is exactly one, and it is ps itself, as PID 1 (process ID 1). The container's first process is simply the command you started it with. The container has its own PID namespace: its own private numbering of processes, in which it cannot see anyone else.

  2. Start a long-running container to look at

    Start a container that just sleeps for ten minutes, so there is something to inspect. (-d runs it in the background; the name oslab-02-sleeper follows the guide's naming rule.)

    docker run -d --name oslab-02-sleeper --label oslab=true alpine:3.22 sleep 600

    Now run ps inside it with docker exec, and ask the kernel which program PID 1 really is: /proc/1/exe is a link to the executable file of process 1.

    docker exec oslab-02-sleeper ps
docker exec oslab-02-sleeper ls -l /proc/1/exe

    Example output:

    PID   USER     TIME  COMMAND
    1 root      0:00 sleep 600
    7 root      0:00 ps
lrwxrwxrwx    1 root     root             0 Nov 18 16:08 /proc/1/exe -> /bin/busybox

    Why this matters: PID 1 is the sleep 600 you asked for (it is run by BusyBox). The ps you ran with exec is a second process added to the same container, with the next free number. There is no separate operating system here, just your command and anything it starts.

  3. See the same process from outside

    docker top lists a container's processes as seen by the engine, from outside the container.

    docker top oslab-02-sleeper

    Example output (your PID will be a different big number):

    UID                 PID                 PPID                C                   STIME               TTY                 TIME                CMD
root                22149               22128               2                   16:08               ?                   00:00:00            sleep 600

    Why this matters: the same sleep process is PID 1 inside the container and PID 22149 outside. It is one process with two numbers, because the kernel keeps a separate PID numbering for each namespace. This is the core trick of containers: the kernel shows each group of processes its own version of the system.

  4. See the host's processes (read-only peek)

    --pid=host tells Docker not to give this container its own PID namespace, so it sees the host's. We only list the first lines (head -n 8) and do not touch anything.

    docker run --rm --label oslab=true --pid=host alpine:3.22 sh -c 'ps | head -n 8'

    Example output (Docker Desktop's virtual machine; a Linux computer shows its own, such as systemd):

    PID   USER     TIME  COMMAND
    1 root      0:01 /initd
   24 root      0:35 /initd services
   46 root      0:00 /bin/sh /usr/bin/rungetty.sh
   47 root      0:00 /bin/login -f
   53 root      0:00 -bash
   83 100       0:00 /sbin/rpcbind -f
   84 root      0:00 /sbin/rpc.statd -d -F

    Why this matters: this is the other side of the mirror. Without its own namespace the container sees everything running on the host (here Docker Desktop's Linux VM: its init program, /initd, is PID 1). Isolation is not a wall around the container, it is a pair of glasses the kernel puts on it, and --pid=host takes them off.

  5. Why PID 1 is special

    In Linux, PID 1 is the init process: the ancestor of all others. The kernel gives it two special duties and one special protection: it adopts orphans (processes whose parent died), it is expected to collect (“reap”) finished children, and signals sent to it are ignored unless the program has asked to handle them. The program you start in a container is PID 1 of that container, so it inherits these duties whether it expects them or not. Module 5 describes parents and children; a later lab in this guide (Lab 6) returns to what goes wrong when PID 1 is not ready for the job.

  6. Build a PID namespace by hand

    Docker did that for you, but you can do it yourself with the unshare command, which runs a program inside new namespaces. First try it without any extra permission. This is expected to fail:

    docker run --rm --label oslab=true alpine:3.22 unshare --pid --fork sleep 1

    Example output:

    unshare: unshare(0x20020000): Operation not permitted

    Creating a namespace is a privileged operation, and Docker's default security settings block it. The narrowest permission that allows it is the Linux capability SYS_ADMIN. --cap-add=SYS_ADMIN gives this one container that one capability (it is much narrower than --privileged, which we never use). --pid asks for a new PID namespace and --fork starts the command as the first process in it.

    docker run -d --name oslab-02-ns --label oslab=true --cap-add=SYS_ADMIN alpine:3.22 sh -c 'unshare --pid --fork sleep 300'

    Now list that container's processes, and ask the kernel for every PID each one has. NSpid in /proc/PID/status lists a process's PID in each namespace it belongs to, outermost first.

    docker exec oslab-02-ns ps
docker exec oslab-02-ns sh -c 'grep NSpid /proc/*/status'
docker top oslab-02-ns

    Example output (the numbers will differ):

    PID   USER     TIME  COMMAND
    1 root      0:00 unshare --pid --fork sleep 300
    7 root      0:00 sleep 300
    8 root      0:00 ps
/proc/1/status:NSpid:	1
/proc/14/status:NSpid:	14
/proc/7/status:NSpid:	7	1
/proc/self/status:NSpid:	14
/proc/thread-self/status:NSpid:	14
PID                 PPID                COMMAND
17570               17547               unshare --pid --fork sleep 300
17586               17570               sleep 300

    Why this matters: find the sleep process. The container sees it as PID 7. Inside the namespace you just made, it is PID 1 (that is what NSpid: 7 1 says). And from the engine's point of view it is 17586. Three numbers for one process, because PID namespaces nest like Russian dolls and each layer numbers its own residents. A process is “inside” a container only in the sense that it lives in these namespaces; underneath it is an ordinary process of the one kernel.

  7. The other namespaces, one at a time

    PID is only one of several namespaces. Each one hides a different part of the system.

    Host name (UTS). Give a container its own name, then make it share the host's instead:

    docker run --rm --label oslab=true --hostname lab-box alpine:3.22 hostname
docker run --rm --label oslab=true --uts=host alpine:3.22 hostname

    Network. A normal container has its own network interfaces. With --network none it has only the loopback interface lo:

    docker run --rm --label oslab=true alpine:3.22 sh -c 'ip addr | head -n 8'
docker run --rm --label oslab=true --network none alpine:3.22 ip addr

    Mounts (the file-system view). Write a file in one container, then look for it in the next. The second command is expected to fail:

    docker run --rm --label oslab=true alpine:3.22 sh -c 'echo hello > /tmp/note; cat /tmp/note'
docker run --rm --label oslab=true alpine:3.22 cat /tmp/note

    Example output for the three:

    lab-box
docker-desktop
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
    inet 127.0.0.1/8 scope host lo
       valid_lft forever preferred_lft forever
    inet6 ::1/128 scope host
       valid_lft forever preferred_lft forever
2: eth0@if130: <BROADCAST,MULTICAST,UP,LOWER_UP,M-DOWN> mtu 1500 qdisc noqueue state UP
    link/ether 86:53:fe:de:88:32 brd ff:ff:ff:ff:ff:ff
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
    inet 127.0.0.1/8 scope host lo
       valid_lft forever preferred_lft forever
    inet6 ::1/128 scope host
       valid_lft forever preferred_lft forever
hello
cat: can't open '/tmp/note': No such file or directory

    Why this matters: the host-name namespace gave the container its own name (lab-box), and sharing the host's namespace showed the host's name instead (docker-desktop here). The network namespace gave a container its own network card, or, with none, nothing but loopback. And the file written in one container was not there in the next, because each container has its own mount namespace, a private view of the file system. (Lab 4 will look at that more closely.)

  8. Explore /proc: the kernel's window

    The kernel shows each process as a folder under /proc. /proc/1/ns lists the namespaces a process belongs to, as links with ID numbers. Two processes in the same namespace show the same number. /proc/1/status describes the process. We use the oslab-02-sleeper container from step 2.

    docker exec oslab-02-sleeper sh -c 'head -n 8 /proc/1/status'
docker exec oslab-02-sleeper ls -l /proc/1/ns

    Example output (the long numbers are namespace IDs and will differ):

    Name:	sleep
Umask:	0022
State:	S (sleeping)
Tgid:	1
Ngid:	0
Pid:	1
PPid:	0
TracerPid:	0
total 0
lrwxrwxrwx    1 root     root             0 Nov 18 16:08 cgroup -> cgroup:[4026531835]
lrwxrwxrwx    1 root     root             0 Nov 18 16:08 ipc -> ipc:[4026532824]
lrwxrwxrwx    1 root     root             0 Nov 18 16:08 mnt -> mnt:[4026532822]
lrwxrwxrwx    1 root     root             0 Nov 18 16:08 net -> net:[4026532826]
lrwxrwxrwx    1 root     root             0 Nov 18 16:08 pid -> pid:[4026532825]
lrwxrwxrwx    1 root     root             0 Nov 18 16:08 pid_for_children -> pid:[4026532825]
lrwxrwxrwx    1 root     root             0 Nov 18 16:08 time -> time:[4026532931]
lrwxrwxrwx    1 root     root             0 Nov 18 16:08 time_for_children -> time:[4026532931]
lrwxrwxrwx    1 root     root             0 Nov 18 16:08 user -> user:[4026531837]
lrwxrwxrwx    1 root     root             0 Nov 18 16:08 uts -> uts:[4026532823]

    Why this matters: each line is one kind of namespace: pid, mnt (mounts), net, uts (host name), ipc (inter-process communication), plus cgroup, time and user. Docker gave this container its own PID, mount, network, host-name and IPC namespaces. In this example the user and cgroup numbers are very small (4026531837, …835): those are the host's own namespaces, which means Docker does not isolate users or cgroup views by default. “Container” is a recipe of several kernel features, not one switch.

Try it yourself

  1. Run docker run --rm --label oslab=true alpine:3.22 sh -c 'sleep 30 & ps'. Predict which process is PID 1, then check. (It may surprise you: this shell replaces itself with the last command it runs, so PID 1 is ps, and sleep is its former child.) What does that tell you about how a PID 1 comes to exist?
  2. Compare the ls -l /proc/1/ns output of two different containers, and of a container started with --pid=host. Which entries match? Which kinds of namespace does a container get by default?
  3. Start a container with --network none and try ping -c 1 127.0.0.1 inside it. Does loopback work? What does that tell you about what a network namespace contains?

Check your understanding

Clean up

Two containers are still running in the background. Remove them and check that nothing from this lab is left:

docker rm -f oslab-02-sleeper oslab-02-ns
docker ps -a --filter label=oslab=true

Troubleshooting

  • “unshare: Operation not permitted” even with --cap-add=SYS_ADMIN: some locked-down systems (certain security profiles, rootless Docker) forbid this. Read what you can in steps 1 to 4 and the quiz; the idea is the same.
  • “The container name … is already in use”: a container from an earlier attempt is still there. Run docker rm -f oslab-02-sleeper oslab-02-ns and try again.
  • The PIDs are different from the example: they always are. Look for the pattern (one process, several numbers), not the values.
  • PowerShell shows strange quoting problems: keep each command on one line and use the single quotes exactly as shown. See the troubleshooting page.

Key takeaways

  • A container's processes are ordinary kernel processes in their own namespaces: private views of process IDs, host names, networks, mounts and more.
  • One process has a different PID in each nested PID namespace; docker top, docker exec ps and NSpid show them.
  • The first process of a container is PID 1, which the kernel treats as the init process.
