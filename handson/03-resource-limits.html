Resource limits (cgroups)

Namespaces limit what a process can see. Control groups (cgroups) limit what it can use. Set a memory limit and a CPU limit, and watch the kernel enforce both.

About 40 minutesIntermediateRelated: Module 6 CPU Scheduling, Module 13 Memory Management, Module 19 Virtualization & Containers

Concept link: the control-group simulators in Module 19 model exactly what you will do here, and Module 6 explains the scheduler that enforces the CPU limit.

What you will learn

  • Start a container with --memory and --cpus, and read the limits from the kernel's own files.
  • Watch a program use more memory than it is allowed, and see the out-of-memory (OOM) killer end it (exit code 137).
  • Compare a CPU-bound program with one that mostly waits, under the same CPU limit.
  • Tell a memory limit from a memory reservation, and watch usage with docker stats.

Before you start

  • Prerequisites: Lab 0. It also helps to have done Lab 1's docker build step, but each step is explained again here.
  • Make an empty folder for this lab (for example oslab-03) and open your terminal in it. You will download three small files into it.
  • These tests are safe: every container has a memory limit, so a runaway program cannot use more than the limit. Do not remove the limit from the memory test. Without it the program would keep taking memory from Docker's virtual machine and could slow your computer.

Platform notes. cgroup v1 and v2. Linux has two versions of control groups, with different file names. Step 2 uses a command that works on both. The examples were captured on cgroup v1 (Docker Desktop with WSL2); newer Linux systems, and Docker Desktop on some versions, use v2. docker info says which one you have (Lab 0, step 3). Numbers differ by computer: a faster computer finishes the CPU test sooner, and Docker Desktop's virtual machine may have fewer processors than your computer. Not tested on cgroup v2, macOS or ARM64.

Steps

  1. Build the lab image

    Download these three files into your lab folder. memhog.py keeps asking for more memory until it is stopped; workload.py either computes or waits, and reports how long it took in wall-clock time and in CPU time; the Dockerfile packages both into one small Python image.

    # A small Python image holding the two lab programs.
FROM python:3.12-slim
WORKDIR /lab
COPY workload.py memhog.py ./
# -u: do not buffer output, so you see each line as it is printed, even if the program is killed
ENTRYPOINT ["python", "-u"]
    """Allocate memory 8 MiB at a time until the kernel stops us."""
import time

chunks = []
mib = 0
while True:
    chunks.append(bytearray(8 * 1024 * 1024))   # a bytearray is filled with zeros, so its memory really is used
    mib += 8
    print(f"holding {mib} MiB", flush=True)
    time.sleep(0.05)                            # slow down a little so you can watch it grow
    """Do a fixed amount of CPU-bound or waiting work, then report wall-clock time and CPU time.

Usage: workload.py cpu [rounds]    compute for about two seconds per round
       workload.py io  [rounds]    wait (sleep) for two seconds per round
"""
import sys
import time

kind = sys.argv[1] if len(sys.argv) > 1 else "cpu"
rounds = int(sys.argv[2]) if len(sys.argv) > 2 else 1
wall0, cpu0 = time.perf_counter(), time.process_time()
for _ in range(rounds):
    if kind == "cpu":
        total = 0
        for i in range(15_000_000):             # about two seconds of arithmetic on a typical computer
            total += i * i
    else:
        time.sleep(2)                           # waiting, not computing
wall, cpu = time.perf_counter() - wall0, time.process_time() - cpu0
print(f"{kind}: wall-clock {wall:.1f} s, CPU time {cpu:.1f} s, CPU share {100 * cpu / wall:.0f}%")

    Build the image. -t names it, --label oslab=true marks it for cleanup and -q prints only the image ID. The . means “this folder”.

    docker build -q --label oslab=true -t oslab-03-lab .

    Example output:

    sha256:92681caf93782f14ce2c6060ca4ea81d214a298d5ccff8452dbf74a68bbe00a4

  2. Set limits, then read them from the kernel

    Two new flags: --memory=64m allows at most 64 mebibytes of RAM, and --cpus=0.5 allows half of one CPU core's time. Docker passes these to the kernel, which records them as files under /sys/fs/cgroup inside the container. The file names differ between cgroup v1 and v2, so each command tries v2 first and falls back to v1 (|| means “or else”).

    docker run --rm --label oslab=true --memory=64m alpine:3.22 sh -c 'cat /sys/fs/cgroup/memory.max 2>/dev/null || cat /sys/fs/cgroup/memory/memory.limit_in_bytes'
docker run --rm --label oslab=true --cpus=0.5 alpine:3.22 sh -c 'cat /sys/fs/cgroup/cpu.max 2>/dev/null || cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us /sys/fs/cgroup/cpu/cpu.cfs_period_us'

    Example output (cgroup v1 shows the quota and the period on two lines; v2 shows 50000 100000 on one):

    67108864
50000
100000

    Why this matters: 67108864 is 64 × 1024 × 1024 bytes: the memory limit as the kernel stored it. The CPU limit is a quota of 50,000 microseconds of CPU time in every 100,000-microsecond period, which is half a core. The container did not make these limits. It only reads them. The Linux kernel's cgroup feature holds and enforces them.

  3. Limit the CPU and measure the effect

    workload.py cpu does a fixed amount of arithmetic and reports wall-clock time (the time on a clock) and CPU time (the time the CPU actually spent on it). workload.py io instead sleeps, which uses no CPU. Run the computing job with no limit, then with half a CPU, then run the waiting job with half a CPU.

    docker run --rm --label oslab=true oslab-03-lab workload.py cpu
docker run --rm --label oslab=true --cpus=0.5 oslab-03-lab workload.py cpu
docker run --rm --label oslab=true --cpus=0.5 oslab-03-lab workload.py io

    Example output (the first two numbers depend on how fast your computer is):

    cpu: wall-clock 2.1 s, CPU time 2.1 s, CPU share 100%
cpu: wall-clock 4.1 s, CPU time 2.1 s, CPU share 51%
io: wall-clock 2.0 s, CPU time 0.0 s, CPU share 0%

    Why this matters: the same amount of computing (2.1 seconds of CPU) took twice as long on the clock with --cpus=0.5, because the kernel's scheduler let the container run for only half of each period and made it wait for the rest. The waiting job did not slow down at all: it was not using the CPU, so the quota never applied. Limits slow CPU-bound work and leave I/O-bound work (waiting for disks, networks or people) almost alone. Module 6 explains the two kinds of workload.

  4. Watch a running container with docker stats

    Start a longer computing job in the background (cpu 15 means fifteen rounds, about thirty seconds under the limit) and look at it with docker stats. --no-stream prints one snapshot instead of updating forever.

    docker run -d --name oslab-03-busy --label oslab=true --cpus=0.5 --memory=128m oslab-03-lab workload.py cpu 15
docker stats --no-stream oslab-03-busy

    Example output:

    CONTAINER ID   NAME            CPU %     MEM USAGE / LIMIT   MEM %     NET I/O         BLOCK I/O   PIDS
4953ef25fcfc   oslab-03-busy   49.52%    4.785MiB / 128MiB   3.74%     1.17kB / 126B   0B / 0B     1

    Remove it when you have looked (-f stops it first):

    docker rm -f oslab-03-busy

    Why this matters: the job could use a whole core, but the CPU column holds at about 50%: the quota in action. The memory column shows usage against the limit you set. docker stats reads the same cgroup files you read in step 2.

  5. Run out of memory on purpose

    memhog.py allocates 8 mebibytes at a time and prints how much it holds. We give it a 64 MiB limit. --memory-swap=64m sets the total of memory plus swap to the same 64 MiB, so the program cannot escape the limit by using swap space, and the test behaves the same on every computer. We leave out --rm so we can inspect the stopped container afterwards.

    docker run --name oslab-03-hog --label oslab=true --memory=64m --memory-swap=64m oslab-03-lab memhog.py

    Example output (the exact last line varies; the command then returns to your prompt):

    holding 8 MiB
holding 16 MiB
holding 24 MiB
holding 32 MiB
holding 40 MiB
holding 48 MiB
holding 56 MiB

    It stopped by itself, around 56 MiB. Ask Docker what happened to it:

    docker inspect oslab-03-hog --format 'OOMKilled={{.State.OOMKilled}} ExitCode={{.State.ExitCode}}'
docker rm oslab-03-hog

    Example output:

    OOMKilled=true ExitCode=137
oslab-03-hog

    Why this matters: the program asked for its next 8 MiB and the kernel said no. When a cgroup runs out of memory and nothing can be freed, the kernel's out-of-memory (OOM) killer ends a process in it with signal 9 (SIGKILL), which cannot be caught or ignored, so the program had no chance to clean up or print an error. Exit code 137 means exactly that: 128 plus signal number 9. (The 64 MiB also holds Python itself, so the program stops a little short of 64.) This protects the rest of the computer: a runaway container kills only itself.

  6. A limit is not a reservation

    There are two different memory settings. --memory is a hard limit: go past it and you are killed. --memory-reservation is a soft reservation: a promise the kernel tries to keep when the whole computer is short of memory. Set both and read them back:

    docker run -d --name oslab-03-res --label oslab=true --memory=128m --memory-reservation=64m alpine:3.22 sleep 60
docker inspect oslab-03-res --format 'limit={{.HostConfig.Memory}} reservation={{.HostConfig.MemoryReservation}}'
docker rm -f oslab-03-res

    Example output:

    3f1c0f2a59b8c3a1d3e6f6f2b3b0a8f7a3d5c0e9b1f4c7d2a6e8b9c0d1e2f3a4
limit=134217728 reservation=67108864
oslab-03-res

    Why this matters: the container may use up to 128 MiB (the limit, 134,217,728 bytes) but is only guaranteed its 64 MiB reservation when memory is tight; above it the kernel may reclaim memory from it first. Limits protect everyone else. Reservations protect you. Neither is a promise that a program will work: a program that needs more than its limit simply dies, as you saw.

Try it yourself

  1. Run workload.py cpu with --cpus=0.25 and with --cpus=2. Predict the wall-clock time before each. Why does --cpus=2 not make a single-threaded program faster?
  2. Run memhog.py again with --memory=128m --memory-swap=128m. Does it stop at about twice as many lines? (Remove the container afterwards with docker rm oslab-03-hog.)
  3. Start two workload.py cpu 15 containers at once, both with --cpus=0.5, and look at docker stats --no-stream. Now start them without limits. How does the kernel share the CPU between them?

Troubleshooting

  • The memory test never stops, or “holding” climbs far past 64: check that you typed both --memory=64m and --memory-swap=64m. If it is running away, press Ctrl+C and run docker rm -f oslab-03-hog.
  • The CPU test does not take twice as long: a computer or virtual machine with very few cores, or one that is busy with something else, can blur the result. Close other programs and run it again. The CPU share column (about 50%) is the more reliable signal.
  • “cat: can't open /sys/fs/cgroup/…”: the first file does not exist on your cgroup version. The command is written to fall back to the other, so look for a number in the output; you can ignore the error line if it appears.
  • “WARNING: Your kernel does not support memory limit capabilities”: on some Linux systems memory limits must be enabled in the boot options. This is rare on Docker Desktop.
  • See the troubleshooting page for other problems.

Key takeaways

  • Control groups (cgroups) are a kernel feature. Docker only sets the limits; the kernel's memory manager and scheduler enforce them.
  • Going past a memory limit gets a process killed by the OOM killer (exit code 137); going past a CPU quota only makes it wait.
  • CPU limits slow computing but barely affect programs that mostly wait, and a memory limit is a hard cap while a reservation is a soft promise.
