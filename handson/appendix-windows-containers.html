Hands-on with Docker · Appendix

Windows containers

Everything in the labs uses Linux containers. Docker can also run Windows containers. This page explains what they are and why they are not used here. It is reading only: there is nothing to run.

Not tested. The author's computer runs Windows Home, which cannot run Windows containers, so nothing on this page has been run. The facts come from Docker's and Microsoft's documentation as understood at the time of writing; check their current documentation before relying on a detail.

Where they run

  • Windows containers run only on Windows: Windows 10 and 11 Pro, Enterprise or Education (through Docker Desktop's “Switch to Windows containers”), or Windows Server. They are not available on Windows Home, and not on macOS or Linux.
  • Docker Desktop can be in Linux containers mode or Windows containers mode, and you switch between them. You cannot use both modes at the same time, and images for one kind do not run in the other.
  • That is why this guide uses Linux containers: they work on every platform, including Windows Home with WSL2.

How they differ from Linux containers

  • A different kernel. The shared kernel is the Windows NT kernel, not Linux. The big idea of Lab 0 still holds: a Windows container does not carry its own kernel, it uses the host's.
  • Matching versions. In the default “process isolation” mode, the container's Windows version must match the host's Windows build, because the container uses the host kernel directly. A newer isolation mode, “Hyper-V isolation”, runs each container in a small virtual machine with its own kernel, which allows a mismatch but costs more.
  • Different building blocks. Windows has its own equivalents of namespaces and cgroups (called silos and job objects), a registry instead of /etc files, PowerShell and cmd instead of bash, and drive letters and backslashes in paths.
  • Bigger images. Windows base images are usually much larger than Linux ones: the Server Core image is measured in gigabytes, compared with megabytes for Alpine. (Nano Server is smaller but has far fewer features.)

What it looks like (illustration only)

These commands are here to show the flavour. They are not runnable on every setup (they need Windows containers mode on a Windows edition that supports it), and they were not run for this page.

# Not runnable on every setup: needs Windows containers mode (Windows Pro, Enterprise or Education).
docker run --rm mcr.microsoft.com/windows/nanoserver:ltsc2022 cmd /c ver
docker run --rm mcr.microsoft.com/windows/servercore:ltsc2022 powershell -Command "Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion' | Select-Object ProductName, CurrentBuild"

The first prints the Windows version of the container's user space. The second reads the Windows registry, a database of settings that has no equivalent inside a Linux container.

Questions to think about

  1. In Lab 0 you saw that every Linux container reported the same kernel. What would you expect ver to show in two different Windows containers on one host, and why?
  2. Why might Microsoft have added Hyper-V isolation? (Think about the version-matching rule.)
  3. If a team wanted one container image to run on a developer's Mac, a Windows laptop and a Linux server, which kind would it have to be?

Suggested answers: (1) The same Windows build, for the same reason as in Linux: containers use the host kernel. (2) It lets a container run on a host with a different Windows build, by giving it its own kernel in a lightweight VM. (3) A Linux container, because the Mac and the Windows laptop both run Linux containers through a Linux virtual machine.
