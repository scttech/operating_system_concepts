Hands-on with Docker · Lab 1

A tour of Linux distributions

Different “operating systems” in Docker differ in user space: their files, their package manager, their shell and, most importantly, their C library. Compare five of them, then see why a program built for one can fail on another.

About 40 minutesBeginnerRelated: Module 18 Beyond Windows, macOS & Linux, Module 19 Virtualization & Containers

Concept link: Module 18 compares whole operating systems. This lab compares the user-space half of several Linux systems that all share one kernel (Lab 0).

What you will learn

  • Tell Debian, Ubuntu, Alpine, Fedora and Arch containers apart by their /etc/os-release, shell, image size and package manager.
  • Install the same package with apt, apk, dnf and pacman.
  • Explain what the C standard library does, and how glibc differs from musl.
  • Build a small C program in two distributions, inspect it with ldd, and see a Debian-built program fail on Alpine.

Before you start

  • Prerequisites: Lab 0 (Docker works, and you know docker run).
  • Some steps download packages from the internet inside a container, so allow a few minutes. About 700 MB of disk space.
  • Make an empty folder for this lab, for example oslab-01, and open your terminal in that folder. Steps 5 to 8 use five small files that you will download into it. (A docker build sends that folder to Docker as the “build context”. Use a folder that contains only these files.)

Platform notes. Windows, macOS and Linux: the commands are identical. ARM64 (Apple Silicon, ARM Linux): the Debian, Ubuntu, Alpine and Fedora images publish ARM64 versions, so everything works, but the ldd output names aarch64 instead of x86-64. The Arch Linux image is x86-64 only: on an ARM64 computer skip the Arch lines. Not tested on Apple Silicon.

Steps

  1. Which distribution am I in?

    Every modern Linux has a text file, /etc/os-release, that names the distribution. grep picks the one line we want. (We will run each command inside a throwaway container; the “shell” you type into is still your own.)

    docker run --rm --label oslab=true debian:13-slim grep PRETTY_NAME /etc/os-release
docker run --rm --label oslab=true ubuntu:24.04 grep PRETTY_NAME /etc/os-release
docker run --rm --label oslab=true alpine:3.22 grep PRETTY_NAME /etc/os-release
docker run --rm --label oslab=true fedora:43 grep PRETTY_NAME /etc/os-release

    Arch Linux (x86-64 computers only; skip this on ARM64):

    docker run --rm --label oslab=true archlinux:base grep PRETTY_NAME /etc/os-release

    Example output:

    PRETTY_NAME="Debian GNU/Linux 13 (trixie)"
PRETTY_NAME="Ubuntu 24.04.5 LTS"
PRETTY_NAME="Alpine Linux v3.22"
PRETTY_NAME="Fedora Linux 43 (Container Image)"
PRETTY_NAME="Arch Linux"

    Why this matters: five “operating systems” in seconds, and none had to boot. Each image is just a different set of files. (The tags such as 13-slim pin a version so this lab behaves the same later. Arch is a “rolling” distribution, so its base tag always means the newest.)

  2. Compare the default shell

    /bin/sh is the standard name for “a shell”. readlink -f follows the link to the real program.

    docker run --rm --label oslab=true debian:13-slim readlink -f /bin/sh
docker run --rm --label oslab=true alpine:3.22 readlink -f /bin/sh
docker run --rm --label oslab=true fedora:43 readlink -f /bin/sh

    Example output:

    /usr/bin/dash
/bin/busybox
/usr/bin/bash

    Why this matters: Debian uses dash, a small fast shell. Alpine uses BusyBox, one tiny program that provides hundreds of commands (ls, cp, ps, even the shell). Fedora uses the fuller bash. Small choices like these, repeated everywhere, are what make Alpine small.

  3. Compare image sizes

    docker images lists the images on your computer. Each --filter reference=… keeps images whose name matches.

    docker images --filter reference=debian --filter reference=ubuntu --filter reference=alpine --filter reference=fedora --filter reference=archlinux

    Example output (newer Docker versions show these columns; older ones show a slightly different table):

    IMAGE                ID             DISK USAGE   CONTENT SIZE   EXTRA
alpine:3.22          812e99317af7        8.3MB             0B
archlinux:base       ad77cf4a18d8        400MB             0B
debian:13-slim       596c6d80c879       78.9MB             0B
fedora:43            3866f820f690        182MB             0B
ubuntu:24.04         7da97f743f39       78.2MB             0B

    Why this matters: none of these sizes includes a kernel, because images do not contain one. The 70 MB gap between Alpine and Debian is all user space: a smaller C library, BusyBox instead of the GNU tools, and fewer pre-installed packages.

  4. Install the same package everywhere

    Each distribution has its own package manager: a tool that downloads and installs software. Debian and Ubuntu use apt, Alpine uses apk, Fedora uses dnf and Arch uses pacman. We install a small package named tree in each, then ask it for its version. sh -c '…' runs a short command line inside the container, and > /dev/null hides the installer's chatter.

    docker run --rm --label oslab=true debian:13-slim sh -c 'apt-get update -qq > /dev/null && apt-get install -y -qq tree > /dev/null && tree --version'
docker run --rm --label oslab=true ubuntu:24.04 sh -c 'apt-get update -qq > /dev/null && apt-get install -y -qq tree > /dev/null && tree --version'
docker run --rm --label oslab=true alpine:3.22 sh -c 'apk add --no-cache -q tree && tree --version'
docker run --rm --label oslab=true fedora:43 sh -c 'dnf install -y -q tree > /dev/null && tree --version'

    On an x86-64 computer, Arch too:

    docker run --rm --label oslab=true archlinux:base sh -c 'pacman -Sy --noconfirm tree > /dev/null 2>&1 && tree --version'

    Example output (versions and download times differ, and that is the point):

    tree v2.2.1 (c) 1996 - 2024 by Steve Baker, Thomas Moore, Francesc Rocher, Florian Sesser, Kyosuke Tokoro
tree v2.1.1 (c) 1996 - 2023 by Steve Baker, Thomas Moore, Francesc Rocher, Florian Sesser, Kyosuke Tokoro
tree v2.2.1 © 1996 - 2024 by Steve Baker, Thomas Moore, Francesc Rocher, Florian Sesser, Kyosuke Tokoro
tree v2.2.1 (c) 1996 - 2024 by Steve Baker, Thomas Moore, Francesc Rocher, Florian Sesser, Kyosuke Tokoro
tree v2.3.2 © 1996 - 2026 by Steve Baker, Thomas Moore, Francesc Rocher, Florian Sesser, Kyosuke Tokoro

    Why this matters: the same program, four different installation tools, and a different version in each, because each distribution decides what to ship. On the author's computer Alpine finished in about 2 seconds and Fedora in about 12. A distribution is mostly a choice of packages and the tools that manage them.

  5. What is a C standard library? Build one program twice

    Almost every program calls a C standard library (“libc”): a collection of ready-made functions such as printf (print text) and malloc (get memory). Many of those functions make system calls to the kernel for you. Debian, Ubuntu and Fedora use glibc. Alpine uses a smaller one called musl. They do the same job, but they are different programs.

    Download these three files into your lab folder. hello.c is the program. Each Dockerfile is a short recipe that builds it: FROM picks the starting image, RUN runs a command while building (here, installing the C compiler gcc and compiling), COPY adds a file, and CMD is what the container runs when it starts.

    /* A tiny C program. It asks the C library (libc) to print one line. */
#include <stdio.h>

int main(void) {
    printf("Hello from a C program!\n");
    return 0;
}
    # Build and run hello.c on Debian, which uses the glibc C library.
FROM debian:13-slim
RUN apt-get update -qq && apt-get install -y -qq gcc libc6-dev > /dev/null
COPY hello.c .
RUN gcc -o hello hello.c
CMD ["./hello"]
    # Build and run the same program on Alpine, which uses the musl C library.
FROM alpine:3.22
RUN apk add --no-cache -q gcc musl-dev
COPY hello.c .
RUN gcc -o hello hello.c
CMD ["./hello"]

    Build both images. -t gives the new image a name, -f names the recipe file, --label oslab=true marks the image for cleanup, and the final . means “use the current folder as the build context”. Then run each one.

    docker build -q --label oslab=true -t oslab-01-debian -f Dockerfile.debian .
docker build -q --label oslab=true -t oslab-01-alpine -f Dockerfile.alpine .
docker run --rm --label oslab=true oslab-01-debian
docker run --rm --label oslab=true oslab-01-alpine

    Example output (-q prints just the image ID, which will differ):

    sha256:1bd16363a8a183c20859f36e11e32cb195a22f7626d517214f7e3b648b9367c2
sha256:23986bcbe1d6cae45b310694b063516d521da77a698e86495ef8e4476ccf3c31
Hello from a C program!
Hello from a C program!

    Why this matters: the same source code, compiled in two environments, behaves the same. But are the two programs the same? Look inside next.

  6. Look at which library each program needs

    ldd lists the shared libraries a program will load when it starts.

    docker run --rm --label oslab=true oslab-01-debian ldd hello
docker run --rm --label oslab=true oslab-01-alpine ldd hello

    Example output (x86-64; addresses differ every run, and an ARM64 computer names aarch64 files):

    	linux-vdso.so.1 (0x00007ffd0ffef000)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f45b94e2000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f45b96df000)
	/lib/ld-musl-x86_64.so.1 (0x7f85bce51000)
	libc.musl-x86_64.so.1 => /lib/ld-musl-x86_64.so.1 (0x7f85bce51000)

    Why this matters: the Debian program needs libc.so.6 (glibc) and a loader, ld-linux-x86-64.so.2, a helper the kernel starts first to load libraries. The Alpine program needs ld-musl-… instead. (linux-vdso.so.1 is not a file: the kernel supplies it, so some calls can be answered without a full system call.) The two programs are not interchangeable.

  7. Run a Debian-built program on Alpine

    Download Dockerfile.cross. It builds the program on Debian, then copies only the finished program into an Alpine image. (This is called a multi-stage build: the first FROM … AS build is a scratch workshop, and only what you COPY --from it survives.)

    # Build the program on Debian (glibc), then copy ONLY the finished program into an Alpine image (musl).
FROM debian:13-slim AS build
RUN apt-get update -qq && apt-get install -y -qq gcc libc6-dev > /dev/null
COPY hello.c .
RUN gcc -o hello hello.c

FROM alpine:3.22
COPY --from=build /hello /hello
CMD ["/hello"]

    Build it and run it. The run is expected to fail:

    docker build -q --label oslab=true -t oslab-01-cross -f Dockerfile.cross .
docker run --rm --label oslab=true oslab-01-cross

    Example output:

    sha256:5af25c767d334bdb8a3ea085d69a3ffe5eadabe91d69ebef6a4dbda583b2ac4c
exec /hello: no such file or directory

    Why this matters: the file /hello is there, yet the kernel says “no such file”. The message is about the loader the program names, /lib64/ld-linux-x86-64.so.2, which does not exist on Alpine, because Alpine has no glibc. Same kernel, different user space: that is exactly why a binary built on one distribution can fail on another.

  8. Fix it: carry your own library

    One fix is to link the program statically, so it contains its own copy of the library instead of looking for a shared one. Dockerfile.static is the same recipe with gcc -static.

    # The fix: link the program statically on Debian, so it carries its own copy of the C library.
FROM debian:13-slim AS build
RUN apt-get update -qq && apt-get install -y -qq gcc libc6-dev > /dev/null
COPY hello.c .
RUN gcc -static -o hello hello.c

FROM alpine:3.22
COPY --from=build /hello /hello
CMD ["/hello"]
    docker build -q --label oslab=true -t oslab-01-static -f Dockerfile.static .
docker run --rm --label oslab=true oslab-01-static
docker images --filter 'reference=oslab-01-*'

    Example output (size column trimmed):

    Hello from a C program!
oslab-01-alpine    181MB
oslab-01-debian    296MB
oslab-01-static    9.06MB
oslab-01-cross     8.32MB

    Why this matters: now the Debian-built program runs on Alpine. Look at the sizes: the two images that compile a program contain a whole compiler (hundreds of megabytes), but the multi-stage images ship only the result and are barely larger than Alpine itself.

What is an init system? When a Linux computer boots, the kernel starts exactly one program, which starts everything else: the init system (for example systemd). A container usually skips all that and just runs the one program you ask for. A later lab in this guide (Lab 6) shows why that matters. See also Module 4, the boot process.

Try it yourself

  1. Compile hello.c inside a fedora:43 container as well (use dnf install -y gcc). Does the result run on Debian? On Alpine? Predict, then test.
  2. Use ldd on the static program: build the static image, then run docker run --rm oslab-01-static ldd /hello (it is in an Alpine image). What does it say, and why?
  3. Run docker run --rm --label oslab=true alpine:3.22 ls / and the same for debian:13-slim. Which top-level folders differ?

Troubleshooting

  • “failed to read dockerfile” or “no such file”: your terminal is not in the lab folder, or a file did not download. Check with dir (Windows) or ls.
  • Packages cannot be downloaded inside a container: a firewall or proxy is blocking it. See the troubleshooting page.
  • “no matching manifest for linux/arm64” on Arch: expected. The official Arch image is x86-64 only. Skip the Arch lines.
  • The same step works but the output differs from the example: package versions, sizes and addresses change over time. That is normal.

Key takeaways

  • Distributions differ in user space: files, shell, package manager and C library. The kernel is shared.
  • glibc and musl are two implementations of the C library. A program expects the one it was built for, and the missing loader is why a Debian-built program fails on Alpine.
  • Static linking, or building on the target distribution, makes a program portable across user spaces.
