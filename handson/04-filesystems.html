Hands-on with Docker · Lab 4

Filesystems

A container's files are not one disk. They are stacked read-only layers with a thin writable layer on top, plus mounts that bring in storage from elsewhere. Look at each, then look at the “files” that are not files at all.

About 40 minutesIntermediateRelated: Module 16 File Systems, Module 15 Disk I/O, Module 19 Virtualization & Containers

Concept link: Module 16 explains inodes, links and mounting; here you will see all three in a running system.

What you will learn

  • Read an image's layers with docker history, and see why deleting a file in a later layer does not make the image smaller.
  • Watch copy-on-write with docker diff, and see that changes to a container's own layer disappear with the container.
  • Keep data with a named volume, and compare it with a tmpfs mount and a bind mount.
  • Explore /proc, /sys and /dev, which look like files but are windows into the kernel.
  • See an inode, and the difference between a hard link and a symbolic link.

Before you start

  • Prerequisites: Lab 0.
  • Make an empty folder for this lab (for example oslab-04) and open your terminal in it. You will download one small file into it.
  • Everything here is throwaway. The one thing that outlives a container is the volume you create in step 3, and the clean-up removes it.

Platform notes. On Windows and macOS, Docker keeps its layers and volumes inside the hidden Linux virtual machine, so you will not find them in your own folders; paths such as /var/lib/docker/… belong to that machine. The bind-mount example in step 4 is the exception: it deliberately shares a folder from your computer, and its command differs between bash and PowerShell. The examples were captured on Docker Desktop with WSL2. Not tested on macOS or ARM64.

Steps

  1. Build an image with layers, and read its history

    Each instruction in a Dockerfile that changes files makes one layer. This one makes a small file, then a 5 MB file, then deletes the 5 MB file. Download it into your lab folder:

    # Three layers on top of Alpine. The last one deletes the file the second one made.
FROM alpine:3.22
RUN echo one > /one.txt
RUN dd if=/dev/zero of=/big.bin bs=1M count=5
RUN rm /big.bin
    docker build -q --label oslab=true -t oslab-04-layers .

    Now list the layers. Each row is one instruction, newest first, with the size of the files it added:

    docker history oslab-04-layers

    Example output (IDs, ages and wording vary between Docker versions):

    IMAGE          CREATED                  CREATED BY                                      SIZE      COMMENT
0b8034b5fdff   Less than a second ago   RUN /bin/sh -c rm /big.bin # buildkit           0B        buildkit.dockerfile.v0
<missing>      1 second ago             RUN /bin/sh -c dd if=/dev/zero of=/big.bin b…   5.24MB    buildkit.dockerfile.v0
<missing>      1 second ago             RUN /bin/sh -c echo one > /one.txt # buildkit   4B        buildkit.dockerfile.v0
<missing>      13 days ago              CMD ["/bin/sh"]                                 0B        buildkit.dockerfile.v0
<missing>      13 days ago              ADD alpine-minirootfs-3.22.8-x86_64.tar.gz /…   8.3MB     buildkit.dockerfile.v0

    The file really is gone from the finished image, yet the layer that made it is still there, still 5.24 MB. Check both facts:

    docker image inspect oslab-04-layers --format 'size={{.Size}}'
docker run --rm --label oslab=true oslab-04-layers ls /big.bin

    Example output (the last line is an error; ls failing is the point):

    size=13548...
ls: /big.bin: No such file or directory

    Why this matters: an image is a stack of read-only layers, and each layer only adds to the stack. Deleting /big.bin in the third layer hides it with a marker (a “whiteout”) but the second layer still holds its bytes, so the image stays about 5 MB larger than Alpine alone (about 8.3 MB). This is why people combine commands in one RUN line, or build in stages (Lab 1), so that temporary files never reach a layer. Layers are shared too: a hundred containers from this image use one copy of each.

  2. Copy-on-write: change files and ask what changed

    Start a container and, from a second command, change three things in it: create a file, append to a file that came from the image, and delete another one.

    docker run -d --name oslab-04-cow --label oslab=true alpine:3.22 sleep 300
docker exec oslab-04-cow sh -c 'echo hi > /newfile; echo x >> /etc/motd; rm /bin/true'

    docker diff lists every difference between the container and the image it started from. A means added, C changed and D deleted:

    docker diff oslab-04-cow

    Example output (the order of the lines can vary):

    C /bin
D /bin/true
C /etc
C /etc/motd
A /newfile

    Where do those changes live? Ask the container how its root filesystem is mounted:

    docker exec oslab-04-cow sh -c 'grep overlay /proc/mounts'

    Example output (shortened; the real line is much longer):

    overlay / overlay rw,relatime,lowerdir=/var/lib/docker/overlay2/l/…:/var/lib/docker/overlay2/l/…,upperdir=/var/lib/docker/overlay2/…/diff,workdir=…/work 0 0

    Last, throw the container away and start a new one from the same image. Is your new file still there?

    docker rm -f oslab-04-cow
docker run --rm --label oslab=true alpine:3.22 ls /newfile

    Example output:

    oslab-04-cow
ls: /newfile: No such file or directory

    Why this matters: the root filesystem is an overlay: the image's layers (lowerdir, read-only) with one empty writable layer on top (upperdir). Reading a file finds it in the highest layer that has it. Writing to a file that came from the image first copies it up into the writable layer and changes the copy: this is copy-on-write. A deleted file is hidden by a marker, and the layers below are never touched. The writable layer belongs to the container, so removing the container removes your changes. Data you want to keep must live somewhere else.

  3. Keep data with a named volume

    A volume is storage managed by Docker that lives outside any one container's layers. Create one, write to it from one container, and read it from a completely different one. -v NAME:/data mounts the volume at /data.

    docker volume create --label oslab=true oslab-04-data
docker run --rm --label oslab=true -v oslab-04-data:/data alpine:3.22 sh -c 'echo saved > /data/note.txt'
docker run --rm --label oslab=true -v oslab-04-data:/data alpine:3.22 cat /data/note.txt

    Example output:

    oslab-04-data
saved

    Both containers are gone (--rm), yet the note survived. Ask Docker where it is kept:

    docker volume inspect oslab-04-data --format '{{.Mountpoint}}'

    Example output:

    /var/lib/docker/volumes/oslab-04-data/_data

    Why this matters: the volume is an ordinary folder that Docker mounts into the container, in front of the container's own layers. It has its own life: it exists before the container and after it. That folder is inside Docker's Linux VM on Windows and macOS, which is why you cannot browse to it in File Explorer or Finder. Databases and anything else that must outlive a container belong on a volume.

  4. tmpfs and bind mounts

    Two more kinds of mount. A tmpfs mount is a filesystem that exists only in memory: fast, and gone when the container stops.

    docker run --rm --label oslab=true --tmpfs /scratch alpine:3.22 sh -c 'echo gone > /scratch/f; mount | grep scratch'

    Example output:

    tmpfs on /scratch type tmpfs (rw,nosuid,nodev,noexec,relatime)

    A bind mount shares a folder from your own computer with the container, so both sides see the same files. That is useful for editing code on your computer while it runs in a container, and it is exactly what this guide avoids elsewhere, because a container with a bind mount can change your files. Run the next command only from your empty lab folder: it shares just that folder.

    # bash, zsh or WSL (run from your lab folder)
docker run --rm --label oslab=true -v $PWD:/work alpine:3.22 sh -c 'echo from-the-container > /work/made.txt'
cat made.txt
    # PowerShell (run from your lab folder)
docker run --rm --label oslab=true -v ${PWD}:/work alpine:3.22 sh -c 'echo from-the-container > /work/made.txt'
Get-Content made.txt

    Example output:

    from-the-container

    Delete made.txt afterwards. (If your path contains spaces, these simple commands need quotes, and the double quotes this guide avoids; see the Docker documentation on --mount.)

    Why this matters: now a file made inside a container exists on your real disk, and it stays after the container is gone. The three mounts differ in where the bytes live: a volume in Docker's own storage, a bind mount in a folder you choose, and tmpfs only in memory. On Windows and macOS a bind mount crosses from the Linux VM to your host's filesystem, which is much slower than a volume for programs that do many small file operations.

  5. “Everything is a file”: /proc, /sys and /dev

    Unix presents many things as files. Some are special filesystems that hold no data on any disk: the kernel makes their contents when you read them. See three of them. First /proc: look at the size ls reports for /proc/cpuinfo, then at how many bytes you actually get:

    docker run --rm --label oslab=true alpine:3.22 sh -c 'ls -l /proc/cpuinfo; wc -c /proc/cpuinfo; head -n 2 /proc/meminfo'

    Example output (the numbers depend on the computer):

    -r--r--r--    1 root     root             0 Nov 18 19:37 /proc/cpuinfo
20194 /proc/cpuinfo
MemTotal:        8067492 kB
MemFree:         4867388 kB

    Now /dev (devices as files) and the mount list that shows what kind each of these is:

    docker run --rm --label oslab=true alpine:3.22 sh -c 'ls -l /dev/null /dev/zero; head -c 8 /dev/zero | od -c; grep -e ^proc -e ^sysfs /proc/mounts'

    Example output:

    crw-rw-rw-    1 root     root        1,   3 Nov 18 19:37 /dev/null
crw-rw-rw-    1 root     root        1,   5 Nov 18 19:37 /dev/zero
0000000  \0  \0  \0  \0  \0  \0  \0  \0
0000010
proc /proc proc rw,nosuid,nodev,noexec,relatime 0 0
sysfs /sys sysfs ro,nosuid,nodev,noexec,relatime 0 0

    Why this matters: /proc/cpuinfo claims to be 0 bytes long yet produces about 20,000 bytes: it is not stored anywhere, the kernel writes it as you read it. The leading c in crw-rw-rw- marks /dev/null and /dev/zero as character devices: reading /dev/zero gives endless zero bytes, and writing to /dev/null discards them. They are interfaces to the kernel's code, not to a disk. /proc (processes and kernel state) and /sys (devices and settings; read-only in a container) are the mounts of type proc and sysfs. You already read /sys/fs/cgroup in Lab 3 and /proc/PID/status in Lab 2.

  6. Inodes, hard links and symbolic links

    A file's real identity is its inode, a record holding its size, owner, permissions and where its data is. A file name is only an entry in a directory that points to an inode. Make a file, a hard link to it (ln) and a symbolic link to it (ln -s), and list their inode numbers with ls -i:

    docker run --rm --label oslab=true alpine:3.22 sh -c 'cd /tmp; echo hello > a; ln a hard; ln -s a soft; ls -li'

    Example output (the first column is the inode number):

    total 8
 210255 -rw-r--r--    2 root     root             6 Nov 18 19:37 a
 210255 -rw-r--r--    2 root     root             6 Nov 18 19:37 hard
 210258 lrwxrwxrwx    1 root     root             1 Nov 18 19:37 soft -> a

    Now delete the original name a and try each link:

    docker run --rm --label oslab=true alpine:3.22 sh -c 'cd /tmp; echo hello > a; ln a hard; ln -s a soft; rm a; cat hard; cat soft'

    Example output:

    hello
cat: can't open 'soft': No such file or directory

    Why this matters: a and hard have the same inode number (and a link count of 2): they are two names for one file, so deleting one name leaves the data reachable through the other. The data is freed only when the last name is removed. The symbolic link has its own inode and holds only the text “a”: when a is gone, the link points at nothing. (Module 16 draws this picture.) The inode table is also finite: df -i / shows how many inodes the filesystem has, and a disk can run out of them before it runs out of space.

Try it yourself

  1. Change the Dockerfile so the second and third instructions are one line (RUN dd if=/dev/zero of=/big.bin bs=1M count=5 && rm /big.bin), build it as oslab-04-layers2, and compare docker history. What happened to the 5 MB layer? (Remove the image afterwards with docker rmi oslab-04-layers2.)
  2. Run docker run --rm --label oslab=true alpine:3.22 df -i /. How many inodes does the root filesystem have, and how many are in use?
  3. Make a volume-backed container and a plain one, write the same file into each, remove both containers, and start new ones. Which files survive, and why?

Check your understanding

Clean up

Remove the container (if you stopped before the end of step 2), the volume and the image, then check that nothing from this lab remains. The last command lists any oslab containers and should print only its header line. Also delete made.txt from your lab folder if you did the bind-mount example.

docker rm -f oslab-04-cow
docker volume rm oslab-04-data
docker rmi oslab-04-layers
docker ps -a --filter label=oslab=true

(Any line that says “No such …” is for something you had already removed. That is fine.)

Troubleshooting

  • “volume is in use”: a container still has it mounted, even a stopped one. Run docker rm -f NAME for it, then remove the volume again.
  • The bind-mount command creates an empty folder or is refused: on Docker Desktop, the folder must be shared with Docker (in the settings, under file sharing). A path with spaces needs quotes. This is the one place the guide asks you to run something that depends on your shell.
  • “rm: can't remove '/etc/hostname': Resource busy” if you try to delete /etc/hostname, /etc/hosts or /etc/resolv.conf: Docker mounts those files into every container. That is why step 2 deletes /bin/true instead.
  • docker history shows <missing> for most rows: expected. Only the newest layer has an image ID on your computer.
  • See the troubleshooting page for other problems.

Key takeaways

  • An image is a stack of read-only layers; a container adds one thin writable layer using copy-on-write. Remove the container and the writable layer goes with it.
  • Data that must survive lives in a volume (Docker's storage) or a bind mount (your folder); tmpfs lives only in memory.
  • Not every “file” is data on a disk: /proc, /sys and /dev are interfaces to the kernel, and a file name is just one of possibly several names for an inode.
