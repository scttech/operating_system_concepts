Hands-on with Docker · Lab 0

Setup and the big idea

Install and check Docker, run your first containers, and discover the idea behind this whole guide: a container is not a separate operating system.

About 30 minutesBeginnerRelated: Module 1 OS Fundamentals, Module 19 Virtualization & Containers

The big idea. A container is not a separate operating system. Containers share the kernel of the computer they run on, and differ only in user space: files, libraries, a package manager and the programs that came with the image. On Windows and macOS, Docker Desktop quietly runs a small Linux virtual machine, and every Linux container shares that machine's kernel. You will prove this in a few minutes.

What you will learn

  • Check that Docker works, and find out which platform and kernel it is using.
  • Run containers and use the six everyday Docker words: image, container, run, exec, ps and rm.
  • See that containers made from different Linux distributions report the same kernel.
  • Explain why a Windows or macOS computer has a hidden Linux machine inside it.

Before you start

  • Docker, installed and running: Docker Desktop on Windows or macOS, or Docker Engine on Linux. Both are free for personal learning. Nothing else is needed: no accounts, no paid software, no special hardware.
  • About 2 GB of free disk space for the images used across these labs, and an internet connection for the downloads.
  • A terminal: PowerShell, Windows Terminal or a WSL shell on Windows; Terminal on macOS; any shell on Linux. Every command here works in bash, zsh and PowerShell unless a note says otherwise.
  • This guide is optional. Nothing else on this site depends on it.

Windows Home. Docker Desktop uses the WSL2 backend on Windows Home, and the setting cannot be changed there. That is expected, and it is the setup this guide is written for. Windows containers are not available on Home (see the note on Windows containers).

macOS. Docker Desktop runs a Linux virtual machine. Intel Macs use x86-64 images and Apple Silicon Macs use ARM64 images: the images in these labs publish both, so the commands are the same. The author did not test on Apple Silicon.

Linux. There is no virtual machine: containers use your own computer's kernel directly.

Is this safe? Containers are disposable and these labs only use throwaway ones. Every container is named oslab-… and labelled oslab=true, so one command can remove all of them (see Clean up everything). The labs never mount your files into a container. Two later labs add one extra permission (--cap-add) and explain why. Nothing here uses --privileged. Use these labs on your own computer, not on a shared or production machine.

Steps

  1. Check that Docker is installed

    docker version prints information about two programs: the client (the docker command you type) and the server, also called the engine or daemon, which actually creates and runs containers.

    docker version

    Example output (version numbers will differ; this is trimmed):

    Client:
 Version:           29.5.3
 OS/Arch:           windows/amd64
 Context:           desktop-linux

Server: Docker Desktop 4.78.0
 Engine:
  Version:          29.5.3
  OS/Arch:          linux/amd64

    Why this matters: look at the two OS/Arch lines. On this Windows computer the client is windows/amd64 but the server is linux/amd64. The engine that runs your containers is a Linux system, even though you are typing on Windows. That is the hidden Linux machine. On Linux both lines say linux.

  2. Run your first container

    docker run creates a container from an image and starts it. An image is a read-only bundle of files (a program and what it needs). If the image is not on your computer, Docker downloads it first. --rm tells Docker to delete the container as soon as it stops, so nothing is left behind.

    docker run --rm hello-world

    Example output (the first lines):

    Hello from Docker!
This message shows that your installation appears to be working correctly.

To generate this message, Docker took the following steps:
 1. The Docker client contacted the Docker daemon.
 2. The Docker daemon pulled the "hello-world" image from the Docker Hub.

    Why this matters: the message lists what just happened: your client asked the engine, the engine fetched an image and ran it. hello-world is the one image in this guide that has no version tag, because it is Docker's own install check. Every other image is pinned to a specific version, so the labs keep behaving the same way.

  3. Ask Docker about its platform

    docker info reports on the engine. --format picks out just the fields we want, using a template written between double braces.

    docker info --format 'OS: {{.OperatingSystem}} | kernel {{.KernelVersion}} | cgroup v{{.CgroupVersion}} | {{.Architecture}}'

    Example output (from Windows 11 Home with Docker Desktop; yours will differ):

    OS: Docker Desktop | kernel 5.15.146.1-microsoft-standard-WSL2 | cgroup v1 | x86_64

    Why this matters: the kernel is the Linux kernel inside Docker Desktop's virtual machine, not Windows. A Mac typically shows linuxkit in the kernel name (the author has not tested on a Mac), and on Linux you see your own distribution and kernel. Write down the kernel version. In the next step you will see it again, from inside several different containers. (cgroup is the kernel feature you will use in Lab 3; aarch64 instead of x86_64 means an ARM64 computer.)

  4. Run containers from different Linux distributions

    Each line below starts a throwaway container from a different distribution's image and runs uname -srm, which prints the kernel's name, release (version) and the machine type. image:tag names an image and a version of it. --label oslab=true attaches a label so cleanup commands can find the container later.

    docker run --rm --label oslab=true debian:13-slim uname -srm
docker run --rm --label oslab=true ubuntu:24.04 uname -srm
docker run --rm --label oslab=true alpine:3.22 uname -srm
docker run --rm --label oslab=true fedora:43 uname -srm

    Example output (the first run downloads each image, which takes a little while):

    Linux 5.15.146.1-microsoft-standard-WSL2 x86_64
Linux 5.15.146.1-microsoft-standard-WSL2 x86_64
Linux 5.15.146.1-microsoft-standard-WSL2 x86_64
Linux 5.15.146.1-microsoft-standard-WSL2 x86_64

    Why this matters: Debian, Ubuntu, Alpine and Fedora are four different Linux distributions, yet all four report the same kernel. They are not four operating systems. They are four sets of user-space files running on one kernel.

  5. Compare with your own computer

    Now ask your own computer for its kernel. What you see depends on your system:

    • Linux: run uname -r. It matches the containers exactly, because containers use your own kernel.
    • Windows with WSL2: run wsl uname -r. WSL2 and Docker Desktop normally use the same Linux kernel, so you will usually see the same version as above.
    • macOS: run uname -srm. It prints Darwin, Apple's kernel, which is different from the containers' Linux kernel. The containers are using the Linux kernel inside Docker Desktop's virtual machine.
    • Windows without WSL: there is no uname. Windows itself runs the NT kernel, which is not Linux at all.
    uname -r          # Linux
wsl uname -r      # Windows with WSL2 installed
uname -srm        # macOS

    Why this matters: on Linux the container kernel and the host kernel are one and the same. On Windows and macOS they are different from the system you are typing on, which proves a Linux virtual machine sits in between.

  6. Read the kernel's own description of itself

    The kernel shows information as files under /proc. This one is its version banner.

    docker run --rm --label oslab=true debian:13-slim cat /proc/version

    Example output (from the author's computer):

    Linux version 5.15.146.1-microsoft-standard-WSL2 (root@65c757a075e2) (gcc (GCC) 11.2.0, GNU ld (GNU Binutils) 2.37) #1 SMP Thu Jan 11 04:09:03 UTC 2024

    Why this matters: /proc/version is not a file on disk. The kernel generates it when you read it. Much of Linux works this way ("everything is a file"), and you will use /proc a lot in later labs.

  7. Learn the everyday commands

    Four more commands complete the vocabulary. First start a container that keeps running in the background: -d (detached) returns your prompt immediately, and --name gives the container a name you can refer to. sleep 300 is just a command that does nothing for five minutes, to keep the container alive.

    docker run -d --name oslab-00-sleeper --label oslab=true debian:13-slim sleep 300

    Now list running containers (add -a to include stopped ones), run a second command inside the running container with exec, and finally remove it (-f stops it first if it is still running).

    docker ps --filter label=oslab=true
docker exec oslab-00-sleeper uname -r
docker rm -f oslab-00-sleeper

    Example output:

    CONTAINER ID   IMAGE            COMMAND       CREATED         STATUS         PORTS   NAMES
66cc82ffae4b   debian:13-slim   "sleep 300"   2 seconds ago   Up 1 second            oslab-00-sleeper
5.15.146.1-microsoft-standard-WSL2
oslab-00-sleeper

    Why this matters: exec started a new process inside the same container, and it reported the same kernel as before. The word-for-word vocabulary is small: an image is the recipe (files), a container is a running (or stopped) instance made from it, run creates and starts one, exec runs another command in it, ps lists them and rm deletes them.

The picture

Try it yourself

  1. Run docker run --rm --label oslab=true alpine:3.22 cat /etc/os-release, then the same with debian:13-slim. Which one file tells you the distribution? Which command from step 4 could not tell them apart?
  2. Run docker run --rm --label oslab=true alpine:3.22 sh -c 'nproc; head -n 2 /proc/meminfo'. These numbers describe the machine the container sees. On Windows and macOS compare them to your real computer. What do you notice? (Docker Desktop's virtual machine may have fewer processors and less memory than your computer.)
  3. Run docker images. Which images are smallest and which are largest? Keep the answer in mind for Lab 1.

Check your understanding

Clean up

Every container in this lab was removed by --rm or docker rm -f. Check that none are left (the list should be empty):

docker ps -a --filter label=oslab=true

The images you downloaded can stay: the next labs reuse them. To remove the hello-world image: docker rmi hello-world. The overview page has a command that removes everything from this whole guide.

Troubleshooting

  • “Cannot connect to the Docker daemon” / “error during connect”: the engine is not running. Start Docker Desktop and wait until it says it is running, or on Linux run sudo systemctl start docker.
  • “permission denied … /var/run/docker.sock” (Linux): your user is not allowed to use Docker. Either put sudo in front of each command or add yourself to the docker group (see Docker's Linux post-install steps), then log out and back in.
  • “docker: command not found” or “is not recognized”: close and reopen your terminal after installing, so it sees the new command.
  • Downloads fail or hang: check your internet connection; on a work or school network a proxy may be needed. See the troubleshooting page.

Key takeaways

  • A container is a set of user-space files run on a shared kernel. It is not a separate operating system.
  • Different distributions (Debian, Ubuntu, Alpine, Fedora) report the same kernel because they all use the machine's one kernel.
  • On Windows and macOS, Docker Desktop hides a small Linux virtual machine whose kernel every Linux container shares.
