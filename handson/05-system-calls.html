System calls

A program cannot touch a disk, the screen or memory management itself. It asks the kernel, through system calls. A tool called strace lets you watch every one of those requests.

About 35 minutesIntermediateRelated: Module 1 OS Fundamentals, Module 5 Processes, Module 2 Security

Concept link: Module 1 introduces the user/kernel boundary and system calls; this lab makes that boundary visible.

What you will learn

  • Trace a program with strace and read a line of its output: the call, its arguments and its result.
  • Count how many system calls a tiny “hello world” makes, and compare it with ls and with Python.
  • Recognise the common ones: execve, open, read and write, mmap, fork and exit_group.
  • See a system call refused by the kernel, and what the refusal looks like to the program.

Before you start

  • Prerequisites: Lab 0. Lab 1 (the C library) is a helpful background.
  • Make an empty folder for this lab (for example oslab-05) and open your terminal in it. You will download four small files into it.
  • You only trace programs that you start inside throwaway containers. Nothing here looks at your computer.

Platform notes. Is --cap-add=SYS_PTRACE needed? strace works through a system call named ptrace. Many guides say a container needs --cap-add=SYS_PTRACE to use it. On the setup used to write this guide (Docker 29, kernel 5.15 in Docker Desktop's WSL2 machine) it was not needed, either to trace a program that strace starts or to attach to another process of the same user, so none of the commands below add it. On older Docker or kernel versions, or on systems with extra security policies, you may see ptrace: Operation not permitted; the fix is to add --cap-add=SYS_PTRACE to the docker run command (an untested remedy here). The output below comes from Alpine Linux, so it shows the musl C library; Debian or Ubuntu programs (glibc) make slightly different calls. Not tested on macOS or ARM64: system call names such as open differ on ARM64, where the kernel offers only openat.

Steps

  1. Build the tools image

    Download these four files into your lab folder. hello.c is a one-line C program; spawn.sh is a script that runs another program; the Dockerfile compiles hello.c in one stage and then makes a small image holding the program, strace and Python.

    #include <stdio.h>

int main(void) {
    printf("hello, world\n");
    return 0;
}
    #!/bin/sh
ls /etc > /dev/null
    # Stage 1: compile the hello program. The compiler stays behind in this stage.
FROM alpine:3.22 AS build
RUN apk add --no-cache gcc musl-dev
COPY hello.c .
RUN gcc -o hello hello.c

# Stage 2: a small image with strace, Python and the finished program.
FROM alpine:3.22
RUN apk add --no-cache strace python3
COPY --from=build /hello /usr/local/bin/hello
COPY spawn.sh /usr/local/bin/spawn.sh
    docker build -q --label oslab=true -t oslab-05-tools .

    Example output (the first build downloads a few packages and takes a minute):

    sha256:4472f1a4de5e90af841e5af010535ae1fbf9bd372d86152749b1e7cd0997599d

  2. Trace “hello, world”

    strace PROGRAM runs the program and prints each system call it makes. -o /tmp/t writes that list to a file, so it does not get mixed into the program's own output; then cat shows the file. Everything between the single quotes runs inside the container.

    docker run --rm --label oslab=true oslab-05-tools sh -c 'strace -o /tmp/t hello; cat /tmp/t'

    Example output (addresses change on every run):

    hello, world
execve("/usr/local/bin/hello", ["hello"], 0x7fffcf6d99a0 /* 3 vars */) = 0
arch_prctl(ARCH_SET_FS, 0x7f2f5174cb28) = 0
set_tid_address(0x7f2f5174cf90)         = 9
brk(NULL)                               = 0x564124096000
brk(0x564124098000)                     = 0x564124098000
mmap(0x564124096000, 4096, PROT_NONE, MAP_PRIVATE|MAP_FIXED|MAP_ANONYMOUS, -1, 0) = 0x564124096000
mprotect(0x7f2f51749000, 4096, PROT_READ) = 0
mprotect(0x5641231f7000, 4096, PROT_READ) = 0
ioctl(1, TIOCGWINSZ, 0x7fff26a4b6d8)    = -1 ENOTTY (Not a tty)
writev(1, [{iov_base="hello, world", iov_len=12}, {iov_base="\n", iov_len=1}], 2) = 13
exit_group(0)                           = ?
+++ exited with 0 +++

    Why this matters: each line is one request to the kernel: the name of the call, its arguments, and after = what the kernel returned. The program's whole job is the writev line near the end: “write these 13 bytes to file descriptor 1” (standard output). Everything else is the program starting up: execve loads it, brk and mmap set up memory, ioctl asks whether output is a terminal (it is not, so the answer is an error, ENOTTY), and exit_group ends it. One printed line cost about a dozen calls.

  3. Count the calls: hello, ls and Python

    Add -f to follow any processes the program starts, send the program's own output to /dev/null, and count the lines in the trace with wc -l (one call per line). Run it on three programs:

    docker run --rm --label oslab=true oslab-05-tools sh -c 'strace -f -o /tmp/t hello > /dev/null; wc -l < /tmp/t'
docker run --rm --label oslab=true oslab-05-tools sh -c 'strace -f -o /tmp/t ls / > /dev/null; wc -l < /tmp/t'
docker run --rm --label oslab=true oslab-05-tools sh -c 'strace -f -o /tmp/t python3 -c 1 > /dev/null; wc -l < /tmp/t'

    Example output (the numbers differ between versions; the pattern does not):

    12
42
521

    strace -c instead summarises: how many times each call was made, and how many failed. Try it on ls:

    docker run --rm --label oslab=true oslab-05-tools sh -c 'strace -c -o /tmp/t ls / > /dev/null; cat /tmp/t'

    Example output (times are tiny and vary):

    % time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 40.38    0.000529          31        17           lstat
 13.82    0.000181         181         1           execve
  6.95    0.000091          45         2           writev
  6.41    0.000084          42         2           mprotect
  5.80    0.000076          19         4         4 ioctl
  5.50    0.000072          36         2           getdents64
  4.35    0.000057          28         2           brk
  3.28    0.000043          21         2           mmap
  2.21    0.000029          29         1           munmap
  2.14    0.000028          28         1           close
------ ----------- ----------- --------- --------- ----------------
100.00    0.001309          ...        43         4 total

    Why this matters: the same “run something and show text” costs a dozen calls in C, about forty for ls (one lstat per file it lists, plus getdents64 to read the directory) and hundreds for Python, which loads an interpreter, libraries and its own modules at start-up. Each call is a switch from user mode into the kernel and back, so a program that makes many small calls pays a real price. This is why buffered input and output, which groups many small writes into one call, matters so much for speed.

  4. Find open, read, write and close

    Trace cat reading a file. The grep keeps only the lines about files:

    docker run --rm --label oslab=true oslab-05-tools sh -c 'strace -o /tmp/t cat /etc/hostname; grep -e open -e read -e sendfile -e write -e close /tmp/t'

    Example output (the first line is the file's contents; the rest are the calls):

    ad07b756aa72
open("/etc/hostname", O_RDONLY|O_LARGEFILE) = 3
sendfile(1, 3, NULL, 16777216)          = 13
sendfile(1, 3, NULL, 16777216)          = 0
close(3)                                = 0

    Why this matters: this is the pattern of all file input. open asks the kernel to find the file and checks permissions, and it returns a small number (here 3), a file descriptor that stands for the open file in every later call. sendfile(1, 3, …) means “copy from descriptor 3 (the file) to descriptor 1 (standard output)”: BusyBox's cat uses it to copy 13 bytes without bringing them into the program. A second call returning 0 means end of file. Other programs use read and write for the same job. close gives the descriptor back. Descriptors 0, 1 and 2 are standard input, output and error, which is why writev(1, …) printed to the screen in step 2.

  5. Watch a process start another: fork and execve

    spawn.sh does one thing: it runs ls. To run another program, a shell must make a copy of itself (fork), wait for it (wait4) and have the copy turn into the new program (execve). -e trace=process shows only the calls about processes, and -f follows the child. The number at the start of each line is the process ID.

    docker run --rm --label oslab=true oslab-05-tools sh -c 'strace -f -e trace=process -o /tmp/t sh /usr/local/bin/spawn.sh; cat /tmp/t'

    Example output:

    10    execve("/bin/sh", ["sh", "/usr/local/bin/spawn.sh"], 0x7ffff275bdb0 /* 5 vars */) = 0
10    fork()                            = 11
10    wait4(-1,  <unfinished ...>
11    execve("/bin/ls", ["ls", "/etc"], 0x7efd2c550200 /* 5 vars */) = 0
11    exit_group(0)                     = ?
11    +++ exited with 0 +++
10    <... wait4 resumed>[{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 11
10    --- SIGCHLD {si_signo=SIGCHLD, si_code=CLD_EXITED, si_pid=11, si_uid=0, si_status=0, ...} ---
10    wait4(-1, 0x7fffdbd475fc, WNOHANG, NULL) = -1 ECHILD (No child process)
10    exit_group(0)                     = ?
10    +++ exited with 0 +++

    Why this matters: this is how every Unix program is started. Process 10 (the shell) calls fork() and the kernel creates process 11, a copy; the shell goes to sleep in wait4 until its child is done. Process 11 calls execve, which replaces its program with /bin/ls, keeping the same process ID. When ls finishes, the kernel tells the parent with a signal (SIGCHLD), and wait4 returns 11, the child's ID, and collects its exit status. (Other systems may show clone or vfork instead of fork: they are variants of the same idea. Lab 6 shows what happens when a parent never calls wait4.)

  6. See the kernel say no

    In Lab 2 the command unshare failed unless you added --cap-add=SYS_ADMIN. Now watch it fail. -e trace=unshare shows only that one system call:

    docker run --rm --label oslab=true oslab-05-tools sh -c 'strace -e trace=unshare -o /tmp/t unshare --pid --fork sleep 1; cat /tmp/t'

    Example output:

    unshare: unshare(0x20020000): Operation not permitted
unshare(CLONE_NEWNS|CLONE_NEWPID)       = -1 EPERM (Operation not permitted)
+++ exited with 1 +++

    Run it again with the one extra capability:

    docker run --rm --label oslab=true --cap-add=SYS_ADMIN oslab-05-tools sh -c 'strace -e trace=unshare -o /tmp/t unshare --pid --fork sleep 1; cat /tmp/t'

    Example output:

    unshare(CLONE_NEWNS|CLONE_NEWPID)       = 0
--- SIGCHLD {si_signo=SIGCHLD, si_code=CLD_EXITED, si_pid=11, si_uid=0, si_status=0, ...} ---
+++ exited with 0 +++

    Why this matters: the program made exactly the same call both times. The first time the kernel returned −1 with the error code EPERM (“operation not permitted”); the second time it returned 0, success. A system call is the one place where the kernel can check who is asking and decide. In a container two things can say no: the kernel's own permission checks (capabilities, such as SYS_ADMIN), and a seccomp filter that Docker installs by default, a list of system calls a container may not make at all. That is how a container is made safer without being a separate machine: the kernel is shared, so the system call boundary is where the walls are built.

Try it yourself

  1. Trace hello again with -e trace=write,writev. Which call prints the text? Does the count change if you change the C program to print two lines?
  2. Count the calls for cat /etc/hostname and for cat /etc/os-release. Why are they nearly the same, even though the files have different sizes?
  3. Use strace -e trace=openat,open python3 -c 1 (inside sh -c '…' as above) and look at the failures (ENOENT). Why would Python try to open files that do not exist?
  4. Optional and untested here: attach to a running process with sh -c 'sleep 30 & strace -p $!'. If you get “Operation not permitted”, add --cap-add=SYS_PTRACE.

Troubleshooting

  • “ptrace: Operation not permitted” or “Could not attach to process”: your Docker or kernel setup does not allow tracing by default. Add --cap-add=SYS_PTRACE to the docker run command. (Untested here, because it was not needed.)
  • “strace: command not found”: you are not using oslab-05-tools. The image from step 1 includes it.
  • The trace is empty or very short: make sure the program name comes after the strace options. Anything after the program name is passed to the program, not to strace.
  • The system call names look different from the examples: expected on Debian, Ubuntu and Fedora (glibc uses openat and write where Alpine's musl uses open and writev) and on ARM64.
  • See the troubleshooting page for other problems.

Key takeaways

  • A system call is the controlled doorway between a user program and the kernel. Every file, process and memory request goes through one, and strace lists them.
  • Even “hello, world” makes about a dozen: starting a program (execve), setting up memory (brk, mmap), the real work (write) and exiting (exit_group). Starting another program is fork plus execve, and the parent collects the result with wait4.
  • Because every request passes the kernel, the kernel can refuse it. A refusal is a normal return value (-1 and an error such as EPERM), and this is where capabilities and seccomp filters protect a container.
