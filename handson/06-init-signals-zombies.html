Init, signals and zombies

The first process in a container has a job most programs never expect: it must handle signals the way init does, and it must collect the exit status of orphaned processes. Break both rules on purpose, then fix them.

About 40 minutesIntermediateRelated: Module 5 Processes, Module 4 Boot Process, Module 12 Inter-Process Communication

Concept link: Module 5 covers process creation, termination and zombies, and Module 4 shows where init comes from at boot. Lab 2 explained why PID 1 is special.

What you will learn

  • Send signals (SIGTERM, SIGINT, SIGKILL) to a container with docker kill and docker stop.
  • See why a program running as PID 1 can ignore SIGTERM, and what docker stop does about it (exit code 137).
  • Make a zombie process on purpose and find it in /proc.
  • Fix both problems with docker run --init, and explain what an init process does.

Before you start

  • Prerequisites: Lab 0, and Lab 2 is strongly recommended (PID 1 and namespaces).
  • Make an empty folder for this lab (for example oslab-06) and open your terminal in it. You will download three small files into it.
  • A zombie process uses almost nothing: only an entry in the process table. This lab is safe, and every container is removed at the end.

Platform notes. The stop timeout. docker stop sends SIGTERM, waits, and then sends SIGKILL. Docker documents the wait as 10 seconds. On the Docker used to write this guide (Docker 29 in Docker Desktop) the default turned out to be shorter, so every docker stop below says -t 3 (three seconds) explicitly and the result does not depend on your version. Times and numbers in the example output will differ. Not tested on macOS or ARM64.

Steps

  1. Build the lab image

    Download these three files into your lab folder. sleeper.py does nothing and installs no signal handlers, like most simple programs. zombie.py creates a zombie. The Dockerfile packages both.

    # A small Python image holding the two lab programs.
FROM python:3.12-slim
WORKDIR /lab
COPY sleeper.py zombie.py ./
# -u: do not buffer output, so you see each line as it is printed
ENTRYPOINT ["python", "-u"]
    """Do nothing, politely, and never install a signal handler: what most programs do."""
import time

print("sleeping; I installed no signal handlers", flush=True)
while True:
    time.sleep(1)
    """Make a zombie. A grandchild is orphaned, so the kernel hands it to PID 1. When it exits, it stays a zombie unless PID 1 collects it."""
import os
import time

middle = os.fork()
if middle == 0:
    if os.fork() == 0:          # the grandchild: lives two seconds, then exits
        time.sleep(2)
        os._exit(0)
    os._exit(0)                 # the middle process exits at once, so the grandchild is orphaned
os.waitpid(middle, 0)           # we collect only our own child, as most programs do
print("started; I never wait for anything else", flush=True)
time.sleep(60)
    docker build -q --label oslab=true -t oslab-06-lab .

    Example output:

    sha256:29cc6efc1ea8bc9e415c0ca26c26e82d685f1a5bd9eac6df69e6711f1c5c36b2

  2. Send signals: one is ignored, one works

    A signal is a short message the kernel delivers to a process. SIGTERM means “please finish and exit”. SIGINT is what Ctrl+C sends. Start sleeper.py in the background, then send it SIGTERM and ask whether it is still running:

    docker run -d --name oslab-06-sleeper --label oslab=true oslab-06-lab sleeper.py
docker kill --signal=SIGTERM oslab-06-sleeper
docker inspect oslab-06-sleeper --format 'running={{.State.Running}}'

    Example output (the first line is the container's ID, which docker run -d prints, and the signal's target, which docker kill prints back):

    3f1c0f2a59b8c3a1d3e6f6f2b3b0a8f7a3d5c0e9b1f4c7d2a6e8b9c0d1e2f3a4
oslab-06-sleeper
running=true

    It ignored the polite request. Now send SIGINT, wait for the container to finish (docker wait prints its exit code) and read its log:

    docker kill --signal=SIGINT oslab-06-sleeper
docker wait oslab-06-sleeper
docker logs oslab-06-sleeper
docker rm oslab-06-sleeper

    Example output:

    oslab-06-sleeper
130
sleeping; I installed no signal handlers
Traceback (most recent call last):
  File "/lab/sleeper.py", line 6, in <module>
    time.sleep(1)
KeyboardInterrupt
oslab-06-sleeper

    Why this matters: the same program, the same process, two signals, two results. The cause is the rule you met in Lab 2: PID 1 is protected by the kernel. For any other process, SIGTERM kills it unless it has installed a handler. For PID 1, the kernel ignores a signal unless the program has installed a handler for it. Our script installed none for SIGTERM, so it was ignored. Python itself does install a handler for SIGINT (it turns it into a KeyboardInterrupt error), so that one worked, and the exit code 130 is 128 + 2, the number of SIGINT. This is why Ctrl+C sometimes does nothing in a container: a program that installs no handler, such as sleep or many small tools, is PID 1 and ignores it.

  3. Watch docker stop give up waiting

    docker stop sends SIGTERM, waits for the number of seconds after -t, and if the process is still there sends SIGKILL. SIGKILL can never be caught or ignored, not even by PID 1. This command pauses for about three seconds, which is the waiting:

    docker run -d --name oslab-06-stop --label oslab=true oslab-06-lab sleeper.py
docker stop -t 3 oslab-06-stop
docker inspect oslab-06-stop --format 'exit={{.State.ExitCode}}'
docker rm oslab-06-stop

    Example output:

    3f1c0f2a59b8c3a1d3e6f6f2b3b0a8f7a3d5c0e9b1f4c7d2a6e8b9c0d1e2f3a4
oslab-06-stop
exit=137
oslab-06-stop

    Why this matters: exit code 137 is 128 + 9: the container was ended by SIGKILL, the same code you saw from the out-of-memory killer in Lab 3. The program never got a chance to save its work, close connections or delete temporary files. Real services (databases, web servers) can lose data this way. The fix is not to wait longer, it is to make sure SIGTERM reaches code that handles it.

  4. Add an init process with --init

    --init puts a tiny program (Docker's copy of tini) in front of yours. It becomes PID 1; your program becomes an ordinary child. Run the same test:

    docker run -d --init --name oslab-06-init --label oslab=true oslab-06-lab sleeper.py
docker stop -t 3 oslab-06-init
docker inspect oslab-06-init --format 'exit={{.State.ExitCode}}'
docker rm oslab-06-init

    Example output (and this time there is no three-second wait):

    3f1c0f2a59b8c3a1d3e6f6f2b3b0a8f7a3d5c0e9b1f4c7d2a6e8b9c0d1e2f3a4
oslab-06-init
exit=143
oslab-06-init

    Why this matters: the same program stopped at once, with exit code 143, which is 128 + 15 (SIGTERM). The init program forwards the signal to its child. The child is no longer PID 1, so the kernel treats SIGTERM normally and its default action, ending the process, applies. Nothing in the program changed; only its place in the process tree did.

  5. Make a zombie

    When a process ends, the kernel keeps a small record of it, its exit status, until its parent collects it with wait. A process in that state is a zombie: dead, but still listed. zombie.py starts a process that starts another and exits at once. That leaves the youngest process an orphan, and the kernel gives orphans to PID 1. Here PID 1 is our script, which never waits for it. Wait four seconds for the orphan to finish, then list every process's name, state and parent in /proc:

    docker run -d --name oslab-06-zombie --label oslab=true oslab-06-lab zombie.py
docker exec oslab-06-zombie sleep 4
docker exec oslab-06-zombie sh -c 'grep -H -e Name -e State -e PPid /proc/[0-9]*/status'

    Example output (process numbers vary; look for the line with Z (zombie)):

    3f1c0f2a59b8c3a1d3e6f6f2b3b0a8f7a3d5c0e9b1f4c7d2a6e8b9c0d1e2f3a4
/proc/1/status:Name:	python
/proc/1/status:State:	S (sleeping)
/proc/1/status:PPid:	0
/proc/8/status:Name:	python
/proc/8/status:State:	Z (zombie)
/proc/8/status:PPid:	1
/proc/…/status:Name:	sh
…

    Why this matters: process 8 has finished, yet it is still in the table: State: Z (zombie), with parent 1. Its parent, our script, will never ask for its exit status, so it stays until the container ends. One zombie is harmless, but each one occupies a process-table slot, and a long-running service that keeps creating them can eventually fill the table and be unable to start anything new. (ps shows these as Z or <defunct>.) You cannot kill a zombie, because it is already dead. Only its parent collecting it, or the parent's own end, removes it.

  6. Fix it: an init that collects orphans

    Remove that container, and run exactly the same thing with --init. -e, -H and the other letters are the same as before; --init is the only difference.

    docker rm -f oslab-06-zombie
docker run -d --init --name oslab-06-reaped --label oslab=true oslab-06-lab zombie.py
docker exec oslab-06-reaped sleep 4
docker exec oslab-06-reaped sh -c 'grep -H -e Name -e State /proc/[0-9]*/status'

    Example output (no Z anywhere):

    oslab-06-zombie
3f1c0f2a59b8c3a1d3e6f6f2b3b0a8f7a3d5c0e9b1f4c7d2a6e8b9c0d1e2f3a4
/proc/1/status:Name:	docker-init
/proc/1/status:State:	S (sleeping)
/proc/7/status:Name:	python
/proc/7/status:State:	S (sleeping)
/proc/…/status:Name:	sh
…

    Why this matters: now PID 1 is docker-init and our script is process 7. When the orphan was left behind, the kernel gave it to PID 1, and docker-init did what every init program does: it called wait and collected the exit status, so the zombie vanished at once. Reaping orphans is PID 1's second job, and most application programs do not know they have it. This is also why --init is a common recommendation for containers that start helper processes, such as shell scripts that launch other programs.

  7. What init systems do, and how they differ

    On a full computer, PID 1 is a full init system (Module 4). Check what PID 1 is in a plain container and with --init. /proc/1/comm holds the name of PID 1's program:

    docker run --rm --label oslab=true alpine:3.22 cat /proc/1/comm
docker run --rm --init --label oslab=true alpine:3.22 cat /proc/1/comm

    Example output:

    cat
docker-init

    Four ways to be PID 1, from the largest to the smallest. This table is for reading; nothing here is run.

    ApproachWhat it doesWhere you see it
    systemdStarts and supervises many services in dependency order, handles logging, mounts, timers and more, reaps orphans.Most mainstream desktop and server Linux (Debian, Ubuntu, Fedora, Arch).
    OpenRC, runitSmaller init systems: start and supervise services, reap orphans, with far fewer features.Alpine Linux (OpenRC), some minimal systems (runit).
    tini / --initDoes only two jobs: forwards signals to one child and reaps orphans.Containers.
    NothingYour program is PID 1 and must do both jobs itself.The default in Docker, as you saw.

    Not run here: a container can run systemd, but it needs extra privileges and settings that differ by platform, so this guide only describes it.

    Why this matters: “init” is a role, not one program. The kernel starts exactly one program as PID 1 and gives it extra duties: adopt orphans, and decide what to do with signals. A big init system adds service management; tini adds nothing else; with no init, your application is that role, whether it knows it or not.

  2. Run sleeper.py and stop it with docker stop -t 1 and with docker stop -t 20. Does the exit code change? Does the time?
  3. Run docker run --rm --label oslab=true alpine:3.22 sh -c 'sleep 30 & sleep 30' with --init and without, and compare how docker stop behaves (use -d and --name oslab-06-try for this, and remove the container afterwards).

Troubleshooting

  • The zombie does not appear: run the docker exec … sleep 4 line first and make sure at least two seconds have passed since the container started, because the orphan lives two seconds before it becomes a zombie. A zombie also disappears when the container's script ends after 60 seconds.
  • docker top or ps do not list the zombie: some versions of ps hide or label it differently. Reading /proc/*/status, as the steps do, always works.
  • “The container name … is already in use”: remove the old one (docker rm -f NAME) and run the command again.
  • docker stop returns at once even without --init: a program that handles SIGTERM exits at once, and so does one that ends by itself. Use sleeper.py exactly as shown.
  • See the troubleshooting page for other problems.

Key takeaways

  • As PID 1, a program must install its own signal handlers or the kernel ignores the signals. That is why docker stop can time out and fall back to SIGKILL (exit code 137).
  • A zombie is a finished process whose parent has not collected its exit status. Orphans are handed to PID 1, which must collect them.
  • An init process (docker run --init) takes over both jobs: it forwards signals and reaps orphans, so ordinary programs can run safely as its children.
