Threads, race conditions and the GIL

Create threads, make them share a counter, watch updates disappear, and fix the problem with a lock. Then measure when threads actually make Python faster, and when you need separate processes instead.

Part A: a race condition

Predict first: four threads each add 1 to a shared counter 2,000 times. What should the final value be? Without a lock, do you expect exactly that, more, or less?

In C the race needs no help. Python's interpreter lock keeps most threads from running at the same moment, so the Python version calls time.sleep(0) to force a switch, which is a little contrived. In C the four threads really run on different CPU cores at once, so updates are lost on their own, much as they are in real programs. volatile stops the compiler from keeping the counter in a register, so the read and the write really happen. Build it with gcc -std=c99 -D_POSIX_C_SOURCE=200809L -pthread -O0 -o lab2_threads lab2_threads.c. C is so much faster that each thread adds 200,000 times, so the numbers differ from the Python output, but the lesson is the same.

/* Lab 2a (C) - Threads, race conditions and locks with POSIX threads. Build with:  gcc -std=c99 -D_POSIX_C_SOURCE=200809L -pthread */
#include <pthread.h>
#include <stdio.h>

#define THREADS 4
#define ITERATIONS 200000

static volatile long counter = 0;           /* volatile: every use is a real read from or write to memory */
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

static void *unsafe_worker(void *arg) {
    (void)arg;
    for (int i = 0; i < ITERATIONS; i++) {
        long temp = counter;                /* (1) READ the shared value */
        /* (2) Nothing to add here: the threads really run at the same moment on different CPU cores,
               so another thread can slip in between the read and the write all by itself. */
        counter = temp + 1;                 /* (3) WRITE back a possibly stale value */
    }
    return NULL;
}

static void *safe_worker(void *arg) {
    (void)arg;
    for (int i = 0; i < ITERATIONS; i++) {
        pthread_mutex_lock(&lock);          /* (4) only one thread at a time may be between lock and unlock */
        long temp = counter;
        counter = temp + 1;
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

static long run(void *(*worker)(void *)) {
    pthread_t threads[THREADS];
    counter = 0;
    for (int i = 0; i < THREADS; i++) pthread_create(&threads[i], NULL, worker, NULL);   /* (5) all threads now run at once */
    for (int i = 0; i < THREADS; i++) pthread_join(threads[i], NULL);                    /* (6) wait for every thread to finish */
    return counter;
}

int main(void) {
    const long expected = (long)THREADS * ITERATIONS;
    printf("%d threads each add 1 to a shared counter %d times; the right answer is %ld\n", THREADS, ITERATIONS, expected);
    const char *labels[] = { "without a lock", "with a lock" };
    void *(*workers[])(void *) = { unsafe_worker, safe_worker };
    for (int k = 0; k < 2; k++) {
        long got = run(workers[k]);
        if (got == expected) printf("  %-15s got %5ld: correct\n", labels[k], got);
        else printf("  %-15s got %5ld: WRONG (%ld updates lost)\n", labels[k], got, expected - got);
    }
    return 0;
}

The time.sleep(0) in (2) is a teaching device. Because only one thread runs Python bytecode at a time, small programs often get lucky without it, which is dangerous: the bug is still there and shows up later under load. The C tab shows the race happening naturally, with no help.

"""Lab 2a - Threads, race conditions and locks."""
import threading
import time

THREADS, ITERATIONS = 4, 2000
counter = 0
lock = threading.Lock()


def unsafe_worker():
    global counter
    for _ in range(ITERATIONS):
        temp = counter              # (1) READ the shared value
        time.sleep(0)               # (2) yield the CPU: another thread can run between the read and the write
        counter = temp + 1          # (3) WRITE back a possibly stale value


def safe_worker():
    global counter
    for _ in range(ITERATIONS):
        with lock:                  # (4) only one thread at a time may be inside this block
            temp = counter
            time.sleep(0)
            counter = temp + 1


def run(worker):
    global counter
    counter = 0
    threads = [threading.Thread(target=worker) for _ in range(THREADS)]
    for t in threads:
        t.start()                   # (5) all threads now run at once
    for t in threads:
        t.join()                    # (6) wait for every thread to finish
    return counter


expected = THREADS * ITERATIONS
print(f"{THREADS} threads each add 1 to a shared counter {ITERATIONS} times; the right answer is {expected}")
for label, worker in (("without a lock", unsafe_worker), ("with a lock", safe_worker)):
    got = run(worker)
    verdict = "correct" if got == expected else f"WRONG ({expected - got} updates lost)"
    print(f"  {label:<15} got {got:>5}: {verdict}")

Your “without a lock” number will be different every time. The “with a lock” line will always be correct.

  with a lock     got  8000: correct

What to notice

  1. (1)–(3) counter += 1 is really three steps: read, add, write (the same load, add, store you stepped through in the race-condition lab). Here they are spelled out as separate lines.
  2. (2) time.sleep(0) makes the thread give up the CPU between the read and the write. That makes the race easy to see. Without it, Python's interpreter lock hides many races on small programs, which is dangerous because the bug is still there and shows up later under load.
  3. (3) Two threads that read the same old value both write back the same new value, so one increment is lost. Many updates are lost because each thread usually reads a value that another thread has already made stale.
  4. (4) The with lock: block makes read, add and write behave as one indivisible step. Only one thread can be inside at a time.
  5. (5) and (6) start() lets the threads run; join() waits for each one. Forgetting join() would print the counter before the threads finish.

Part B: threads versus processes (the GIL)

CPython (the standard Python) has a Global Interpreter Lock: only one thread can run Python bytecode at a time. Predict first: will four threads finish four CPU-heavy tasks faster than doing them one after another? Will four processes?

"""Lab 2b - Threads versus processes for CPU-bound work (the Global Interpreter Lock)."""
import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor

TASKS, SIZE = 4, 6_000_000


def work(n):
    """(1) Pure CPU work: no waiting for I/O at all."""
    return sum(i * i for i in range(n))


def timed(label, executor_class):
    start = time.perf_counter()
    with executor_class(max_workers=TASKS) as pool:
        results = list(pool.map(work, [SIZE] * TASKS))
    elapsed = time.perf_counter() - start
    print(f"{label:<22} {elapsed:5.2f} s")
    return results, elapsed


if __name__ == "__main__":          # required on Windows and macOS so new processes can import this file safely
    start = time.perf_counter()
    expected = [work(SIZE) for _ in range(TASKS)]          # (2) baseline: one task after another
    print(f"{'one after another':<22} {time.perf_counter() - start:5.2f} s")
    by_threads, t_threads = timed(f"{TASKS} threads", ThreadPoolExecutor)          # (3) threads share one interpreter lock
    by_processes, t_processes = timed(f"{TASKS} processes", ProcessPoolExecutor)   # (4) each process has its own interpreter
    print("all three methods give the same answers:", expected == by_threads == by_processes)

Run it with python lab2_gil.py. The tasks are pure calculation with no waiting.

Example output

From a 16-thread Windows PC. Your times will differ, but the pattern should match.

one after another       1.99 s
4 threads               1.91 s
4 processes             0.76 s
all three methods give the same answers: True

What to notice

  • (1) and (2) The task is pure calculation, and (2) is the baseline of running it four times in a row.
  • (3) Threads gave almost no speedup for CPU-bound work, because the interpreter lock lets only one thread compute at a time.
  • (4) Processes were faster (about 2.6× here). Each has its own interpreter and its own lock, so they truly run on different cores. They did not reach 4× because starting processes costs time and the work is split across only four tasks: compare this with Amdahl's law, where the serial part (here, starting up) limits the speedup.
  • Processes do not share memory. Arguments and results are copied between them, which costs time and means they cannot simply update a shared variable. That is the trade-off for their isolation (see Module 7).
  • The if __name__ == "__main__": guard is required on Windows and macOS because new processes re-import the file.

Newer Python: Python 3.13 and later offer an experimental “free-threaded” build without the interpreter lock, and the results of Part B can differ there. The ideas, though (shared memory needs locks; processes isolate), apply to every language.

Common mistakes

  • Trusting a test that passed once. Races are timing-dependent. A passing run proves very little.
  • Locking too little. The lock must cover the whole read-modify-write, not just the write.
  • Locking too much. Holding a lock during slow work (disk, network) makes every other thread wait.
  • Forgetting join(). The main program may print or exit before the work is done.
  • Using threads for CPU-bound work in CPython and expecting a speedup.

Reflection questions (good journal entries)

  1. Explain the unsafe result in your own words, using the three steps read, add and write. Why was the result so much smaller than 8000, not just a little smaller?
  2. A locked counter is correct but each increment now waits for the lock. Using ideas from Amdahl's law, explain how heavy locking can erase the benefit of adding more threads.
